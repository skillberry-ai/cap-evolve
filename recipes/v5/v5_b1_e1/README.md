# recipes/v5/v5_b1_e1

The cap-evolve project config every `v5_b1_e1` task's eval used — copied verbatim, one shared
template rather than 136 near-duplicates.

## What's here

- **`capevolve.yaml`** — the entire per-task project config, byte-identical across all 136 tasks.
  `max_iterations: 0` is the whole story: this is a pure baseline measurement, never an optimizer
  loop. `optimizer_skill`/`optimizer_model`/`algorithm_skill` appear in the file but are inert at
  zero iterations — the scaffolder renders one template for both eval and optimize use.
- **`split_ids.json`** — one representative copy. Every task's real file substitutes its own id
  into `train == val == test`, the same single-task convention as
  [`../../v4/v4_t_e1/`](../../v4/v4_t_e1/README.md). For a baseline arm the degenerate split is
  immaterial: nothing is fit, so there is nothing to leak.

Both are generated by `scripts/parsec/v5/scaffold_eval_projects.py` in the `parsec-intake_v5`
worktree (not committed here, matching the v4 convention for its scaffolder).

## This was a harness sweep, not one `cap-evolve run`

Each task's eval ran as its own `bsub` job on CCC/LSF. `scripts/parsec/v5/run_one_eval.sh` brought
up the parsec simulator stack (5 containers + the `parsec-live` app) in a dedicated per-job lane,
then handed off to `scripts/ccc/run_ccc_experiment.sh --max-iterations 0`, which is what actually
invokes `cap-evolve run`. `scripts/parsec/v5/fan_out.sh` kept 10 jobs in flight across the 136
tasks, one per compute node (podman's graphroot is per-UID-per-host, so two jobs cannot share a
node without corrupting each other's image store).

- **Models:** agent `claude-sonnet-4-6`; simulator LLM `azure/gpt-5.4`. Gateway per this repo's
  documented provider order.
- **Trials:** 5 per task, 680 total, 0 errored.
- **Concurrency:** 10 concurrent jobs; ~9h elapsed for 48.8h of summed task time.
- **Task source:** `rhdp-parsec/v5_2026-10-10/bench-v5-harbor-tasks/` after the `v5_2026-10-12`
  drop was merged into it (136 dirs, no id collisions).
- **Seed installation:** the `v5_2026-10-12` drop's stricter `install_seeds.py`, which additionally
  resets every *undeclared but live* service to empty before each trial. The earlier, laxer version
  left an undeclared service answering from its generic sample `db.json`; with 23 of 68 tasks in
  the first drop declaring 2-3 services, that could let a cross-domain trap task read rows nobody
  authored.

## What is deliberately not here

No `.env`, no raw `.capevolve/` run directories (gitignored in `parsec-intake_v5`), no task
definitions — v5's 136 tasks are their own benchmark checkout, not a per-experiment `tasks.json`.

## No `seed_capability/` here

The skill every task evaluated lives in [`../../../artifacts/v5/seed/`](../../../artifacts/v5/seed/),
not duplicated under `recipes/`, matching the v4 convention. It is verified byte-identical to
parsec commit `28e2c40` — see [`../../../results/v5/v5_b1_e1/summary.md`](../../../results/v5/v5_b1_e1/summary.md)
for why that verification is load-bearing.
