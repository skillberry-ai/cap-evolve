# recipes/v5/v5_g2_e1

The cap-evolve project config every `v5_g2_e1` task's eval used — copied verbatim, one shared
template rather than 136 near-duplicates. Same structure as
[`../v5_b1_e1/`](../v5_b1_e1/README.md); the only real difference is which 8-file bundle each
task's project starts with.

## What's here

- **`capevolve.yaml`** — the entire per-task project config, byte-identical across all 136 tasks.
  `max_iterations: 0`: this is a reuse measurement, not an optimizer loop. The project's starting
  capability is `cand_0004` (`artifacts/v4/v4_g_e1/best`), not the original seed —
  `optimizer_skill`/`optimizer_model`/`algorithm_skill` are inert at zero iterations, same as in
  `v5_b1_e1`.
- **`split_ids.json`** — one representative copy, same degenerate single-task convention as
  [`../v5_b1_e1/`](../v5_b1_e1/README.md): nothing is fit here either, so there is nothing to leak.

Both are generated by `scripts/parsec/v5/scaffold_eval_projects.py` in the `parsec-intake_v5`
worktree (not committed here, matching the v4 and `v5_b1_e1` convention).

## This was a harness sweep, not one `cap-evolve run`

Identical mechanics to [`v5_b1_e1`](../v5_b1_e1/README.md): each task's eval ran as its own `bsub`
job on CCC/LSF, bringing up the parsec simulator stack per lane via
`scripts/parsec/v5/run_one_eval.sh`, handed off to
`scripts/ccc/run_ccc_experiment.sh --max-iterations 0`.

- **Models:** agent `claude-sonnet-4-6`; simulator LLM `azure/gpt-5.4`. Gateway per this repo's
  documented provider order.
- **Trials:** 5 per task, 680 total, all individually audited; 0 unresolved infra problems in the
  final ledger. 4 tasks never produced 5 clean trials in any single run across repeated
  resubmission (recurring gateway hangs); for those, 5 trials were drawn at random from the pool
  of every error-free trial across every attempt on disk for that task — see
  [`../../results/v5/v5_g2_e1/summary.md`](../../results/v5/v5_g2_e1/summary.md).
- **Concurrency:** ramped 5 → 10 → 15 concurrent jobs across several rounds of resubmission.
- **Task source:** same as `v5_b1_e1` —
  `rhdp-parsec/v5_2026-10-10/bench-v5-harbor-tasks/` after the `v5_2026-10-12` drop was merged in
  (136 dirs, no id collisions).

## The skill under test is `cand_0004`, not a seed capability

Every task's project is scaffolded with `artifacts/v4/v4_g_e1/best` installed as its starting
capability, in place of `v5_b1_e1`'s `artifacts/v5/seed/`. `cand_0004` is v4's accepted G2-arm
champion — optimized once, against v4's 34-task set, before this arm ever ran; nothing here
re-optimizes it. **Verified byte-identical** to
[`artifacts/v4/v4_g_e1/best`](https://github.com/skillberry-ai/cap-evolve/tree/parsec-history/artifacts/v4/v4_g_e1/best)
on this branch — see
[`../../results/v5/v5_g2_e1/summary.md`](../../results/v5/v5_g2_e1/summary.md) for why that
verification matters (the discarded `v5_t1_e1` run installed the wrong candidate from the same
directory tree without checking).

## What is deliberately not here

No `.env`, no raw `.capevolve/` run directories (gitignored in `parsec-intake_v5`), no task
definitions, and no `artifacts/v5/v5_g2_e1/` — the skill is `artifacts/v4/v4_g_e1/best`, reused
by reference, not duplicated.
