# recipes/v5/v5_t1_e1

The cap-evolve project config every v5_t1_e1 task's eval used — copied verbatim, one shared
template rather than 68 near-duplicates.

## What's here

- **`capevolve.yaml`** — the entire per-task project config, byte-identical across all 68 tasks
  (confirmed via `diff` against a second task during this doc's writing; unlike v4_t_e1's copy,
  this one doesn't even have a per-task header comment to differ). `max_iterations: 0` is the whole
  story — this is a pure baseline measurement, never an optimizer loop:
  ```yaml
  optimizer_skill: claude-code
  optimizer_model: claude-opus-5
  algorithm_skill: hill-climb
  target_model: claude-sonnet-4-6
  capabilities: [system-prompt]
  split_ids_file: split_ids.json
  num_trials: 5
  max_iterations: 0
  max_usd: 50.0
  ```
- **`split_ids.json`** — one representative copy; every task's real file substitutes its own task
  id into `train == val == test`, same single-task-tuning design as v4_t_e1 (no held-out split
  this phase).

Generated by `scripts/parsec/v5/scaffold_eval_projects.py` in the `parsec-intake_v5` worktree (not
committed here, same convention as v4's `scaffold_projects.py`).

## This was a harness sweep, not a `cap-evolve run` you'd invoke by hand

Each task's eval ran as its own `bsub` job on CCC/LSF:
`scripts/parsec/v5/run_one_eval.sh` brought up the parsec simulator stack (5 containers + the
`parsec-live` app) in a dedicated per-job lane, then handed off to
`scripts/ccc/run_ccc_experiment.sh --max-iterations 0 --spec capevolve.yaml --project <project>`,
which is the thing that actually calls `cap-evolve run`. `scripts/parsec/v5/fan_out.sh` submitted
these jobs 5-, then 10-, then 13-at-a-time (ramped, not jumped, per the established CCC discipline)
across all 68 tasks, each pinned to its own compute node (podman's graphroot is per-UID-per-host, so
two jobs can't share a node).

- **Model:** target `claude-sonnet-4-6` via the ETE-INT/ETE gateway order this repo's
  `CLAUDE.md` documents for benchmark CI; simulator LLM `azure/gpt-5.4`.
- **Trial timeout:** 20 min/trial (adapter-level cap); task timeout well under that in every run.
- **Concurrency:** ramped 5 → 10 → 13 concurrent jobs across the sweep.
- **Task source:** `rhdp-parsec/v5_2026-10-10/bench-v5-harbor-tasks/` (the isolated v5 benchmark
  checkout — see `results/v5/README.md` for why it's a from-scratch rebuild, not a v4/h4 copy).

The adapter, lane-per-job design, and the two genuine setup bugs found and fixed while bringing
this sweep up (broken `_run/skills/` symlinks across the podman bind-mount boundary; a missing
`.env` in the fresh worktree) are documented in the `parsec-intake_v5` worktree's own session
record, not duplicated here.

## What is deliberately not here

Same exclusions as v4's recipes: no `.env`, no raw `.capevolve/` run directories (gitignored in
`parsec-intake_v5`), no task definitions (v5's 68 tasks are their own harbor benchmark plugin
checkout, not a per-experiment `tasks.json`).
