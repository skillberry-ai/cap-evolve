# spreadsheet-helpers

No helper scripts exist yet. This file holds hard-won procedural rules for spreadsheet manipulation tasks.

## Interaction protocol (critical)
- Reply with **exactly one fenced ```python code block** per round. Never use XML/tool-call syntax, never put code outside the block, never put prose outside the block — malformed replies waste rounds and can cause the output file to never be written.
- **Every reply must contain code; an empty reply or prose-only reply executes nothing.** Never send a "final summary" round without a code block — the harness only runs code. The way to finish is: run your last verification code block, and only when the next prompt returns do you stop (no code block at all is what ends the session).
- Every write must end with `wb.save(output_path)` in the same round. A round that computes but does not save is worthless: a missing output file scores 0 regardless of correct reasoning.
- **Copy `output_path` character-for-character from the task message.** A single transcribed digit difference (e.g. `1000002` instead of `1050002`) silently writes the file to a nonexistent expected location and the whole task scores 0 even though every computed value was correct. Never retype paths; if you reference them across rounds, copy from your earlier verified block. If `wb.save(output_path)` raises because a directory does not exist, `os.makedirs(os.path.dirname(output_path), exist_ok=True)` first, then save again.
- Verification prints are your only feedback channel: print the answer-position values AND your exact output path each verification round so path typos are caught.

## Procedure
1. **Inspect first**: open the file with `openpyxl.load_workbook(path)` (NOT `data_only=True`) and print the target sheet's cells, sheet names, and formulas near the answer range. One inspection round is cheap; wrong assumptions are fatal. Print a full small-region dump (values AND types) — many failures come from assuming a header is in one row when it is actually one row lower.
2. **Solve**: compute or write values/formulas.
3. **Verify every time**: re-open `output_path` in a fresh round and print the values in `answer_position` before declaring done. Never re-run identical "solution" code repeatedly — if verification fails, change the code.

## Domain facts and pitfalls
- **Never rebuild the workbook with `pd.ExcelWriter` from DataFrames.** That drops formulas, formatting, merged cells, and other sheets, and replaces the whole file — a guaranteed mismatch. Always `wb = openpyxl.load_workbook(original_path)`, modify only the answer cells, and `wb.save(output_path)`. If pandas reads are slow or sheets error out, fall back to openpyxl `iter_rows` immediately rather than piling up try/except pandas fallbacks that time out (60s timeouts killed whole tasks).
- **If a specific expected value is stated in the instruction** (e.g. "the expected 699 for Q2"), treat it as ground truth: compute the target cell, compare, and if it disagrees, re-derive your criteria (wrong column, wrong criteria row, too many rows summed, missing a positivity/extra filter) BEFORE saving. Do not save values you know contradict a stated example.
- **"HIGHER than expected" scorer feedback means you summed too broadly**: wrong criteria row, wrong filter column, or included rows the expected output excludes. Also: cells whose expected value equals their ORIGINAL input must be left untouched — "leave unchanged" is an answer. Do not overwrite a whole answer range with your computed values when only some cells should change; compute each cell, and where the instruction's logic does not call for a change, keep the original value.
- **Do not round-trip through pandas for writing.** Use pandas only for reading/aggregating if convenient, then write results back through the openpyxl workbook object. `df.to_excel` rewrites sheets and loses everything else.
- **Sheet names may have trailing spaces** (e.g. `'SANDBOX '`). `wb['SANDBOX']` raises `KeyError` while the preview shows "SANDBOX". Always list `wb.sheetnames` and match exactly (strip-aware: try exact first, then a `.strip()` match).
- **openpyxl is 1-indexed; pandas is 0-indexed and treats the first row as header.** Cell `K6` is `ws.cell(row=6, column=11)` / `ws['K6']`; pandas `df.iloc[5, 10]` if the preview's row 0 is the header. Convert carefully — indexing mistakes are the most common wrong-value cause. Also, if the preview's first displayed row is `NaN`s, the real content is further down: the pandas header row in the preview maps to openpyxl row 2, and preview row *i* maps to openpyxl row *i+2* in that case. Never hardcode a header row from the preview — scan rows 1-10 with openpyxl and find the label yourself.
- **`load_workbook(path)` returns formulas; `load_workbook(path, data_only=True)` returns cached values.** If source cells contain formulas (e.g. Points columns computed by IF from Place columns), the plain load gives formula strings, not numbers. Load with `data_only=True` to read cached results, or evaluate the underlying logic yourself.
- **The user's stated formula intent may need re-interpretation.** When an instruction says "the formula should sum X based on criteria", read the actual criteria cells at the actual row of the target cell (e.g. for target K6, criteria are typically I6/J6, not I3/J3 — check the surrounding table layout and which rows are populated). Verify against any manually entered example total visible in the sheet; if your computed value disagrees with a known-good sample in the file, re-derive the criteria before saving. When the scorer says a value is "HIGHER than expected", you likely summed too many rows or used the wrong criteria row.
- **Prefer writing live Excel formulas** when the task asks "write a formula" (e.g. `=SUMIFS(sum_range, crit_range1, crit1, crit_range2, crit2)` with proper `$` anchoring like `B$2` / `$A5` for fill-down/across grids). Also apply requested number formats (e.g. `'"$"#,##0.00'` for Currency) via `cell.number_format`. But when the instruction only asks for the *result* (values populated based on a lookup), writing the computed literal values is acceptable and safer. When a task describes OR-logic across multiple selectable criteria (e.g. up to 3 regions with an "All" option), read the actual selection cells from the sheet and compute: if "All" is selected (or selections are blank-with-All-default), sum across all matching rows; otherwise sum only matching selected values, skipping empty selection cells.
- **When matching a lookup key (dates, months, labels)**, compare types carefully: a cell may hold a `datetime` while your key is a string. Normalize both (e.g. compare `.date()`/`str()` forms) and search the actual header row found by inspection, not the row you assumed from the preview. If an exact match fails, print the candidate cells with their types before retrying.
- **Moving columns/rows**: use `ws.insert_cols(idx)` / `ws.delete_cols(idx)` rather than manually shifting cells — manual shifting with `ws.cell(row, col+1).value = ...` does NOT move styles and can silently leave the sheet half-modified (values shifted but formatting not). After `insert_cols`, remember the original source column index shifts by +1 if it was to the right of the insertion point; compute the delete index from the shifted geometry.
- **Copying cell styles requires `copy.copy`**: `cell.font` etc. are `StyleProxy` objects and assigning them to another cell raises `TypeError: unhashable type: 'StyleProxy'`. Use `from copy import copy; target.font = copy(source.font)` (same for `border`, `fill`, `number_format` needs no copy). Better: use `ws.move_range` or insert/delete column operations that carry formatting automatically.
- **Respect the exact target range**: only put values where `answer_position` says. Do not write into cells past the end of the answer range even if the source data extends further — "a cell holds a value where the expected output has none" is scored as a mismatch, as are empty cells where values are expected. Blank cells in a source column should map to blank (or be skipped) exactly as the expected layout dictates; when in doubt, the expected output usually contains values only where the source column had values. For extraction/filter tasks, the answer range size tells you the expected row count — if your filter yields fewer rows than the range has cells, your criteria are too strict (e.g. the prefix list may match more variants than the literal examples suggest); if more, too loose.
- **Preserve the rest of the workbook**: load the original, modify only `answer_position` cells (plus whatever structural edits the task requires), save to `output_path`. Do not rebuild the sheet from a pandas DataFrame — that drops formulas, formatting, and other sheets.
- **Multi-criteria lookups** (month + category grids) need `SUMIFS`, not `SUMIF`; the classic "April totals in the March column" bug comes from matching on the wrong column or ignoring one criterion.
- **Deleting matched rows across sheets**: collect the row indices to delete first, deduplicate, then delete in descending row order so indices don't shift; match keys with type-aware comparison (invoice numbers may be int on one sheet, string on the other — normalize via `str(...).strip()` before comparing, and amounts via `round(float(...), 2)`).
- **Repeated identical executions are a failure mode.** If the same code block runs successfully several times with no output, you are stuck: instead verify the saved file by printing `answer_position` values and either finish (no code block) or fix something concrete. If verification shows wrong cells, restart from the ORIGINAL `spreadsheet_path` (not the output) and change the approach — re-running the same transform on the already-transformed output compounds errors.
