- What to try next iteration: the round's one resolved regression (41978) shows the real lever for round 2 — **prose advice in prompt.md §3 that the trace shows was never exercised means the FORM was wrong, not the content**. The "reproduce the workbook's own worked example first" rule existed as prose and was skipped; it needs to become a numbered step inside the CHECK recipe. Generalize: when a cluster survives an edit, first ask whether the agent ever ran the rule before rewriting what the rule says.

## Iteration r3_decide (round 3) — ACCEPTED, new champion 0.8875
- **The strategy that broke the plateau:** after a flat round 2, I changed the *kind* of edit rather than its content. Rounds 1–2 were facts ("a formula is not a number", "the clause beats the example"); round 3 was a control-flow procedure ("when you don't know, implement both readings and let the file's own numbers choose"). Found by clustering on the agent's own hedge prose instead of on grader feedback: 4 of 7 remaining failures had `usually` / `ambiguous` / `fallback` / `is often used` in a comment immediately before the wrong write. **Generalize: when consecutive fact-shaped rounds come out flat, cluster on the agent's reasoning tokens, not on the failure strings — the failure strings tell you where it went wrong, the reasoning tokens tell you what kind of rule is missing.**
- **Two failures that are each other's mirror image are a signal about edit SHAPE.** 33722 invented a value where gold had a real one; 5835 refused to write where gold extended the sheet's own convention. Same decision point, opposite errors — so no fact could fix both, and that is exactly the situation where a procedure wins. Worth checking for explicitly: if two tasks in a cluster fail in opposite directions, stop writing facts.
- **`provisional` + `grow.py` is the move for a tie, and I nearly mis-booked it.** The first gate came back `verdict: reject`, `verdict_stable: true` — but with `gate_delta 0.05263` against `gate_threshold 0.05263`, i.e. *exactly* the bar, needing strictly greater, on 3 fixed / 0 broken. A reject asserts the edit was refuted; that would have been a false statement and would have incremented STALL and filed a working edit in rejected.jsonl. `--decision provisional` books nothing, snapshots the candidate, and lets `grow.py --add-trials 1` pool trials onto the SAME candidate: pooled 0.8875 at n=40, Δ +0.1125 > 0.0551, `promote`. **Read `gate_delta` against `gate_threshold` numerically before trusting the verdict word — `verdict_stable: true` means the verdict did not flip between control replicates, NOT that the edit was refuted.**
- **The split's resolution is now the binding constraint, and this is the run's main structural limit.** `resolvable_effect_size` was 0.105 at n=38/1-trial — larger than a 3-task improvement on 40 tasks (0.075). Only 7 val tasks still fail and 3 of them are outside prompt-space (341-40, 535-20 confirmed; 56427 is intermittent infrastructure). So the reachable pool is ~4 tasks ≈ 0.10, and every future round is fighting a bar of comparable size. Any further accept will need either 3+ fixes in one round or 2 trials from the start.
- **Screen-then-fix, not screen-then-shrug.** The screen flagged `353-29` and the flag was real: my new "silence is an answer too" rule over-filled by exactly one row. Because I had pre-computed which passing tasks depend on PRESERVING originals (6 of 31, with cell counts), the flag was immediately interpretable; I bounded the rule ("scope ends where the DATA ends") and it was clean on full val. **A screen's value is not only kill/promote — it is a cheap localizer for a regression your own new rule is about to cause. Always seed the screen's `--ids` with the tasks your edit could plausibly harm, not just the ones it targets.**
- **Drift is systematic here, not noise:** +0.0671 (round 2) and +0.0712 (round 3) between the stored parent and a concurrent byte-identical control. grow.py's pooled gate uses the STORED parent, so its +0.1125 is optimistic by roughly that much. I booked the accept on the drift-free evidence (3 fixed / 0 broken vs both replicates) and wrote the caveat into the journal. **Any future round reading `best_val 0.8875` should treat it as "best text so far by ~2–3 tasks", not as +0.11 over seed.**
- **Pacing:** 3 rounds booked (1 accept, 1 reject, 1 accept), 5 remaining. Cost so far: full-val gate ~36 min, growth ~30 min, 9-task screen ~22 min. A round that screens, gates and grows is ~90 min, so ~4 more full rounds fit. Keep `--concurrency 8 --max-parallel 4` fixed (round 2's drift from `--max-parallel 2` was flagged; round 3 matched it and the warning cleared).
- **What to try next round:** `46646`'s calendar bug is the cleanest remaining prompt-space target, and it is now a *form* problem — the rule ("use `calendar.monthrange`, never a literal 28") is present in both files as of this champion and demonstrably did not fire. Restating it is refuted in advance. The next attempt should make it a REQUIRED PRINT in the READ step (print every date-derived denominator with the year it came from) rather than another piece of advice, on the round-1 principle that an unexercised rule means the form was wrong.

## From r4_silent — on the search process

- **Screen subsets must be seeded with the blast-radius list, every time, not just when the edit
  looks risky.** r4_silent's screen 2 promoted at Δ̄ +0.10 with only 11842 flagged; the full gate
  then found 13-1 and 353-29 broken. 353-29 had been in screen 1 (and I fixed it), but 13-1 — the
  single most preserve-dependent task in the run, 120 original cells inside `answer_position` — was
  in neither subset. A screen that omits the tasks an edit can plausibly damage does not screen the
  edit; it advertises it. The 6-task subset cost 20 min and bought a false positive.
- **Iterating on a screen is cheap but it is not free of bias.** Two corrective edits between screen
  1 and screen 2 fixed exactly the tasks that were IN the subset (33722: 30 turns → 5; 353-29 →
  1.0) and the result generalized to neither. Fixing what the screen shows you, then re-screening
  the same ids, measures how well you fit 6 tasks.
- **Next round should change SURFACE, not just form.** Rounds 2–4 all edited prompt.md's body prose
  (r2 rejected, r3 accepted, r4 rejected). Per the round-3+ precondition, and because the two live
  targets left (the 30-turn loop; anchor-cell choice on 46646) are both about *when the agent stops
  or commits*, the untried surface is the interaction contract in task_template.md — the text the
  agent reads FIRST and as a user instruction rather than as reference material. r3_decide's
  accepted diff touched task_template.md only lightly.

  round because both PASSED the screen and 353-29 then broke on full val. At 1 trial the screen sees

## After round 7 — about the search process

**The strategy that stalled, named precisely.** Rounds 4–7 all failed the same way: I found a real
failure in a trace, wrote correct and safe text about it, and lost 0.05–0.10. The text was never
wrong. What was wrong was the implicit model that the prompt is an accumulator — that adding a true
rule adds its value. On this reader it is closer to zero-sum: four of the last four additions
displaced attention from the reading/scoping work that decides these tasks, and the one accept (r3)
worked because it **replaced** a decision procedure rather than appending a rule, and it **deleted**
a harmful bullet in the same edit.

**The sizing discipline I should have had from round 4.** Before proposing, compute the target
cluster's base rate over all stored rollouts and multiply by the split size. r7's target was 0.24%
of rollouts ≈ 0.09 tasks ≈ Δ 0.002 on a noise floor of 0.03–0.08 — unwinnable arithmetic, visible
before spending anything. I had all the data to compute it and did not. Rounds 4, 5 and 6 would each
have survived this filter (their clusters were 3–6 tasks), so it is not a universal veto; it is
specifically the filter that would have saved round 7.

**Screening earns its keep; I under-trusted it.** The screen caught a value-destroying invariant on
the candidate's own target task for 9 rollouts instead of 120, and then correctly killed the path fix
twice before the gate confirmed it. In a 5-round stretch with no accept, the screen was the most
informative instrument used, and the one round where I overrode it cost a full gate.

**What a next round should try, if one is available.** Not another addition. The two forms with
evidence behind them are (a) a **replacement** of an existing section with a shorter version that
says the same thing — testing the displacement hypothesis directly by REMOVING words, and (b) a
**deletion-only** candidate: cut the lowest-value paragraphs from the champion and gate it. Both are
structurally different from everything in rejected.jsonl, which is uniformly additive. Deletion is
also the only form whose blast radius shrinks rather than grows with size.

**Budget reality.** 7 rounds spent, 1 accept, stall high. The champion r3_decide at 0.8875 stored
(~0.86 pooled) sits ~0.09 below an effective ceiling of 0.95, over ~6 tasks, against a per-round
noise floor of 0.03–0.08. Under those numbers a genuine 2-task improvement is at the edge of
resolvability at n=40/1 trial, so a future run should either buy trials (grow.py) on any candidate
with Δ>0, or accept that the remaining headroom is not resolvable at this measurement budget.

## Round 8 (`r8_cut`) — about the SEARCH PROCESS

**A driver crash mid-round is recoverable, and the recovery is cheap — if the rollouts were already
written.** The session that built and evaluated `r8_cut` died on an `api_error` (`num_turns: 341`)
*after* its val eval finished and *before* it called `commit.py`. The retry driver booked the round
from artifacts alone: the candidate diff, the 120 val rollouts, and `work/round_i7.json` reproduced
the gate exactly via `gate_check.py`, with no re-evaluation. **Process lesson: the rollouts on disk
are the round, not the driver's context.** Because the harness tags rollouts by candidate dir name,
an interrupted round is resumable by any later driver — so the correct response to a crash is to
re-derive the verdict from the run dir, never to re-run the eval (which would REPLACE `t0` and buy no
new evidence) and never to abandon the paid round unbooked. An unbooked round is the one outcome that
loses everything: the iteration is spent, `rejected.jsonl` never learns the edit was refuted, and a
later round can re-propose it.

**What a crash DOES lose, and how to make it lose less.** `PROCESS.md` in the working copy was still
`r2_numeric`'s — the crashed driver had not yet written it. So the edit's *rationale* was
unrecoverable while its *diff and measurement* were fully recoverable. **Suggestion for future
drivers on this loop: write `PROCESS.md`/`JOURNAL.md` for a round at the moment the candidate dir is
prepared (intent is knowable then), not after the gate returns.** The gate numbers can always be
reconstructed; the intent cannot.

**Strategy retrospective over the whole run — which levers were tried, and the shape of the result.**
Eight rounds, one accept (`r1_contract` +0.150, the fenced-reply/output-contract round), one later
accept (`r3_decide` → 0.8875), six rejects. The six rejects were NOT six variations of one idea —
they covered genuinely distinct forms: knowledge recipes (r2), a required-print structural rule (r4),
a harness-aligned stop rule (r5), a scoping reframe (r6), a path-binding mechanical rule (r7), and a
pure deletion (r8). **Three of those six had their mechanism FIRE as designed and still lost** (r4's
print, r5's saves/rollout 3.5→1.6, r7's `saved:` line on 39/40). That is the run's central process
finding: **"the rule fired" and "the rule helped" are independent, and on this benchmark the gap
between them is attention displacement** — every word added to the two files the agent reads first
competes with the reading and scoping work that actually decides these tasks.

**What to try next on a future run of this benchmark, in priority order.**
1. **Raise `num_trials` before proposing anything else.** At 1 trial on a 40-task val the resolvable
   effect is 3-4 tasks. Every round after r1 was measuring an effect smaller than its own instrument.
   This is the single change that would make the remaining prompt search decidable.
2. **Size every cluster by BASE RATE across all rollouts before spending a round** (r7's lesson,
   worth restating as process): expected Δ = base rate × split size. If that is under the noise
   floor, the edit is unmeasurable however real it is.
3. **Stop treating word count as a free variable.** Both directions are now measured and both cost.
   A future round should hold total length fixed and REPLACE text, so the attention budget is
   constant and the edit's content is what varies.
4. **Exclude the known-unfixable tasks from the leverage arithmetic up front**: openpyxl load→save
   float re-serialization vs the grader's `round(x,2)` (not prompt-space) and intermittent sandbox
   500s (environment). They consume 2 of the champion's 4-5 residual val failures, so the true
   addressable headroom on val is ~2 tasks = 0.05, which is *below* the resolvable effect size. That
   arithmetic, computed at round 2 rather than round 8, would have said "this search is instrument-
   limited" six rounds earlier.
