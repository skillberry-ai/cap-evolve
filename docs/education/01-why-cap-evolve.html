The problem: agents fail on real tasks

✗

Policy gaps

The system prompt misses a rule. The agent breaks it on a real case.

✗

Weak tools

A tool returns a vague error. The agent loops or gives up.

✗

Thin skills

A skill package has no script for the hard step. The agent improvises.

Example: τ²-bench airline, a seed policy + tools scored 0.536 mean reward over 50 tasks. Almost half the work is lost.

Source: docs/RESULTS.md (τ²-Bench airline, fit-metric run)

[1:30–2:30] Let us start with the problem. An LLM agent is a model plus things it reads: a system prompt, tools, maybe MCP servers, maybe skill packages. On real benchmarks, agents fail a lot.

The failures have typical shapes. The prompt misses a rule, so the agent breaks a policy. A tool returns a vague error, so the agent loops. A skill package explains a task but has no script for the hardest step, so the agent improvises and gets it wrong.

A concrete example from our own results. On τ²-bench airline, a customer-service benchmark, the seed policy and tools scored 0.536 mean reward over all 50 tasks. That is close to half the tasks lost. Note that a better model is not always an option. You may be tied to one model for cost or policy reasons. So the question is: can we fix the agent without changing the model?

[1:30–2:30] נתחיל מהבעיה. סוכן LLM הוא מודל ועוד דברים שהוא קורא: system prompt, כלים, אולי שרתי MCP, אולי skill packages. על benchmarks אמיתיים, סוכנים נכשלים הרבה.

לכשלונות יש צורות קבועות. ב-prompt חסר כלל, אז הסוכן מפר מדיניות. כלי מחזיר שגיאה לא ברורה, אז הסוכן נכנס ללולאה. skill package מסביר את המשימה אבל אין בו סקריפט לשלב הקשה, אז הסוכן מאלתר וטועה.

דוגמה קונקרטית מהתוצאות שלנו. ב-τ²-bench airline, benchmark של שירות לקוחות, ה-policy והכלים ההתחלתיים קיבלו reward ממוצע של 0.536 על כל 50 המשימות. זה קרוב לחצי מהמשימות שהולכות לאיבוד. ושימו לב, מודל חזק יותר זה לא תמיד אופציה. לפעמים אתם קשורים למודל אחד בגלל עלות או מדיניות. אז השאלה היא: אפשר לתקן את הסוכן בלי לשנות את המודל?

↓
Edit the promptone small tweak at a time
↓
Re-run the same tasksthe ones you just looked at
↓
"It went up"one noisy run, no error bar

What goes wrong

  • Slow: hours per idea
  • Tuned and reported on the same tasks
  • Noise looks like progress
  • Old wins break without anyone noticing
  • No record of what was tried

[2:30–3:30] The usual fix is hand-tuning. An engineer reads a few failed traces, edits the prompt, re-runs, and looks at the number. This has two big problems.

It is slow. Each idea costs hours of reading and re-running.

And it is not measured honestly. You tune on the same tasks you report. One run of a stochastic agent is noisy, so a random bump looks like progress. A fix for task 12 can silently break task 30. And nobody keeps a record of what was tried and rejected, so the next person tries it again.

Example: if you try ten prompt variants and keep the best-looking one, it is often best by luck. The number climbs, but the agent did not get better. cap-evolve is built to fix both problems: automate the loop, and make the measurement honest by construction.

[2:30–3:30] הפתרון הרגיל הוא כיוונון ידני. מהנדס קורא כמה traces שנכשלו, משנה את ה-prompt, מריץ שוב ומסתכל על המספר. יש בזה שתי בעיות גדולות.

זה איטי. כל רעיון עולה שעות של קריאה והרצה.

וזה לא נמדד ביושר. מכווננים על אותן משימות שעליהן מדווחים. ריצה אחת של סוכן סטוכסטי היא רועשת, אז קפיצה אקראית נראית כמו התקדמות. תיקון למשימה 12 יכול לשבור בשקט את משימה 30. ואף אחד לא שומר תיעוד של מה נוסה ונדחה, אז האדם הבא מנסה את זה שוב.

דוגמה: אם מנסים עשר גרסאות של prompt ושומרים את זו שנראית הכי טוב, הרבה פעמים היא הכי טובה במקרה. המספר עולה, אבל הסוכן לא השתפר. cap-evolve בנוי לפתור את שתי הבעיות: לאוטמט את הלולאה, ולהפוך את המדידה לכנה מעצם המבנה.

The core idea: optimize what the agent reads

[3:30–4:45] This is the core idea. An agent is a model plus what it reads. cap-evolve leaves the model weights alone. No fine-tuning, no gradients. It edits the files the agent reads at runtime.

We call each kind of file a capability. There are four capability types, and each has its own skill in the library: system-prompt, tools for executable tool code, mcp-tool for an MCP tool surface, and skill-package for an Agent Skill folder with SKILL.md, references and scripts.

You can pick one or several and optimize them together. For example, the τ²-bench run used [system-prompt, tools]: the optimizer rewrote the airline policy and also edited the Python tool code.

Why this matters: it works with any model, including closed API models you cannot train. And every change is a readable diff you can review.

[3:30–4:45] זה הרעיון המרכזי. סוכן הוא מודל ועוד מה שהוא קורא. cap-evolve לא נוגע במשקלות של המודל. אין fine-tuning ואין gradients. הוא עורך את הקבצים שהסוכן קורא בזמן ריצה.

לכל סוג קובץ כזה אנחנו קוראים capability. יש ארבעה סוגים, ולכל אחד skill משלו בספרייה: system-prompt, tools לקוד של כלים, mcp-tool למשטח כלים של MCP, ו-skill-package לתיקיית Agent Skill עם SKILL.md, references וסקריפטים.

אפשר לבחור אחד או כמה ולעשות להם אופטימיזציה ביחד. למשל, הריצה על τ²-bench השתמשה ב-[system-prompt, tools]: ה-optimizer כתב מחדש את ה-policy של חברת התעופה וגם ערך את קוד ה-Python של הכלים.

למה זה חשוב: זה עובד עם כל מודל, כולל מודלים סגורים דרך API שאי אפשר לאמן. וכל שינוי הוא diff קריא שאפשר לבדוק.

"A tool body the model cannot skip beats a sentence it can forget."

Source: README.md, docs/ARCHITECTURE.md, skills/capabilities/

[4:45–5:45] Here are the four capabilities with their edit limits. Each capability skill gives the optimizer a menu called "What you can change here" and a set of boundaries.

For a system prompt, the optimizer may rewrite, merge and add rules, but it must never drop a rule that is still needed. For tools, it may edit the actual Python code, improve error messages, and wrap or swap a tool, but never just delete one. For MCP, only safe edits: docs, examples, and which tools are exposed. For a skill package, it may change the whole folder.

The quote at the bottom is from the architecture doc, and it is a key design opinion. If a policy must always hold, enforce it in tool code. For example, a tool that refuses to cancel a non-refundable ticket is stronger than a prompt line that asks the model to check. The τ²-bench run grew tools.py from 593 to 832 lines for this reason.

[4:45–5:45] אלה ארבעת ה-capabilities עם גבולות העריכה שלהם. כל capability skill נותן ל-optimizer תפריט שנקרא "What you can change here" וסט של גבולות.

ב-system prompt, ה-optimizer יכול לכתוב מחדש, לאחד ולהוסיף כללים, אבל אסור לו למחוק כלל שעדיין נחוץ. בכלים, הוא יכול לערוך את קוד ה-Python עצמו, לשפר הודעות שגיאה, ולעטוף או להחליף כלי, אבל לא סתם למחוק אותו. ב-MCP רק עריכות בטוחות: תיעוד, דוגמאות, ואילו כלים חשופים. ב-skill package הוא יכול לשנות את כל התיקייה.

הציטוט למטה הוא מתוך מסמך הארכיטקטורה, והוא עמדת תכנון חשובה. אם מדיניות חייבת להתקיים תמיד, אוכפים אותה בקוד של הכלי. למשל, כלי שמסרב לבטל כרטיס שלא ניתן להחזר חזק יותר משורה ב-prompt שמבקשת מהמודל לבדוק. בריצה על τ²-bench הקובץ tools.py גדל מ-593 ל-832 שורות בגלל זה.

Bring your agent and your eval

You write one small adapter. Three required methods:

tasks(split)                   -> list[Task]
    # your eval cases: 'train'|'val'|'test'|'all'
run_target(task, ctx, *, seed) -> Rollout
    # run your agent with the candidate live
score(task, rollout)           -> Score
    # reward in [0,1] + feedback, never the gold

Source: README.md, docs/ADAPTER_CONTRACT.md

The core gives you the rest

  • Splits and trials
  • The significance gate
  • pass^k and error bars
  • The sealed test split
  • Memory across iterations
  • Dashboard and reports

[5:45–6:45] The second promise is "bring your agent and your eval". cap-evolve does not ship its own agent framework. You already have an agent and some way to score it. You connect them through one small class called an adapter.

It has three required methods. tasks(split) returns your eval cases. run_target(task, ctx, seed) runs your agent once on one task, with the candidate files live. The result is a Rollout. score(task, rollout) returns a reward between zero and one, plus text feedback for the optimizer. The feedback must never leak the gold answer.

Everything else comes from the core: splits, trials, the gate, pass^k, the sealed test, memory, the dashboard. For common cases you do not even write the adapter. There are templates for JSONL, HuggingFace, tau2-bench, SWE-bench and SkillsBench. Chapter 4 covers the adapter contract and its optional hooks in detail.

[5:45–6:45] ההבטחה השנייה היא "תביאו את הסוכן שלכם ואת ה-eval שלכם". cap-evolve לא מגיע עם framework של סוכנים משלו. כבר יש לכם סוכן ודרך כלשהי לתת לו ציון. מחברים אותם דרך מחלקה קטנה אחת שנקראת adapter.

יש לה שלוש מתודות חובה. tasks(split) מחזירה את מקרי ה-eval. run_target(task, ctx, seed) מריצה את הסוכן פעם אחת על משימה אחת, כשקבצי ה-candidate פעילים. התוצאה היא Rollout. score(task, rollout) מחזירה reward בין אפס לאחת, ועוד feedback טקסטואלי ל-optimizer. ה-feedback אסור שידליף את התשובה הנכונה.

כל השאר מגיע מה-core: splits, trials, ה-gate, pass^k, ה-test החתום, memory וה-dashboard. במקרים נפוצים אפילו לא כותבים adapter. יש templates ל-JSONL, HuggingFace, tau2-bench, SWE-bench ו-SkillsBench. פרק 4 מפרט את חוזה ה-adapter וה-hooks האופציונליים שלו.

The loop at a high level

[6:45–8:00] This is the loop. One pass is called an iteration.

Evaluate: run the current best version of the files on the validation split. Diagnose: read the failed traces and group them into failure clusters. Propose: a coding agent, which we call the optimizer, edits the files. The result is a new candidate. Gate: score the candidate on val and accept it only if the gain is bigger than k standard errors. Commit: the accepted candidate becomes the new best and is saved as a git commit.

A rejected candidate is not wasted. It goes into memory, so the optimizer will not propose it again. The optimizer also sees which tasks each earlier edit broke and fixed, so it protects the wins.

The loop stops on a budget: max_iterations, stall (consecutive rejects), or max_usd. Then finalize scores the best candidate on the sealed test split exactly once. Chapter 5 walks one iteration step by step.

[6:45–8:00] זו הלולאה. מעבר אחד נקרא iteration.

Evaluate: מריצים את הגרסה הטובה ביותר הנוכחית של הקבצים על ה-validation split. Diagnose: קוראים את ה-traces שנכשלו ומקבצים אותם לאשכולות כשל. Propose: סוכן קוד, שאנחנו קוראים לו optimizer, עורך את הקבצים. התוצאה היא candidate חדש. Gate: נותנים ל-candidate ציון על val ומקבלים אותו רק אם השיפור גדול מ-k שגיאות תקן. Commit: ה-candidate שהתקבל הופך להיות הטוב ביותר ונשמר כ-git commit.

candidate שנדחה לא הולך לפח. הוא נכנס ל-memory, כדי שה-optimizer לא יציע אותו שוב. ה-optimizer גם רואה אילו משימות כל עריכה קודמת שברה ותיקנה, כך שהוא שומר על ההצלחות.

הלולאה עוצרת לפי תקציב: max_iterations, stall כלומר דחיות ברצף, או max_usd. ואז finalize נותן ציון ל-candidate הטוב ביותר על ה-test split החתום, פעם אחת בדיוק. פרק 5 עובר על iteration אחד צעד אחר צעד.

[8:00–9:00] The loop is one phase of a longer pipeline. There are six phases.

intake does the integration work: it installs the benchmark, wires the adapter, and writes the spec file capevolve.yaml. implement-and-check is a hard gate. The command cap-evolve check refuses to continue until every adapter method is real and score() is deterministic. So you never pay for a run against a stub.

baseline freezes the train, val and test split and scores the seed, which is your unmodified files. algorithm is the loop from the last slide. The default is hill-climb; there are others, covered in chapter 7. finalize scores test once. report writes report.md and a self-contained dashboard.html.

Each phase is a skill. That is why the same pipeline runs on many coding-agent hosts.

[8:00–9:00] הלולאה היא שלב אחד בתוך pipeline ארוך יותר. יש שישה שלבים.

intake עושה את עבודת האינטגרציה: מתקין את ה-benchmark, מחבר את ה-adapter, וכותב את קובץ ה-spec capevolve.yaml. implement-and-check הוא שער קשיח. הפקודה cap-evolve check מסרבת להמשיך עד שכל מתודה ב-adapter אמיתית ו-score() דטרמיניסטית. כך אף פעם לא משלמים על ריצה מול stub.

baseline מקבע את החלוקה ל-train, val ו-test ונותן ציון ל-seed, כלומר לקבצים המקוריים שלכם. algorithm הוא הלולאה מהשקף הקודם. ברירת המחדל היא hill-climb, ויש עוד אלגוריתמים שמכוסים בפרק 7. finalize נותן ציון על test פעם אחת. report כותב report.md ו-dashboard.html שעומד בפני עצמו.

כל שלב הוא skill. בגלל זה אותו pipeline רץ על הרבה hosts של סוכני קוד.

Why "honest" evaluation matters

Fit metric

train == val == test. Shows the loop works. Not a generalization claim. The engine logs a splits_warning.

Held-out

Test ids the optimizer never saw, scored exactly once at finalize. The stronger claim.

These rules live in the Python core, not in editable skill text. An optimizer cannot talk its way around them.

Source: docs/HONEST_EVAL.md, docs/RESULTS.md

[9:00–10:15] Now the most important idea of the project: honest evaluation. The project doc says it plainly: "cap-evolve's one differentiator is that its numbers mean something."

The tasks are split three ways with a fixed seed, and the split is written once to splits.json. The optimizer learns from train. The gate decides only on val; gate.decide raises an error for any other split. Test is sealed: RunDir.consume_test() sets a flag and raises TestSealError on a second access. These rules live in the Python core, not in editable instructions, so an optimizer cannot talk its way around them.

Every result we publish carries one of two labels. A fit metric means train, val and test are the same tasks. It proves the loop works, but it is not a generalization claim. Held-out means test was never seen and was scored once. Chapter 6 is all about this.

[9:00–10:15] עכשיו הרעיון הכי חשוב בפרויקט: הערכה כנה. המסמך של הפרויקט אומר את זה ישר: היתרון היחיד של cap-evolve הוא שהמספרים שלו אומרים משהו.

המשימות מחולקות לשלושה חלקים עם seed קבוע, והחלוקה נכתבת פעם אחת ל-splits.json. ה-optimizer לומד מ-train. ה-gate מחליט רק על val, ו-gate.decide זורק שגיאה על כל split אחר. ה-test חתום: RunDir.consume_test() מדליק דגל וזורק TestSealError בגישה שנייה. הכללים האלה חיים בקוד ה-Python של ה-core, לא בהוראות שאפשר לערוך, כך שה-optimizer לא יכול לעקוף אותם.

Why the gate is Δ > k·SE and not Δ > 0

Δ > 0

Screen many candidates. The best-looking one is often best by luck. The val curve climbs while nothing improved.

Δ > k·SE (paired)

Compare per task, on the same val tasks. Accept only a gain larger than the noise of the measurement.

# capevolve.yaml (scaffold defaults)
gate_mode: paired
gate_k_se: 0.2
num_trials: 1
split_train: 0.5
split_val: 0.25
split_test: 0.25

Source: benchmarks/_scaffold/project/capevolve.yaml, docs/HONEST_EVAL.md

[10:15–11:15] One more honest-eval idea, at a high level. Why not accept any candidate that scores higher?

Because search amplifies noise. If you score twenty candidates on a noisy agent, the top one is often there by luck. A "greater than zero" rule banks that luck, and your val curve rises while the agent stays the same.

So the default gate is paired. For each val task, it takes the difference between candidate and parent. It accepts only when the mean difference is larger than k times its standard error. Comparing on the same tasks cancels out task difficulty, so the test is more powerful.

On the right are the scaffold defaults: paired gate, k of 0.2, one trial, and a 50/25/25 split. With more trials per task, the standard error is real and the gate becomes meaningful. We will see in the demo what happens when it is zero.

[10:15–11:15] עוד רעיון אחד של הערכה כנה, ברמה גבוהה. למה לא לקבל כל candidate שקיבל ציון גבוה יותר?

כי חיפוש מגביר רעש. אם נותנים ציון לעשרים candidates על סוכן רועש, הראשון ברשימה הרבה פעמים נמצא שם במקרה. כלל של "גדול מאפס" שומר את המזל הזה, ועקומת ה-val עולה בזמן שהסוכן נשאר אותו דבר.

לכן ה-gate בברירת מחדל הוא paired. לכל משימת val הוא לוקח את ההפרש בין ה-candidate להורה שלו. הוא מקבל רק כשההפרש הממוצע גדול מ-k כפול שגיאת התקן שלו. השוואה על אותן משימות מבטלת את השונות בקושי בין משימות, כך שהמבחן חזק יותר.

בצד ימין ערכי ברירת המחדל מה-scaffold: gate מסוג paired, k של 0.2, trial אחד, וחלוקה של 50/25/25. עם יותר trials לכל משימה, שגיאת התקן אמיתית וה-gate מקבל משמעות. בדמו נראה מה קורה כשהיא אפס.

[15:15–16:00] Now the demo. toy_calc is the smallest end-to-end proof, and it is also our CI gate.

The "agent" is fake and deterministic. It reads prompt.txt from the candidate folder. If the prompt contains the marker [CALC], it computes the arithmetic correctly. If not, it rambles: "I think 3 + 4 is roughly some number." The scorer is exact match, so the seed prompt scores zero.

The optimizer is the mock backend. It reads mock_script.json, which has one edit: make sure prompt.txt contains the [CALC] line. So the score must rise from 0 to 1, and no model is called. That makes it a perfect first run: zero cost, a few seconds, and it exercises every phase of the real pipeline.

[15:15–16:00] עכשיו הדמו. toy_calc הוא ההוכחה הקטנה ביותר מקצה לקצה, והוא גם שער ה-CI שלנו.

Key takeaways

What it optimizes

What the agent reads: prompt, tool code, MCP surface, skill packages. Never weights.

What you bring

Your agent and your eval, joined by a 3-method adapter.

How it decides

Paired gate on val only. Test sealed and scored once, enforced in code.

How to start

bash benchmarks/toy/examples/calc/run.sh, then open dashboard.html.

[19:40–20:00] Four things to remember.

  • cap-evolve optimizes what the agent reads, not the model.
  • You bring your agent and your eval, through a small adapter.
  • It decides with a paired significance gate on val, and the test split is sealed and scored once. The core code enforces this.
  • You can see the whole thing work today, in two minutes, with toy_calc.

Homework before chapter 2: run toy_calc and open the dashboard. In chapter 2 we name every object you just saw: seed, candidate, champion, trial, and the spec file.
