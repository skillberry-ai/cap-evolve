One command, a tree of processes

Source: core/cap_evolve/cli.py (_cmd_run), core/cap_evolve/harness.py, core/cap_evolve/store.py

[1:30–2:40] First, the big shape. The cap-evolve process does very little work itself. It is a sequencer. It starts each phase as a separate Python process with subprocess.run and waits for it. Each phase script prints one JSON document on stdout, and the CLI parses it.

The algorithm process, here hill-climb/scripts/run.py, is the long one. It imports cap_evolve, loads the adapter in-process, and runs the whole search. From it come more children: one run-optimizer process per iteration, which starts the agent CLI, for example claude -p. It also runs git for each commit.

Beside the tree there are two helpers: an optional follow thread that prints progress, and the dashboard server, started with Popen and never waited for. So a crash in one phase never kills the dashboard.

[1:30–2:40] קודם כל, התמונה הגדולה. התהליך של cap-evolve עצמו כמעט לא עושה עבודה. הוא sequencer. הוא מפעיל כל phase כתהליך Python נפרד עם subprocess.run ומחכה לו. כל סקריפט phase מדפיס מסמך JSON אחד ל-stdout, וה-CLI מפענח אותו.

תהליך האלגוריתם, כאן hill-climb/scripts/run.py, הוא הארוך. הוא עושה import ל-cap_evolve, טוען את ה-adapter בתוך התהליך, ומריץ את כל החיפוש. ממנו יוצאים עוד ילדים: תהליך run-optimizer אחד לכל איטרציה, שמפעיל את ה-agent CLI, למשל claude -p. הוא גם מריץ git בכל commit.

לצד העץ יש שני עוזרים: follow thread אופציונלי שמדפיס התקדמות, ושרת ה-dashboard, שמופעל עם Popen ואף אחד לא מחכה לו. כך קריסה של phase אחד לא מפילה את ה-dashboard.

[2:40–3:35] The console script cap-evolve maps to cli.main. It looks up the command in a table and calls _cmd_run. There is also python -m cap_evolve, a very small entry with three commands for hosts that cannot install the CLI.

_cmd_run finds the skills folder. It needs a built _registry/manifest.json, so a random .claude/skills folder is not picked by mistake. It resolves the spec relative to --project, never to the current directory. Then the budget flags overwrite spec keys, but only when you pass them. An explicit zero still counts.

Some settings travel to the children as environment variables, for example the errored trial policy. This way every evaluation in the run, in every process, uses one rule. The CLI also builds the optimizer command string once, here.

[2:40–3:35] ה-console script בשם cap-evolve ממופה ל-cli.main. הוא מחפש את הפקודה בטבלה וקורא ל-_cmd_run. יש גם python -m cap_evolve, נקודת כניסה קטנה מאוד עם שלוש פקודות, בשביל hosts שלא יכולים להתקין את ה-CLI.

[3:35–4:30] Before the first rollout, the CLI does six cheap things in order. It starts the dashboard first, so you can watch from second zero. It checks the intervention, which is how a candidate is delivered. For an out-of-process stack a dead service would error every rollout, so we fail early.

Then comes the hard gate, run_check, the code half of the implement-and-check phase. It runs in-process. It refuses stubs, an empty task list, or a scorer that is not deterministic.

One honest detail: the run plan prints "intake" as the first step, but _cmd_run never runs it. The comment says intake is the user's job before run. If intake wrote intake.json, its spend is copied into the run. Last, with --follow, a thread starts tailing events.jsonl before the run dir even exists.

[3:35–4:30] לפני ה-rollout הראשון, ה-CLI עושה שישה דברים זולים לפי הסדר. הוא מפעיל קודם את ה-dashboard, כדי שאפשר יהיה לצפות מהשנייה הראשונה. הוא בודק את ה-intervention, כלומר איך candidate נמסר. ב-stack שרץ מחוץ לתהליך, שירות מת היה מכשיל כל rollout, אז עדיף להיכשל מוקדם.

אחר כך מגיע ה-gate הקשיח, run_check, חצי הקוד של phase ה-implement-and-check. הוא רץ בתוך התהליך, ומסרב ל-stubs, לרשימת tasks ריקה, או ל-scorer שאינו דטרמיניסטי.

[4:30–5:25] Here are the four steps that _cmd_run starts in deterministic mode. Baseline creates the run dir. It freezes the split and scores the seed on val. It also copies the capability guidance into the run dir and logs a headroom event. The CLI reads run_dir from its JSON.

The algorithm step gets a long command line built from the spec: trials, gate mode, k_se, store, capabilities, instruction file, protected paths, and so on. A spec key that is absent adds no flag, so old specs give identical command lines.

Finalize scores the champion on test once, and report writes the outputs. Why processes and not function calls? Isolation. A native crash in a scorer kills one step. The CLI then records the signal name, for example SIGSEGV or SIGKILL, instead of a silent stop.

[4:30–5:25] אלה ארבעת הצעדים ש-_cmd_run מפעיל ב-deterministic mode. Baseline יוצר את ה-run dir, מקפיא את ה-split ומודד את ה-seed על val. הוא גם מעתיק את ה-guidance של ה-capability לתוך ה-run dir ורושם אירוע headroom. ה-CLI קורא את run_dir מתוך ה-JSON שלו.

צעד האלגוריתם מקבל שורת פקודה ארוכה שנבנית מה-spec: trials, gate mode, k_se, store, capabilities, קובץ הוראות, protected paths וכן הלאה. מפתח שלא קיים ב-spec לא מוסיף דגל, כך ש-specs ישנים נותנים בדיוק אותה שורת פקודה.

[5:25–6:20] The algorithm script is a thin wrapper. It opens the run dir, sets the process-wide worker count, and builds the shared OptimizerContext. Every algorithm builds the optimizer read-context the same way, so no algorithm gets a thinner prompt than its siblings. It makes the version store, loads the adapter, and wraps the optimizer command into a Python function with optimizer_from_command.

The loop itself is short. At the top of every iteration it asks the run dir if the budget is exhausted. It takes the current best as the parent, renders the prompt, and optionally injects a convergence signal. Then it calls run_step, which does all the real work. If the step is accepted, the candidate's val result becomes the new bar.

gepa and skillopt have their own loops, but they call the same harness pieces. Chapter 7 covers them.

[5:25–6:20] סקריפט האלגוריתם הוא עטיפה דקה. הוא פותח את ה-run dir, קובע את מספר ה-workers לכל התהליך, ובונה את ה-OptimizerContext המשותף. כל אלגוריתם בונה את הקונטקסט של ה-optimizer באותה דרך, כך שאף אלגוריתם לא מקבל prompt דל יותר מהאחרים. הוא יוצר את ה-version store, טוען את ה-adapter, ועוטף את פקודת ה-optimizer בפונקציית Python בעזרת optimizer_from_command.

הלולאה עצמה קצרה. בתחילת כל איטרציה היא שואלת את ה-run dir אם התקציב נגמר. היא לוקחת את ה-best הנוכחי כ-parent, מרנדרת את ה-prompt, ואופציונלית מוסיפה סיגנל convergence. אחר כך היא קוראת ל-run_step, שעושה את כל העבודה האמיתית. אם הצעד התקבל, תוצאת ה-val של ה-candidate הופכת לרף החדש.

[6:20–7:10] Here is run_step, about 450 lines, in nine moves. The candidate id is cand_ plus the next iteration number, padded to four digits. The parent is copied to work/cand_N. The context is injected. If protected paths are set, the eval surface is hashed.

Then the optimizer edits the workdir in place. After it, two cheap checks run before we pay for any rollout: tamper detection and the capability's own validator. Then we evaluate, compute the footprint and the paired deltas, and call the gate. Every candidate is snapshotted, accepted or not, so the dashboard can diff it. Only an accepted one becomes the best. Last, we record the iteration and commit.

Note the error policy. One failure costs one iteration. Three evaluation errors in a row stop the run with a loud error, because that pattern means the environment is broken.

[6:20–7:10] זה run_step, בערך 450 שורות, בתשעה מהלכים. ה-id של ה-candidate הוא cand_ ועוד מספר האיטרציה הבאה, בארבע ספרות. ה-parent מועתק ל-work/cand_N, הקונטקסט מוזרק, ואם מוגדרים protected paths, משטח ההערכה עובר hash.

אחר כך ה-optimizer עורך את ה-workdir במקום. אחריו רצות שתי בדיקות זולות לפני שמשלמים על rollout כלשהו: זיהוי tamper וה-validator של ה-capability עצמו. אז מעריכים, מחשבים את ה-footprint ואת ה-paired deltas, וקוראים ל-gate. כל candidate נשמר כ-snapshot, התקבל או לא, כדי שה-dashboard יוכל להציג diff. רק candidate שהתקבל הופך ל-best. ולבסוף רושמים את האיטרציה ועושים commit.

שימו לב למדיניות השגיאות. כישלון אחד עולה איטרציה אחת. שלוש שגיאות הערכה ברצף עוצרות את ה-run עם שגיאה ברורה, כי הדפוס הזה אומר שהסביבה שבורה.

One iteration as a sequence diagram

[7:10–8:50] Now the same nine moves as a sequence. Read it top to bottom. The loop calls run_step. run_step asks the OptimizerContext to fill the workdir. Then it starts the run-optimizer process and blocks. That process builds the agent command line and starts the agent CLI with its working directory set to work/cand_N. The agent edits files in place, for example it rewrites a prompt section and adds a tool. It ends with a JSON result that includes total_cost_usd.

run-optimizer prints its own JSON with the cost. Back in run_step, the tamper check and the capability validator run. Then evaluate_candidate drives the adapter for all val tasks and trials, and returns a SplitResult. Finally, the gate decides, and the run dir and git store record the result.

Key point: the only network spend is in two places, the agent CLI and the adapter.

[7:10–8:50] עכשיו אותם תשעה מהלכים כ-sequence. קוראים מלמעלה למטה. הלולאה קוראת ל-run_step. run_step מבקש מה-OptimizerContext למלא את ה-workdir. אחר כך הוא מפעיל את התהליך run-optimizer ונחסם. התהליך הזה בונה את שורת הפקודה של ה-agent ומפעיל את ה-agent CLI עם תיקיית עבודה work/cand_N. ה-agent עורך קבצים במקום, למשל משכתב סעיף ב-prompt ומוסיף tool. הוא מסיים עם תוצאת JSON שכוללת total_cost_usd.

run-optimizer מדפיס JSON משלו עם העלות. בחזרה ב-run_step, רצים בדיקת ה-tamper וה-validator של ה-capability. אז evaluate_candidate מפעיל את ה-adapter על כל ה-tasks וה-trials של val, ומחזיר SplitResult. בסוף ה-gate מחליט, וה-run dir וה-git store רושמים את התוצאה.

הנקודה החשובה: הוצאה על רשת יש רק בשני מקומות, ה-agent CLI וה-adapter.

[8:50–9:45] This is the folder the optimizer agent wakes up in. The base is a copy of the parent candidate, which is what it may edit. Next to it is INSTRUCTIONS.md, written by optimizer_from_command just before launch.

guidance/ holds the selected capability skills, the diagnose method, the supporting source files, and a reference for the chosen backend. trajectories/ has only the parent's traces, not every rejected attempt. The memory files are rebuilt from the step events each iteration. Note the clean ownership: LEDGER and RUNMAP are framework facts, JOURNAL and PROCESS are written by the optimizer. At snapshot time all scratch is ignored, so the stored candidate is the capability only.

[10:35–11:35] The optimizer is two processes deep. run-optimizer reads the registry row and fills the template. For claude-code it inlines the prompt text and adds the model. Because the CLI passed --json, it appends the json flag. If the spec sets optimizer_max_turns or optimizer_usd_per_iter, it appends --max-turns and --max-budget-usd. It runs the agent with Popen, reads stdout on the main thread, and drains stderr on a second thread to avoid a pipe deadlock. Then parse_cost finds total_cost_usd. The harness adds it to the optimizer spend, even when the CLI exits non-zero after hitting its cap.

Important: I found no wall-clock timeout on this subprocess in the deterministic path. A hung agent is bounded only by its own turn and dollar caps.

Inside evaluate_candidate()

[11:35–12:30] evaluate_candidate is the one place rollouts happen. If the spec sets budget_reserve, it first reserves the rollouts in state.json and refuses before dispatch when they do not fit. It picks a seed offset from the evidence ledger, so a new tag of the same bytes gets fresh seeds. It logs eval_start and enters the adapter's live() context.

Then there are four generation paths, tried in this order. If the adapter has run_trials, it gets the whole grid in one call. Else run_batch per trial. Else, if workers is above one, the framework thread pool. Else a plain serial loop.

Whatever the path, scoring and persistence go through _persist_trial, serially, in task order. That is why a parallel run gives byte-identical numbers. At the end the ledger is updated, spend is charged, and an evaluate event closes the bracket.

[11:35–12:30] evaluate_candidate הוא המקום היחיד שבו קורים rollouts. אם ה-spec מגדיר budget_reserve, הוא קודם שומר את ה-rollouts ב-state.json ומסרב לפני השליחה אם הם לא נכנסים בתקציב. הוא בוחר seed offset מתוך ה-evidence ledger, כך ש-tag חדש של אותם bytes מקבל seeds חדשים. הוא רושם eval_start ונכנס ל-context של live() של ה-adapter.

אחר כך יש ארבעה מסלולים ליצירת rollouts, לפי הסדר הזה. אם ל-adapter יש run_trials, הוא מקבל את כל הגריד בקריאה אחת. אחרת run_batch לכל trial. אחרת, אם workers גדול מאחד, ה-thread pool של ה-framework. אחרת לולאה סדרתית פשוטה.

לא משנה איזה מסלול, הניקוד והשמירה עוברים דרך _persist_trial, באופן סדרתי ולפי סדר ה-tasks. בגלל זה run מקבילי נותן בדיוק אותם מספרים. בסוף ה-ledger מתעדכן, ההוצאה נרשמת, ואירוע evaluate סוגר את הסוגריים.

[12:30–13:25] Here are the post-edit checks in order. The tamper seal is opt-in through protected_paths. Files are hashed before the optimizer runs and verified after. Timeline: who is running during one iteration

[14:10–15:30] This is the picture to remember. Time goes left to right through one iteration. The CLI's main thread is blocked the whole time. The follow thread and the dashboard server only read files, so they can never slow down or corrupt the run.

The algorithm process does the inject quickly, then waits for the optimizer for minutes. During that time two more processes are alive: run-optimizer with its stderr drain thread, and the agent CLI, which may start its own subagents. When the agent exits, the checks run. Then evaluation starts. With workers above one, a thread pool generates rollouts, while the main thread waits. Scoring then happens on the main thread. Finally the gate, the record, and a few short git processes.

Notice: optimize and evaluate never overlap in the default loop. Only HC-2 runs several proposals at once.

[14:10–15:30] זו התמונה שכדאי לזכור. הזמן זורם משמאל לימין לאורך איטרציה אחת. ה-thread הראשי של ה-CLI חסום כל הזמן. ה-follow thread ושרת ה-dashboard רק קוראים קבצים, ולכן הם לא יכולים להאט או לקלקל את ה-run.

תהליך האלגוריתם עושה את ה-inject מהר, ואז מחכה ל-optimizer כמה דקות. בזמן הזה חיים עוד שני תהליכים: run-optimizer עם ה-thread שמרוקן את stderr, וה-agent CLI, שיכול להפעיל subagents משלו. כשה-agent יוצא, רצות הבדיקות. אחר כך מתחילה ההערכה. עם workers גדול מאחד, thread pool מייצר rollouts, וה-thread הראשי מחכה. הניקוד קורה אחר כך ב-thread הראשי. ולבסוף ה-gate, הרישום, וכמה תהליכי git קצרים.

שימו לב: בלולאה הרגילה optimize ו-evaluate אף פעם לא חופפים. רק HC-2 מריץ כמה הצעות במקביל.

[16:20–17:10] Now, what is shared and how is it protected. state.json holds the seal, the budget and the spend, so it gets the strongest care. Every change is a read-modify-write under an advisory lock file created with O_EXCL. A lock older than ten seconds is treated as stale and stolen. The write itself is a temp file, fsync, and os.replace, so a reader sees the old or the new file, never half.

events.jsonl is append-only, one write per line, no lock. The evidence ledger uses the same lock plus replace. Rollout files never collide because each name is unique. Two subtle ones: stdout is redirected once around the whole thread pool, because redirect_stdout is process-global and not thread-safe. And the candidate-fault registry has its own threading.Lock. The agent-optimize conductor adds flock, which the OS releases even on SIGKILL.

[16:20–17:10] עכשיו, מה משותף ואיך הוא מוגן. state.json מחזיק את ה-seal, התקציב וההוצאה, ולכן הוא מקבל את ההגנה החזקה ביותר. כל שינוי הוא read-modify-write תחת קובץ נעילה שנוצר עם O_EXCL. נעילה שעברו עליה עשר שניות נחשבת stale ונלקחת. הכתיבה עצמה היא קובץ זמני, fsync ו-os.replace, כך שקורא רואה את הקובץ הישן או החדש, אף פעם לא חצי.

events.jsonl הוא append-only, כתיבה אחת לכל שורה, בלי נעילה. ה-evidence ledger משתמש באותה נעילה ועוד replace. קבצי rollout אף פעם לא מתנגשים כי כל שם ייחודי. ושני מקרים עדינים: stdout מופנה פעם אחת סביב כל ה-thread pool, כי redirect_stdout הוא גלובלי לתהליך ולא thread-safe. ול-registry של candidate faults יש threading.Lock משלו. ה-conductor של agent-optimize מוסיף flock, שמערכת ההפעלה משחררת גם ב-SIGKILL.

[17:10–18:00] Budgets live in state.json. The CLI passes them to baseline, which freezes them. Each iteration, the loop calls budget_exhausted, which checks the reasons in this order and returns the first one. That string becomes stop_reason in the algorithm's JSON.

Two details matter in practice. First, the check runs between iterations. Without budget_reserve, one large evaluation can push you past max_usd. With it, the rollouts are reserved first and a BudgetExhausted stops the loop cleanly with budget_reserved. Second, indecisive steps do not count toward stall, because an infra outage says nothing about the optimizer's ideas.

stop_at_reward still finalizes on test. Convergence is a graded signal, recomputed from the steps each time, so it is resume-safe. lr_schedule is only used by skillopt.

[17:10–18:00] התקציבים נמצאים ב-state.json. ה-CLI מעביר אותם ל-baseline, שמקפיא אותם. בכל איטרציה הלולאה קוראת ל-budget_exhausted, שבודק את הסיבות בסדר הזה ומחזיר את הראשונה. המחרוזת הזו הופכת ל-stop_reason ב-JSON של האלגוריתם.

שני פרטים חשובים בפועל. ראשון, הבדיקה רצה בין איטרציות. בלי budget_reserve, הערכה גדולה אחת יכולה לעבור את max_usd. איתו, ה-rollouts נשמרים מראש, ו-BudgetExhausted עוצר את הלולאה בצורה נקייה עם budget_reserved. שני, צעדים שהם indecisive לא נספרים ל-stall, כי תקלת תשתית לא אומרת כלום על הרעיונות של ה-optimizer.

stop_at_reward עדיין עושה finalize על test. Convergence הוא סיגנל מדורג שמחושב מחדש מה-steps בכל פעם, ולכן הוא בטוח ל-resume. lr_schedule משמש רק את skillopt.

[18:00–19:00] Crash first. Importing cap_evolve turns on faulthandler, so even a segfault in a C extension leaves a traceback. The CLI keeps the head and the tail of stderr and names the signal. test_crash_visibility.py pins this.

Ctrl-C: cap-evolve run installs no SIGINT handler. The terminal sends SIGINT to the whole foreground group, so the CLI, the phase, the optimizer and the agent all get it. A reservation whose pid is dead stops counting, and a stale lock file is stolen after ten seconds.

Then resume. --resume reopens the latest run dir with exist_ok, so state is kept. Baseline sees baseline.json and skips. The algorithm reads the champion's val result back from rollout files and continues at the next candidate id. The half-done iteration is simply redone. If test was already scored, finalize is skipped. Budget flags on the resume command extend the frozen budget.

[18:00–19:00] קודם קריסה. import של cap_evolve מפעיל faulthandler, כך שגם segfault בהרחבת C משאיר traceback. ה-CLI שומר את ההתחלה והסוף של stderr ונותן שם ל-signal. test_crash_visibility.py מקבע את זה.

Ctrl-C: cap-evolve run לא מתקין handler ל-SIGINT. הטרמינל שולח SIGINT לכל קבוצת התהליכים בחזית, כך שה-CLI, ה-phase, ה-optimizer וה-agent כולם מקבלים אותו. reservation שה-pid שלה מת מפסיקה להיספר, וקובץ נעילה ישן נלקח אחרי עשר שניות.

ואז resume. --resume פותח מחדש את ה-run dir האחרון עם exist_ok, כך שה-state נשמר. Baseline רואה את baseline.json ומדלג. האלגוריתם קורא את תוצאת ה-val של ה-champion מתוך קבצי ה-rollout וממשיך מה-id הבא של candidate. האיטרציה שנקטעה פשוט רצה מחדש. אם test כבר נמדד, מדלגים על finalize. דגלי תקציב בפקודת ה-resume מרחיבים את התקציב המוקפא.

Key takeaways

A sequencer of processes

cap-evolve run = check gate + phase scripts, each with one JSON reply.

run_step is the iteration

copy → inject → optimize → checks → evaluate → gate → snapshot → record → commit.

Parallel generation, serial judgment

Threads make rollouts. Scoring, gate and state stay on one thread.

Files are the shared memory

Locked atomic state.json, append-only events.jsonl, so --resume just reads them back.
