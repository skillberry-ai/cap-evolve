The core objects in one picture

Source: core/cap_evolve/types.py · adapter.py · gate.py · rundir.py

[1:20–2:30] This is the whole vocabulary in one picture. Read it from left to right.

The seed capability is your original artifact, for example a system prompt in a folder called seed_capability. cap-evolve never edits it. It makes a copy. A copy that the optimizer has edited is a candidate, with an id like cand_0001.

The adapter is your code. It takes a Task, runs your agent with the candidate live, and returns a Rollout: the output and the trace. Then score() turns the rollout into a Score: a reward between 0 and 1 plus text feedback.

Scores on the val split go to the gate. If the gain is larger than k standard errors, the candidate becomes the new champion. Its id is stored as best_id in state.json, and it becomes the parent of the next candidate.

[1:20–2:30] זה כל אוצר המילים בתמונה אחת. קוראים משמאל לימין.

ה-seed capability הוא הארטיפקט המקורי שלכם, למשל system prompt בתיקייה שנקראת seed_capability. cap-evolve אף פעם לא עורך אותו, הוא עושה עותק. עותק שה-optimizer ערך הוא candidate, עם מזהה כמו cand_0001.

ה-adapter הוא הקוד שלכם. הוא מקבל Task, מריץ את הסוכן כשה-candidate פעיל, ומחזיר Rollout: הפלט וה-trace. אחר כך score() הופך את ה-rollout ל-Score: reward בין 0 ל-1 ועוד feedback בטקסט.

הציונים על ה-val split הולכים ל-gate. אם השיפור גדול מ-k שגיאות תקן, ה-candidate הופך ל-champion החדש. המזהה שלו נשמר כ-best_id בתוך state.json, והוא נהיה ה-parent של ה-candidate הבא.

Capability: what the agent reads

A capability is the artifact under optimization. Each kind is a capability skill in skills/capabilities/.

system-prompt

Prompt, developer message, or policy text.

Add, merge, or change rules. Never drop a needed rule.

tools

The agent's own tool surface: code, docs, return values.

Wrap or replace a tool. Never bare-remove it.

mcp-tool

Tool surface of an external MCP server the agent calls.

Names, descriptions, schemas, tool subset.

skill-package

An Agent Skill: SKILL.md, references, scripts.

So the agent triggers it and follows it.

# combine kinds: one run edits all of them jointly
capabilities: [system-prompt, tools]
capability_path: seed_capability   # the seed dir
Weights never change. cap-evolve edits the files the agent reads.

Source: skills/capabilities/*/SKILL.md · benchmarks/tau2/examples/airline/capevolve.yaml

[2:30–3:40] A capability is the thing we optimize. It is always files that the agent reads at runtime. It is never model weights.

There are four kinds. Each kind is a capability skill: a folder with a SKILL.md that tells the optimizer what it may change and what it must keep.

  • system-prompt: rules and policy text.
  • tools: the agent's own tools. The optimizer may edit tool code, so a rule becomes code the model cannot skip.
  • mcp-tool: the surface of an external MCP server.
  • skill-package: when the thing you ship is itself a skill.

You can combine kinds. The tau2 airline example uses [system-prompt, tools], so one candidate can change the policy and the tools together.

[2:30–3:40] capability הוא הדבר שעושים לו אופטימיזציה. זה תמיד קבצים שהסוכן קורא בזמן ריצה. זה אף פעם לא משקלות של מודל.

יש ארבעה סוגים. כל סוג הוא capability skill: תיקייה עם SKILL.md שמסבירה ל-optimizer מה מותר לשנות ומה חייב להישאר.

  • system-prompt: חוקים וטקסט מדיניות.
  • tools: הכלים של הסוכן עצמו. ה-optimizer יכול לערוך קוד של כלי, וכך חוק הופך לקוד שהמודל לא יכול לדלג עליו.
  • mcp-tool: המשטח של שרת MCP חיצוני.
  • skill-package: כשהדבר שאתם משחררים הוא בעצמו skill.

אפשר לשלב סוגים. הדוגמה של tau2 airline משתמשת ב-[system-prompt, tools], כך ש-candidate אחד יכול לשנות את המדיניות ואת הכלים ביחד.

[3:40–4:50] These four words describe versions of the capability. The picture is a real toy_calc run that I ran for this slide.

The seed is the starting version. Its id is literally the string seed. It scored 0.0 on val. The optimizer made cand_0001, which scored 1.0. The gate accepted it, so it became the champion. The code mostly says "best": best_id, set_best(), cap-evolve diff --best. The docs often say champion. They mean the same thing.

Then cand_0002 and cand_0003 were built on top of the champion. They also scored 1.0, but a delta of zero is not a gain, so both were rejected. Two rejects in a row hit stall: 2, and the run stopped.

Lineage is the parent link of every candidate. In hill-climb the parent is always the current best. Other algorithms branch more. Chapter four shows the candidate graph.

[3:40–4:50] ארבע המילים האלה מתארות גרסאות של ה-capability. התמונה היא ריצה אמיתית של toy_calc שהרצתי בשביל השקף הזה.

ה-seed הוא הגרסה ההתחלתית. המזהה שלו הוא ממש המחרוזת seed. הוא קיבל 0.0 על val. ה-optimizer יצר את cand_0001, שקיבל 1.0. ה-gate קיבל אותו, ולכן הוא נהיה ה-champion. בקוד בדרך כלל כתוב "best": best_id, set_best(), cap-evolve diff --best. בתיעוד הרבה פעמים כתוב champion. זה אותו דבר.

אחר כך נבנו cand_0002 ו-cand_0003 מעל ה-champion. גם הם קיבלו 1.0, אבל delta של אפס הוא לא שיפור, ולכן שניהם נדחו. שתי דחיות ברצף הגיעו ל-stall: 2, והריצה עצרה.

lineage זה הקישור ל-parent של כל candidate. ב-hill-climb ה-parent הוא תמיד ה-best הנוכחי. אלגוריתמים אחרים מתפצלים יותר. בפרק ארבע נראה את ה-candidate graph.

The adapter: your glue code

# .capevolve/project/adapters/adapter.py
class Adapter(CapabilityAdapter):
    # 1. where tasks come from: train | val | test | all
    def tasks(self, split) -> list[Task]: ...

    # 2. run the agent with the candidate live as ctx
    def run_target(self, task, ctx, *, seed=0): ...  # Rollout

    # 3. reward in [0, 1] + feedback, deterministic
    def score(self, task, rollout) -> Score: ...

[4:50–6:00] The adapter is the only code you write to connect cap-evolve to a new agent or benchmark. It lives in .capevolve/project/adapters/adapter.py and subclasses CapabilityAdapter.

Three methods are abstract and required. tasks(split) returns the evaluation data and must return the same list every time. run_target runs the agent under test with the candidate live, and returns a Rollout. It does no scoring. If the agent is random, forward the seed. score returns a reward between zero and one plus feedback. It must be deterministic for a fixed rollout, and the feedback must never leak the gold answer.

On the right are optional hooks with working defaults. Three of them, run_batch, run_trials, and score_batch, are not on the base class at all. The harness checks for them with hasattr. Chapter four goes deep.

[4:50–6:00] ה-adapter הוא הקוד היחיד שכותבים כדי לחבר את cap-evolve לסוכן חדש או ל-benchmark חדש. הוא נמצא ב-.capevolve/project/adapters/adapter.py ויורש מ-CapabilityAdapter.

שלוש מתודות הן abstract וחובה. tasks(split) מחזירה את נתוני ההערכה, וחייבת להחזיר את אותה רשימה בכל פעם. run_target מריצה את הסוכן שנבדק כשה-candidate פעיל, ומחזירה Rollout. היא לא נותנת ציון. אם הסוכן אקראי, מעבירים הלאה את ה-seed. score מחזירה reward בין אפס לאחת ועוד feedback. היא חייבת להיות דטרמיניסטית על rollout קבוע, וה-feedback אסור שידליף את התשובה הנכונה.

בצד ימין יש hooks אופציונליים עם ברירות מחדל שעובדות. שלושה מהם, run_batch, run_trials ו-score_batch, בכלל לא נמצאים ב-base class. ה-harness בודק אותם עם hasattr. בפרק ארבע נצלול לזה.

Source: core/cap_evolve/types.py (dataclasses with to_dict / from_dict)

[6:00–6:50] These three dataclasses in types.py are the shared vocabulary of the pipeline. Every skill script speaks in them, and they round-trip as JSON.

A Task is one unit of evaluation work: an id, an input, an optional target, and metadata. A Rollout is what happened when the agent ran on that task: the output, the trace, tool calls, cost, and tokens. If the infrastructure failed, for example a network error, the adapter sets error. That is not counted as a zero score.

A Score holds the reward, which is clamped to the range zero to one, and the feedback text. The feedback is what the optimizer learns from. Think of it as a textual gradient. A Score can also carry a metrics list, for example cost, but only the primary metric, the reward, ever moves the gate.

[6:00–6:50] שלושת ה-dataclasses האלה ב-types.py הם אוצר המילים המשותף של כל ה-pipeline. כל סקריפט של skill מדבר בהם, והם עוברים הלוך ושוב כ-JSON.

Task הוא יחידת עבודה אחת של הערכה: מזהה, input, target אופציונלי ו-metadata. Rollout הוא מה שקרה כשהסוכן רץ על ה-task: הפלט, ה-trace, קריאות לכלים, עלות וטוקנים. אם התשתית נכשלה, למשל שגיאת רשת, ה-adapter ממלא את error. זה לא נספר כציון אפס.

Score מחזיק את ה-reward, שנחתך לטווח אפס עד אחת, ואת טקסט ה-feedback. ה-feedback הוא מה שה-optimizer לומד ממנו, מעין gradient טקסטואלי. Score יכול גם להחזיק רשימת metrics, למשל עלות, אבל רק ה-primary metric, כלומר ה-reward, משפיע על ה-gate.

Splits: train, val, and the sealed test

Source: core/cap_evolve/splits.py (make_splits) · rundir.py · gate.py · docs/HONEST_EVAL.md

[6:50–7:50] The tasks are split once, with a seed, into three parts. The default ratio is 50, 25, 25. The ids on the slide are the real toy_calc split from splits.json.

  • train is used by algorithms that work on mini-batches, like gepa and skillopt.
  • val is where decisions happen: the baseline score, the diagnosis of failures, and the gate.
  • test is sealed. It is scored exactly once, in the finalize phase.

The seal is enforced in code, not by good manners. consume_test() flips the test_used flag, and a second call raises TestSealError. The gate raises TrainGateError for any split except val. You can also pin an official split with split_ids_file. Chapter six explains why each rule exists.

[6:50–7:50] ה-tasks מחולקים פעם אחת, עם seed, לשלושה חלקים. היחס ברירת המחדל הוא 50, 25, 25. המזהים על השקף הם החלוקה האמיתית של toy_calc מתוך splits.json.

  • train משמש אלגוריתמים שעובדים עם mini-batches, כמו gepa ו-skillopt.
  • val זה המקום שבו מתקבלות החלטות: ציון ה-baseline, ניתוח הכישלונות וה-gate.
  • test הוא sealed, חתום. מקבל ציון פעם אחת בדיוק, בשלב ה-finalize.

החתימה נאכפת בקוד, לא בנימוס. consume_test() מדליקה את הדגל test_used, וקריאה שנייה זורקת TestSealError. ה-gate זורק TrainGateError על כל split שהוא לא val. אפשר גם לנעול חלוקה רשמית עם split_ids_file. בפרק שש נסביר למה כל חוק קיים.

Source: core/cap_evolve/stats.py (pass_k, pass_at_k) · trials.py · rundir.py

[7:50–8:50] LLM agents are random, so one run per task is not enough. A trial is one run of a candidate on one task. The spec key num_trials sets how many. The default is one. The tau2 example uses ten.

Each trial gets its own seed: trial k uses base seed plus k. If all trials used the same seed, you would measure the same draw many times and your error bars would lie.

pass^k comes from tau-bench. It is the chance that k independent trials all succeed. In the example, task a1 passed three of four trials. pass^2 is C(3,2) over C(4,2), which is one half. Note one rule: if k is larger than the number of trials, pass^k is undefined. The code returns None, never zero, because zero would read as "never reliable".

[7:50–8:50] סוכני LLM הם אקראיים, אז ריצה אחת לכל task לא מספיקה. trial הוא ריצה אחת של candidate על task אחד. מפתח ה-spec num_trials קובע כמה. ברירת המחדל היא אחד. בדוגמה של tau2 משתמשים בעשרה.

כל trial מקבל seed משלו: trial מספר k משתמש ב-base seed ועוד k. אם כל ה-trials היו עם אותו seed, הייתם מודדים את אותה הגרלה הרבה פעמים, ופסי השגיאה היו משקרים.

pass^k מגיע מ-tau-bench. זו ההסתברות ש-k trials בלתי תלויים כולם מצליחים. בדוגמה, task a1 עבר שלושה מתוך ארבעה trials. pass^2 הוא C(3,2) חלקי C(4,2), כלומר חצי. חוק אחד חשוב: אם k גדול ממספר ה-trials, pass^k לא מוגדר. הקוד מחזיר None ולא אפס, כי אפס ייקרא כמו "אף פעם לא אמין".

✓ accept

Real gain. set_best(), row in history.jsonl.

✗ reject

No real gain. Row in rejected.jsonl. Stall counter +1.

~ indecisive

Gate could not judge. step_indecisive event. Not a reject, no stall.

agent-optimize books one more outcome, inconclusive, plus a non-booked provisional.

Source: core/cap_evolve/gate.py (GateDecision.accept, .indecisive) · tui.py GLYPHS · skills/algorithms/agent-optimize/scripts/commit.py

[8:50–10:00] An iteration is one turn of the loop and produces exactly one candidate. Diagnose the failing val traces, let the optimizer propose an edit, evaluate it on val, ask the gate, then commit the result to git and update memory. Each iteration writes one step event.

The gate returns a GateDecision with two flags, accept and indecisive. That gives three verdicts.

  • accept: the gain beats k standard errors. The candidate becomes the best.
  • reject: no significant gain. It goes into the rejected memory, and the stall counter goes up.
  • indecisive: the gate declined to judge, for example because too few val tasks produced a valid score. This is not "the edit was bad". It does not count toward stall.

The live view shows these as tick, cross, and tilde. The agent-optimize algorithm uses the word inconclusive for a similar case, and also has provisional. Chapter six covers re-gating.

[8:50–10:00] iteration הוא סיבוב אחד של הלולאה, והוא מייצר candidate אחד בדיוק. מנתחים את ה-traces הכושלים ב-val, נותנים ל-optimizer להציע עריכה, מעריכים אותה על val, שואלים את ה-gate, ואז עושים commit ל-git ומעדכנים זיכרון. כל iteration כותב event אחד מסוג step.

ה-gate מחזיר GateDecision עם שני דגלים, accept ו-indecisive. זה נותן שלוש תוצאות.

  • accept: השיפור עובר k שגיאות תקן. ה-candidate נהיה ה-best.
  • reject: אין שיפור מובהק. הוא נכנס לזיכרון הדחיות, ומונה ה-stall עולה.
  • indecisive: ה-gate סירב לשפוט, למשל כי מעט מדי tasks ב-val נתנו ציון תקין. זה לא אומר שהעריכה גרועה, וזה לא נספר ל-stall.

התצוגה החיה מראה אותם כוי, איקס וטילדה. האלגוריתם agent-optimize משתמש במילה inconclusive למקרה דומה, ויש לו גם provisional. בפרק שש נדבר על re-gate.

[10:00–10:50] A phase is one stage of the pipeline. There are six, always in this order.

intake interviews you, scaffolds .capevolve/project, and wires the adapter. If a needed input is missing, it asks. implement-and-check is the hard gate. cap-evolve check must print ok before any budget is spent, so you never pay for a run against a stub. baseline creates the run dir, freezes the split, and scores the seed on val. algorithm runs the iterations. finalize scores the best candidate on the sealed test, once. report writes report.md and a self-contained dashboard.

[10:50–11:50] Three words that people mix up.

A skill is the packaging unit. It is a folder with a SKILL.md. Phases, capabilities, algorithms, the optimizer runner, interventions, memory, and orchestrate are all skills. The registry manifest lists 22.

An algorithm is a skill whose job is the search strategy. hill-climb is the default: the parent is always the current best. gepa is reflective Pareto search. skillopt runs epochs with a shrinking edit budget. agent-optimize runs only in agent mode. evograph is deprecated and stays only so old specs still resolve.

An optimizer backend is the coding-agent CLI that actually writes the edit, for example claude-code or codex. It is one row of registry.yaml. The mock backend makes no API calls. CI and the toy example use it. These counts are checked by test_advertised_counts.py.

[10:50–11:50] שלוש מילים שאנשים מבלבלים ביניהן.

algorithm הוא skill שהתפקיד שלו הוא אסטרטגיית החיפוש. hill-climb הוא ברירת המחדל: ה-parent הוא תמיד ה-best הנוכחי. gepa הוא חיפוש Pareto רפלקטיבי. skillopt רץ ב-epochs עם תקציב עריכה שהולך וקטן. agent-optimize רץ רק ב-agent mode. evograph הוא deprecated ונשאר רק כדי ש-specs ישנים עדיין יעבדו.

Host and orchestration mode

host = the coding-agent CLI where you load the cap-evolve skills: the Claude Code plugin (/cap-evolve:<skill>) or any host via ./install.sh.

Source: docs/AGENT_ORCHESTRATION.md · RUN.md · install.sh

[11:50–12:50] A host is the coding-agent CLI you talk to, where the cap-evolve skills are installed. With Claude Code you load the plugin, and every skill becomes a /cap-evolve: command plus honesty hooks. Other hosts, like Codex, Gemini CLI, or Cursor, get the skills copied by ./install.sh.

Do not confuse the host with the optimizer backend. The host is the conversation. The backend is the CLI the engine spawns to write each edit. They can be the same product, but they are different processes.

The orchestration mode decides who drives the loop. In deterministic mode, the default, cap-evolve run runs everything and spawns an optimizer subprocess per iteration. In agent mode, run does check and baseline, prints the run dir, and returns. Then the host agent itself drives the rounds. In that mode the agent is the optimizer. The honesty rules live in core, so both modes have the same guarantees.

[11:50–12:50] host הוא ה-CLI של סוכן הקוד שאתם מדברים איתו, שבו מותקנים ה-skills של cap-evolve. ב-Claude Code טוענים את ה-plugin, וכל skill הופך לפקודה /cap-evolve: ועוד hooks של יושר. hosts אחרים, כמו Codex, Gemini CLI או Cursor, מקבלים את ה-skills דרך העתקה עם ./install.sh.

לא לבלבל בין ה-host ל-optimizer backend. ה-host הוא השיחה. ה-backend הוא ה-CLI שהמנוע מפעיל כדי לכתוב כל עריכה. זה יכול להיות אותו מוצר, אבל אלה תהליכים שונים.

ה-orchestration mode קובע מי מניע את הלולאה. במצב deterministic, ברירת המחדל, cap-evolve run מריץ הכל ומפעיל subprocess של optimizer בכל iteration. במצב agent, ה-run עושה check ו-baseline, מדפיס את ה-run dir וחוזר. מכאן סוכן ה-host בעצמו מניע את הסבבים. במצב הזה הסוכן הוא ה-optimizer. חוקי היושר נמצאים ב-core, ולכן לשני המצבים יש אותן הבטחות.

# --- data + splits

Advanced gate keys (gatecfg.py, optimizer_config.py): split_mode, coverage_policy, promotion_rule, optimizer.ablation.*. Chapter 6.

[14:40–15:40] The second half is about measurement and money.

dataset_source is a tasks file, or the word adapter, which means "call tasks()". The split keys we saw before. num_trials sets the trials per task.

The gate block: paired is the recommended mode. It compares candidate and parent on the same val tasks. gate_k_se is the k in delta greater than k times SE. Do not set strict on a random scorer. It means delta greater than zero, and it banks noise.

The budget block: every cap is a hard stop, and zero means off. max_iterations is the main cost knob. stall stops after that many rejects in a row. Run cap-evolve estimate first to see a dollar range.

At the bottom are optional keys. For example, protected_paths hashes files like the scorer, and an edit to them makes the step indecisive, never a zero. The advanced gate keys are read by gatecfg.py and optimizer_config.py. We cover them in chapter six.

[14:40–15:40] החצי השני עוסק במדידה ובכסף.

dataset_source הוא קובץ tasks, או המילה adapter, שמשמעותה "תקרא ל-tasks()". את מפתחות החלוקה כבר ראינו. num_trials קובע כמה trials לכל task.

בלוק ה-gate: paired הוא המצב המומלץ. הוא משווה candidate ו-parent על אותם tasks של val. gate_k_se הוא ה-k בנוסחה delta גדול מ-k כפול SE. לא לשים strict על scorer אקראי. המשמעות שלו היא delta גדול מאפס, וזה פשוט אוסף רעש.

בלוק התקציב: כל תקרה היא עצירה קשיחה, ואפס אומר כבוי. max_iterations הוא כפתור העלות הראשי. stall עוצר אחרי כמה דחיות ברצף. כדאי להריץ קודם cap-evolve estimate כדי לראות טווח בדולרים.

למטה יש מפתחות אופציונליים. למשל protected_paths עושה hash לקבצים כמו ה-scorer, ועריכה שלהם הופכת את ה-step ל-indecisive, אף פעם לא לאפס. מפתחות ה-gate המתקדמים נקראים על ידי gatecfg.py ו-optimizer_config.py. נכסה אותם בפרק שש.

Cross-iteration files: who owns what

FileOwnerKindWhat it holds
LEDGER.mdframeworkfactsEvery iteration's outcome + the exact val tasks it broke or fixed
JOURNAL.mdoptimizerjudgmentAppend-only handover: tried, worked, regressed, refuted, focus next
PROCESS.mdoptimizerexplainabilityHow this iteration was done. Fresh each time, snapshotted with the candidate
RUNMAP.mdframeworkmanifestIndex of prior iterations; their PROCESS.md + diff in prior_iterations/
Rule: facts are deterministic and owned by the framework. Judgment and process belong to the optimizer. The framework stamps a RESULT line under each JOURNAL entry.

Also optimizer-owned: INSIGHTS.md, META_INSIGHTS.md, FRAMEWORK_IMPROVEMENTS.md. Source: core/cap_evolve/harness.py · docs/ARCHITECTURE.md

[17:20–18:10] Each iteration's optimizer starts fresh, with no memory. So cap-evolve puts files in its working dir that carry knowledge across iterations. Ownership is strict, because an older design with a shared memory file confused everyone.

  • LEDGER.md is facts. The framework regenerates it each iteration: outcomes and which tasks each candidate broke or fixed.
  • JOURNAL.md is the optimizer's diary. It appends one entry per iteration and never edits old ones. The optimizer cannot know its own gate result while it writes, so the framework adds a RESULT line below each entry later.
  • PROCESS.md explains how this iteration was done.
  • RUNMAP.md is the framework's index of prior iterations.

You saw them in the work/cand_0001 folder of the toy run. These files are excluded from the content hash, so they never count as a capability edit. The history ablation switch removes them, for experiments.

Objects

Measurement

Decide on val. Test is sealed. Trials use their own seeds. The gate can say "I cannot tell".

Machinery

Phases and algorithms are skills. The optimizer backend writes edits. The mode decides who drives.

One capevolve.yaml. One run dir. LEDGER is facts, JOURNAL is judgment.

[19:10–20:00] Let me sum up in four lines.

  • Objects: a seed becomes candidates, and the gate picks a champion. The adapter connects it all with three methods.
  • Measurement: decisions use val only, the test is opened once, every trial has its own seed, and the gate is allowed to say indecisive.
  • Machinery: everything is a skill. The optimizer backend writes edits. The orchestration mode decides whether core or the agent drives the loop.
  • Config and files: one spec, one run dir, and clear ownership of the shared memory files.
