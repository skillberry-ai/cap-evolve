A library of Agent Skills over a tiny core

Source: docs/ARCHITECTURE.md line 3 · skills/_registry/manifest.json (22 skills)

[1:30–2:40] The first line of docs/ARCHITECTURE.md says it directly: cap-evolve is a library of Agent Skills over a tiny pure-stdlib core. The core is the amber box. It owns the rules that must not be bypassed: the seeded splits, the gate, the sealed test in rundir.py. The core also holds the loop engines, such as harness.py, gepa.py and skillopt.py.

Around it are 22 skills in seven component types. The counts are on the boxes: two orchestrate skills, eight phases, four capabilities, five algorithms, one optimizer runner with a registry, one intervention, and one memory skill. Each skill is a thin script that imports cap_evolve and prints one JSON object. This split is the key design choice. A skill is text plus a script, so an agent can read it and follow it. The honesty rules sit in code that no skill and no prompt can edit.

[1:30–2:40] השורה הראשונה ב-docs/ARCHITECTURE.md אומרת את זה ישירות: cap-evolve הוא ספרייה של Agent Skills מעל core קטן ב-pure stdlib. ה-core הוא הקופסה הכתומה. הוא מחזיק את הכללים שאסור לעקוף: ה-splits עם seed, ה-gate, וה-test החתום ב-rundir.py. ה-core מחזיק גם את מנועי הלולאה, כמו harness.py, gepa.py ו-skillopt.py.

מסביב יש 22 skills בשבעה סוגי component. המספרים כתובים על הקופסאות: שני orchestrate, שמונה phases, ארבעה capabilities, חמישה algorithms, optimizer runner אחד עם registry, intervention אחד ו-memory skill אחד. כל skill הוא script דק שעושה import ל-cap_evolve ומדפיס אובייקט JSON אחד. זו החלטת התכנון המרכזית. skill הוא טקסט ועוד script, אז agent יכול לקרוא אותו ולפעול לפיו. כללי הכנות יושבים בקוד שאף skill ואף prompt לא יכולים לערוך.

[2:40–3:50] Every skill has the same shape. SKILL.md is what a host agent loads. Its frontmatter has name, description, component, needs and provides. The description matters most, because a host shows only the description before it decides to load the skill. meta.yaml is the machine side. Its component: key says which of the seven types this is. It also names the entry, abstract and check scripts and the needs and provides tokens.

In the scripts folder, run.py does the work and prints exactly one JSON object on stdout. For example, the system-prompt run.py builds a Candidate and validates it, then prints the candidate and a valid block. check.py is a smoke test that must fail on stubs. abstract.py holds the methods, such as materialize and validate. _bootstrap.py only puts core on sys.path, so the script runs standalone.

[2:40–3:50] לכל skill יש אותו מבנה. SKILL.md הוא מה שה-host agent טוען. ב-frontmatter יש name, description, component, needs ו-provides. ה-description הכי חשוב, כי host מציג רק אותו לפני שהוא מחליט לטעון את ה-skill. meta.yaml הוא הצד של המכונה. המפתח component: אומר לאיזה מתוך שבעת הסוגים ה-skill שייך. הוא גם נותן את שמות ה-scripts של entry, abstract ו-check, ואת ה-tokens של needs ו-provides.

בתיקיית scripts, run.py עושה את העבודה ומדפיס בדיוק אובייקט JSON אחד ל-stdout. למשל, ה-run.py של system-prompt בונה Candidate, בודק אותו, ומדפיס את ה-candidate ובלוק valid. check.py הוא smoke test שחייב להיכשל על stubs. abstract.py מחזיק את המתודות, כמו materialize ו-validate. ‏_bootstrap.py רק מוסיף את ה-core ל-sys.path, כדי שה-script ירוץ לבד.

[3:50–4:50] How do 22 skills become one pipeline? Each meta.yaml declares tokens. A token is a name for a kind of data. build_manifest.py walks all meta.yaml files and writes skills/_registry/manifest.json. The manifest has two keys: skills and errors. The orchestrate skill and cli.py read it. cli.py uses it to find each skill's entry script, in the function _resolve_skills.

The table shows the real tokens. For example, evaluate provides scores and traces. diagnose needs both and provides reflective_dataset. Only gepa declares reflective_dataset as a need. The other algorithms read traces directly. The compatible_with lists use a star, which means any. That star is what gives you any capability with any algorithm with any optimizer. You can add a new token. Just make sure some skill provides it before another skill needs it, or the orchestrator flags an unmet need.

[3:50–4:50] איך 22 skills הופכים ל-pipeline אחד? כל meta.yaml מצהיר על tokens. token הוא שם לסוג של מידע. ‏build_manifest.py עובר על כל קבצי meta.yaml וכותב את skills/_registry/manifest.json. ל-manifest יש שני מפתחות: skills ו-errors. ה-orchestrate skill ו-cli.py קוראים אותו. ‏cli.py משתמש בו כדי למצוא את ה-entry script של כל skill, בפונקציה _resolve_skills.

הטבלה מראה את ה-tokens האמיתיים. למשל, evaluate נותן scores ו-traces. ‏diagnose צריך את שניהם ונותן reflective_dataset. רק gepa מצהיר על reflective_dataset כצורך. שאר האלגוריתמים קוראים traces ישירות. ברשימות compatible_with יש כוכבית, שפירושה הכול. הכוכבית הזו נותנת כל capability עם כל algorithm עם כל optimizer. אפשר להוסיף token חדש. רק צריך לוודא שיש skill שנותן אותו לפני ש-skill אחר צריך אותו, אחרת ה-orchestrator יסמן תלות חסרה.

Source: skills/phases/*/meta.yaml · skills/orchestrate/{orchestrate,using-cap-evolve}/SKILL.md

[4:50–5:50] A phase is one step of the pipeline, packed as a skill. Six phases form the outer chain you see here. intake collects inputs and must ask the user for any missing needed input. It never invents one. implement-and-check is the hard gate: cap-evolve check must print ok before any money is spent. baseline freezes the splits and scores the seed. Then the algorithm runs. finalize touches test once. report writes the result.

Three phases are used inside the loop: evaluate, diagnose and gate. In agent mode the agent calls their run.py scripts directly. The two orchestrate skills sit on top. using-cap-evolve is the router. It does not run anything. It reads the on-disk state and says what comes next: intake, check, a resume, or a reuse of a sealed baseline. orchestrate is the driver that sequences the phases. One small note: orchestrate's SKILL.md still says the default algorithm is "all-at-once". That is the old name. cli.py maps it to hill-climb with focus all.

[4:50–5:50] phase הוא שלב אחד ב-pipeline, ארוז כ-skill. שישה phases בונים את השרשרת החיצונית שרואים כאן. ‏intake אוסף קלטים, וחייב לשאול את המשתמש על כל קלט נדרש שחסר. הוא אף פעם לא ממציא קלט. ‏implement-and-check הוא ה-hard gate: ‏cap-evolve check חייב להחזיר ok לפני שמוציאים כסף. ‏baseline מקפיא את ה-splits ומודד את ה-seed. אחר כך רץ ה-algorithm. ‏finalize נוגע ב-test פעם אחת. ‏report כותב את התוצאה.

שלושה phases משמשים בתוך הלולאה: evaluate, diagnose ו-gate. ב-agent mode ה-agent קורא ישירות ל-run.py שלהם. שני ה-orchestrate skills יושבים למעלה. ‏using-cap-evolve הוא ה-router. הוא לא מריץ כלום. הוא קורא את המצב בדיסק ואומר מה הצעד הבא: intake, check, resume, או שימוש חוזר ב-baseline חתום. ‏orchestrate הוא ה-driver שמריץ את ה-phases לפי הסדר. הערה קטנה: ב-SKILL.md של orchestrate עדיין כתוב שה-algorithm ברירת המחדל הוא "all-at-once". זה השם הישן. ‏cli.py ממפה אותו ל-hill-climb עם focus all.

Source: skills/capabilities/*/SKILL.md · docs/ARCHITECTURE.md "What the optimizer receives"

[5:50–7:00] A capability, from chapter 2, is the part of the agent we optimize. Each of the four capability skills is a menu of allowed edits for one kind of artifact. system-prompt covers prompt and policy text. Its levers are edit classes, such as "add the reason to a bare rule". tools covers tools the agent owns, so the optimizer may change the code itself. mcp-tool is for an MCP server that someone else owns. Only presentation edits are allowed there. skill-package covers a whole Agent Skill. Its top lever is the description, because that is the only text a host loads before the skill fires.

How does the optimizer see this menu? The harness copies the chosen capability skill into the workdir as guidance, and also into the agent's native skills folder, for example .claude/skills for Claude Code. So a headless agent loads it without any flag. A spec can list two capabilities, such as system-prompt and tools together.

[5:50–7:00] capability, מפרק 2, הוא החלק של ה-agent שאנחנו מייעלים. כל אחד מארבעת ה-capability skills הוא תפריט של עריכות מותרות לסוג אחד של artifact. ‏system-prompt מכסה טקסט של prompt ו-policy. ה-levers שלו הם סוגי עריכה, כמו "הוסף את הסיבה לכלל חשוף". ‏tools מכסה tools שה-agent עצמו מחזיק, כך שה-optimizer מותר לשנות את הקוד. ‏mcp-tool מיועד ל-MCP server שמישהו אחר מחזיק, ושם מותרות רק עריכות של הצגה. ‏skill-package מכסה Agent Skill שלם. ה-lever הכי חזק שלו הוא ה-description, כי זה הטקסט היחיד ש-host טוען לפני שה-skill מופעל.

איך ה-optimizer רואה את התפריט? ה-harness מעתיק את ה-capability skill שנבחר ל-workdir כ-guidance, וגם לתיקיית ה-skills הטבעית של ה-agent, למשל .claude/skills עבור Claude Code. כך headless agent טוען אותו בלי שום flag. ‏spec יכול לציין שני capabilities, למשל system-prompt ו-tools ביחד.

[7:00–8:00] Each capability also states hard edit boundaries. The mcp-tool table is the clearest example. The server owns the wire inputSchema and the handler. A candidate that edits them is invalid against the real server. It fails at tools/call, and the run still pays the full rollout cost to learn that.

system-prompt has the rule "never drop a needed rule". Consolidation cuts words, never rules. This rule is also checked by code: apply() counts lines that carry constraints before and after each edit and reports a net loss as a warning. A warning is not a failure. It asks the optimizer to state in PROCESS.md where each dropped constraint went. tools has "never bare-remove a tool": first add the safer replacement, then verify it, then swap. Bare removal strands every task that needed the tool. skill-package asks for a self-check entry on each bundled script.

[7:00–8:00] כל capability גם מגדיר גבולות עריכה קשיחים. הטבלה של mcp-tool היא הדוגמה הכי ברורה. ה-server מחזיק את ה-inputSchema וה-handler. ‏candidate שעורך אותם לא תקף מול ה-server האמיתי. הוא נכשל ב-tools/call, וה-run עדיין משלם את כל עלות ה-rollouts כדי לגלות את זה.

ב-system-prompt יש את הכלל "לעולם לא מוחקים כלל נחוץ". איחוד מקצץ מילים, לא כללים. הכלל הזה גם נבדק בקוד: ‏apply() סופר שורות שנושאות אילוצים לפני ואחרי כל עריכה, ומדווח ירידה נטו כ-warning. ‏warning הוא לא כישלון. הוא מבקש מה-optimizer לכתוב ב-PROCESS.md לאן עבר כל אילוץ שנמחק. ב-tools יש "לעולם לא מסירים tool בלי תחליף": קודם מוסיפים את התחליף הבטוח, בודקים אותו, ורק אז מחליפים. הסרה חשופה משאירה בלי פתרון כל task שהיה צריך את ה-tool. ‏skill-package דורש self-check לכל script שמצורף.

[8:00–9:10] hill-climb is the default algorithm. Its run.py is a thin wrapper over harness.hill_climb_loop. One iteration is harness.run_step, which chapter 5 walked through. The parent is always the current best. Why? Every accepted candidate already passed the gate, so the best is the only candidate with evidence behind it. The cost: a specialist that trades one task class for another can never be kept. If you want that, use gepa.

The --focus flag changes only which failing val tasks the prompt emphasizes. Protection of passing tasks always covers the whole val split. The old skill names all-at-once, cyclic and hardest-first are aliases in cli.py. HC-2 is an opt-in extension in hc2.py. It makes K proposals per round, each from a different failure cluster, with a diversity check against recently rejected diffs. It uses the same P2 evaluator as the agent-optimize conductor.

[8:00–9:10] ‏hill-climb הוא האלגוריתם ברירת המחדל. ה-run.py שלו הוא עטיפה דקה מעל harness.hill_climb_loop. איטרציה אחת היא harness.run_step, שעברנו עליו בפרק 5. ה-parent הוא תמיד ה-best הנוכחי. למה? כל candidate שהתקבל כבר עבר את ה-gate, אז ה-best הוא היחיד שיש מאחוריו ראיות. המחיר: ‏specialist שמחליף סוג אחד של tasks בסוג אחר לא יכול להישמר. אם רוצים את זה, משתמשים ב-gepa.

ה-flag ‏--focus משנה רק אילו val tasks שנכשלו ה-prompt מדגיש. ההגנה על tasks שעוברים תמיד מכסה את כל ה-val split. השמות הישנים all-at-once, cyclic ו-hardest-first הם aliases ב-cli.py. ‏HC-2 היא הרחבה שמפעילים ידנית, ב-hc2.py. היא מייצרת K הצעות בכל סבב, כל אחת מ-failure cluster אחר, עם בדיקת גיוון מול diffs שנדחו לאחרונה. היא משתמשת באותו P2 evaluator שה-conductor של agent-optimize משתמש בו.

gepa: minibatch gate, then the full-val gate

Source: core/cap_evolve/gepa.py gepa_loop · selection.py · budget: --max-metric-calls

[9:10–10:30] gepa implements the GEPA paper, arXiv 2507.19457, in core/cap_evolve/gepa.py. It reuses the core's honest pieces, such as evaluate_candidate and gate.decide, and adds two mechanisms. First, the parent comes from a per-instance Pareto frontier. Each candidate is scored per val task. Any candidate that wins at least one task stays a possible parent, and the pick is weighted by how many tasks it wins. So a specialist that solved one hard task is not lost because its mean is lower.

Second, a cheap filter sits before the expensive gate. The parent and the child run on the same small train minibatch, four tasks by default. The child must have a larger sum. Only then does gepa pay for a full val evaluation and the real paired gate. The minibatch never accepts anything. It can only reject. Budget is counted in metric calls. Merges are optional: two frontier candidates with a common ancestor are combined file by file, then gated like any child.

[9:10–10:30] ‏gepa מממש את מאמר GEPA, ‏arXiv 2507.19457, בקובץ core/cap_evolve/gepa.py. הוא משתמש שוב בחלקים הכנים של ה-core, כמו evaluate_candidate ו-gate.decide, ומוסיף שני מנגנונים. ראשון, ה-parent נבחר מתוך Pareto frontier לפי instance. כל candidate מקבל ציון לכל val task. כל candidate שמנצח לפחות task אחד נשאר parent אפשרי, והבחירה משוקללת לפי כמה tasks הוא מנצח. כך specialist שפתר task קשה אחד לא הולך לאיבוד רק כי הממוצע שלו נמוך יותר.

שני, יש מסנן זול לפני ה-gate היקר. ה-parent וה-child רצים על אותו minibatch קטן של train, ארבעה tasks כברירת מחדל. ל-child צריך להיות סכום גבוה יותר. רק אז gepa משלם על הערכה מלאה של val ועל ה-paired gate האמיתי. ה-minibatch אף פעם לא מקבל candidate. הוא רק יכול לדחות. התקציב נספר ב-metric calls. ‏merges הם אופציונליים: שני candidates מה-frontier עם אב משותף מתאחדים קובץ אחרי קובץ, ואז עוברים gate כמו כל child.

skillopt: epochs and a textual learning rate

  • Single lineage: parent is the current best, like hill-climb
  • --epochs 4 × mini-batches of train; seeded shuffle per epoch
  • L is told in words only: "make at most L bounded edits"
  • Per-epoch rejected-edit buffer, reset and bounded each epoch
  • Epoch boundary (epoch ≥ 2): one extra "slow update" step, gated on val like any step
Known gap #371: the train minibatch ids filter val rows, so the focus block is empty.

Source: core/cap_evolve/{skillopt.py skillopt_loop, lr_schedule.py} · skills/algorithms/skillopt/SKILL.md "Known gaps"

[10:30–11:30] skillopt follows the SkillOpt paper. It keeps a strict single lineage like hill-climb, but organizes steps into epochs over mini-batches of train tasks. The new idea is a textual learning rate. That is an integer edit budget per step, made by lr_schedule.build_schedule with a constant, linear or cosine shape. The chart shows the real default: cosine from 4 down to 2 over ten steps. The budget reaches the optimizer only as a sentence. Nothing clips it mechanically.

Each epoch keeps a small buffer of rejected edits, so the next prompt says what to avoid. At each epoch boundary there is one extra consolidation step: fix the regressions without breaking stable successes. That step is gated on val too, never forced. Be aware: the SKILL.md has an honest "Known gaps" section. For example, issue 371: the minibatch ids come from train but filter val rows, so the per-step focus is empty today.

[10:30–11:30] ‏skillopt מבוסס על מאמר SkillOpt. הוא שומר על שושלת אחת קפדנית כמו hill-climb, אבל מארגן את הצעדים ב-epochs מעל mini-batches של train tasks. הרעיון החדש הוא textual learning rate. זה תקציב עריכות שלם לכל צעד, שנבנה על ידי lr_schedule.build_schedule בצורה constant, ‏linear או cosine. הגרף מראה את ברירת המחדל האמיתית: ‏cosine מ-4 עד 2 לאורך עשרה צעדים. התקציב מגיע ל-optimizer רק כמשפט. שום דבר לא חותך אותו מכנית.

כל epoch שומר buffer קטן של עריכות שנדחו, כך שה-prompt הבא אומר ממה להימנע. בכל גבול epoch יש צעד איחוד נוסף אחד: לתקן את ה-regressions בלי לשבור הצלחות יציבות. גם הצעד הזה עובר gate על val, אף פעם לא מתקבל בכוח. שימו לב: ב-SKILL.md יש סעיף "Known gaps" כן. למשל, issue 371: ה-ids של ה-minibatch באים מ-train אבל מסננים שורות של val, אז ה-focus בכל צעד ריק היום.

[11:30–12:50] agent-optimize runs only in agent orchestration mode. There is no optimizer subprocess. The conversational agent itself writes the edits. The scripts decide the numbers, and the agent judges. The loop is six verbs in act.py plus digest.py. Each round starts with diagnose, then the digest: one screen with budget, noise, clusters, and branch posteriors. propose copies the parent into work/TAG. On the second call it checks the hypothesis and runs a free pregate. probe evaluates only the cells the ledger lacks. promote needs full val coverage. prune records a reason.

Three rules matter. A hypothesis must cover at least two tasks or 0.06 of headroom, because a one-task edit is below the noise. Siblings are parallel candidates in separate work copies. round.py also adds a null control, a byte-identical copy, so each round measures its own noise floor. And commit.py refuses a commit without a DIAGNOSIS.json and a ranked issue list, unless you pass a written justification.

[11:30–12:50] ‏agent-optimize רץ רק ב-agent orchestration mode. אין optimizer subprocess. ה-agent השיחתי עצמו כותב את העריכות. ה-scripts מחליטים על המספרים, וה-agent שופט. הלולאה היא שישה פעלים ב-act.py ועוד digest.py. כל סבב מתחיל ב-diagnose, ואחר כך ה-digest: מסך אחד עם תקציב, רעש, clusters ו-posteriors של הענפים. ‏propose מעתיק את ה-parent ל-work/TAG. בקריאה השנייה הוא בודק את ה-hypothesis ומריץ pregate שלא עולה כלום. ‏probe מעריך רק את התאים שחסרים ב-ledger. ‏promote דורש כיסוי מלא של val. ‏prune רושם סיבה.

שלושה כללים חשובים. ‏hypothesis חייב לכסות לפחות שני tasks או 0.06 של headroom, כי עריכה ל-task אחד נמצאת מתחת לרעש. ‏siblings הם candidates מקבילים בעותקי work נפרדים. ‏round.py גם מוסיף null control, עותק זהה בבייטים, כך שכל סבב מודד את רצפת הרעש שלו. ו-commit.py מסרב ל-commit בלי DIAGNOSIS.json ובלי ranked issue list, אלא אם מעבירים הצדקה כתובה.

Agent orchestration mode in depth

Source: docs/AGENT_ORCHESTRATION.md · cli.py (agent branch) · plugins/cap-evolve/hooks/{require_green_check,goal_reminder}.py

[16:10–17:30] Orchestration mode is one spec key. Deterministic is the default: cap-evolve run sequences the whole loop and spawns an optimizer subprocess per iteration. With orchestration_mode: agent, cap-evolve run does check and baseline, prints a handoff JSON, and returns. There is no algorithm subprocess and no automatic finalize. Then the same conversational agent that ran intake drives the loop. It is not a new agent. In agent mode the agent is the optimizer. It calls evaluate, gate and diagnose scripts each round, and seals by running the finalize phase script. The user can steer or stop at any round.

What keeps it honest? First, the core guards: evaluate accepts only train or val, and a second finalize raises TestSealError. Second, hooks: the Stop hook nudges the agent until the run is finalized, and goal_reminder re-shows the stop_condition predicates every twelve Bash calls. For CI there are two unattended paths: --agent-driver runs host.py, which guarantees a seal, and ao_engine: conductor lets code run the loop.

[16:10–17:30] ‏orchestration mode הוא מפתח אחד ב-spec. ‏deterministic הוא ברירת המחדל: ‏cap-evolve run מריץ את כל הלולאה ומפעיל optimizer subprocess לכל איטרציה. עם orchestration_mode: agent, ‏cap-evolve run עושה check ו-baseline, מדפיס handoff JSON, וחוזר. אין algorithm subprocess ואין finalize אוטומטי. אחר כך אותו agent שיחתי שהריץ את intake מוביל את הלולאה. זה לא agent חדש. ב-agent mode ה-agent הוא ה-optimizer. בכל סבב הוא קורא ל-scripts של evaluate, ‏gate ו-diagnose, וחותם על ידי הרצת ה-finalize phase script. המשתמש יכול לכוון או לעצור בכל סבב.

מה שומר על זה כן? קודם, ה-guards של ה-core: ‏evaluate מקבל רק train או val, ו-finalize שני זורק TestSealError. שנית, hooks: ה-Stop hook דוחף את ה-agent להמשיך עד שה-run עובר finalize, ו-goal_reminder מציג שוב את ה-predicates של stop_condition כל שתים עשרה קריאות Bash. ל-CI יש שתי דרכים בלי אדם: ‏--agent-driver מריץ את host.py, שמבטיח seal, ו-ao_engine: conductor נותן לקוד להריץ את הלולאה.
