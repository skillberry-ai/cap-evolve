Honest evaluation and the gate

How cap-evolve makes its numbers mean something: frozen splits, measured variance, a paired significance gate, and a test split that is scored exactly once.

20 minutesLevel: deepmath explained simply

[0:00–0:45] Welcome to chapter 6. In chapter 5 we followed one iteration of a run. One step in that iteration was the gate. Today we open the gate and everything around it.

This is the part of cap-evolve that makes it different. Many tools can edit a prompt and re-score it. Few tools can tell you if the new score is real. Our rule is simple: an accepted edit must be better by more than the noise of the measurement, and the number we report must come from data the optimizer never touched.

There is some math in this chapter. All of it is mean, standard error, and counting. I will show a small worked example with six tasks, so you can do it on paper.

Why honesty is a design goal

📈

Overfitting to val

Every accept uses val as a signal. After many rounds, val is selected against and reads too high.

🎲

Cherry-picking

Screen 20 candidates. The best one is often best by luck (the "winner's curse").

🔑

Leaking gold

An LLM optimizer can edit the scorer, the answer key, or the test ids instead of the capability.

Search is a noise amplifier. A rule of Δ > 0 banks noise as progress: the val curve climbs while nothing improved. So the rules live in code (core/cap_evolve), not in skill text.

Source: docs/HONEST_EVAL.md, core/cap_evolve/gate.py (module docstring)

[1:30–2:45] Why do we spend so much code on honesty? Because an optimizer is a machine that finds whatever the metric rewards. Three failures show up again and again.

  • Overfitting to val. Every accept decision reads val. After ten rounds, the champion was chosen because it scored high on val, so its val number is optimistic.
  • Cherry-picking. If you try twenty candidates that are all truly equal, one of them still looks best. A "greater than zero" rule would accept it.
  • Leaking gold. The optimizer is an LLM agent with file access. It can edit the gold answers or the scorer. That is reward hacking.

The design answer: the only places that split tasks, aggregate rewards, apply the gate, and seal test are in the core package. Algorithm skills call these functions. They cannot gate on train or re-score test, because the core raises an error.

[1:30–2:45] למה אנחנו משקיעים כל כך הרבה קוד ביושר? כי optimizer הוא מכונה שמוצאת כל מה שהמטריקה מתגמלת. שלוש תקלות חוזרות שוב ושוב.

  • Overfitting ל-val. כל החלטת accept קוראת את val. אחרי עשרה סבבים, ה-champion נבחר כי הוא קיבל ציון גבוה על val, ולכן המספר שלו על val אופטימי מדי.
  • Cherry-picking. אם מנסים עשרים candidates שכולם שווים באמת, אחד מהם עדיין ייראה הכי טוב. כלל של "גדול מאפס" יקבל אותו.
  • דליפת gold. ה-optimizer הוא סוכן LLM עם גישה לקבצים. הוא יכול לערוך את התשובות הנכונות או את ה-scorer. זה reward hacking.

התשובה בעיצוב: המקומות היחידים שמחלקים משימות, מאגדים rewards, מפעילים את ה-gate וחותמים את test נמצאים בחבילת ה-core. ה-skills של האלגוריתמים קוראים לפונקציות האלה. הם לא יכולים לעשות gate על train או למדוד את test שוב, כי ה-core זורק שגיאה.

Three splits, three jobs, one seal

Source: docs/HONEST_EVAL.md "The four guarantees" · core/cap_evolve/splits.py, gate.py, rundir.py

[2:45–3:40] This is the whole chapter in one picture. HONEST_EVAL.md lists four guarantees. One: splits are seeded and frozen. make_splits partitions the task ids once and the result goes to splits.json in the run dir. Two: the test split is sealed. Only finalize scores it, once. Three: acceptance is gated on val, with significance. gate.decide refuses any other split and raises TrainGateError if you pass train. Four: variance is measured, not assumed, through trials and the functions in stats.py.

Each split has one job. Train feeds the optimizer: it reads the train trajectories to find failures. Val feeds the gate. Test feeds the one number we report, in final.json. The default ratios in the scaffold spec are 0.5, 0.25 and 0.25.

[2:45–3:40] זה כל הפרק בתמונה אחת. HONEST_EVAL.md מונה ארבע הבטחות. אחת: ה-splits נוצרים עם seed ומוקפאים. make_splits מחלק את ה-task ids פעם אחת, והתוצאה נכתבת ל-splits.json בתיקיית הריצה. שתיים: ה-test split חתום. רק finalize מודד אותו, פעם אחת. שלוש: ההחלטה מתקבלת על val, עם מובהקות. gate.decide מסרב לכל split אחר וזורק TrainGateError אם מעבירים train. ארבע: השונות נמדדת ולא מונחת, דרך trials והפונקציות ב-stats.py.

לכל split יש תפקיד אחד. train מזין את ה-optimizer, שקורא את ה-trajectories של train כדי למצוא כשלונות. val מזין את ה-gate. test מזין את המספר האחד שמדווחים, ב-final.json. יחסי ברירת המחדל ב-spec של ה-scaffold הם 0.5, 0.25 ו-0.25.

[3:40–4:50] How is a split made? make_splits takes the task ids, removes duplicates, shuffles them with random.Random of the seed, and cuts by ratio. You can also pass absolute counts. The same ids and the same seed always give the same split. That makes a run reproducible.

The key line is in harness.ensure_splits: if splits.json already exists, read it and return. So the split is written once, at intake or baseline time, and every later skill reads it back. No skill re-splits.

A user can also provide the split. The spec key split_ids_file points to a JSON file with train, val and test lists. Use it to lock a benchmark's official split. You can even set train equal to val equal to test for a deliberate fit with no holdout. Then the harness logs a splits_warning event. test_splits_input.py pins both cases, including that a second call does not re-split.

[3:40–4:50] איך נוצר split? make_splits מקבל את ה-task ids, מסיר כפילויות, מערבב אותם עם random.Random של ה-seed, וחותך לפי היחסים. אפשר גם להעביר counts מוחלטים. אותם ids ואותו seed נותנים תמיד אותו split, ולכן הריצה ניתנת לשחזור.

השורה החשובה נמצאת ב-harness.ensure_splits: אם splits.json כבר קיים, קוראים אותו ומחזירים. כך ה-split נכתב פעם אחת, בזמן intake או baseline, וכל skill אחר רק קורא אותו. אף skill לא מחלק מחדש.

המשתמש יכול גם לספק split בעצמו. המפתח split_ids_file ב-spec מצביע על קובץ JSON עם רשימות train, val ו-test. משתמשים בזה כדי לנעול split רשמי של benchmark. אפשר אפילו לשים train שווה ל-val שווה ל-test, כ-fit מכוון בלי holdout, ואז ה-harness רושם אירוע splits_warning. test_splits_input.py בודק את שני המקרים, כולל שקריאה שנייה לא מחלקת מחדש.

[4:50–5:40] This table is worth remembering. Train is the optimizer's data. It sees the train trajectories and can learn anything from them. Val is the gate's data. It decides accept or reject but it is never the number we publish, because it has been selected against. Test is finalize's data. It produces the headline number and nothing else: it never chooses a candidate, tunes a threshold, or decides to stop.

There is an opt-in fourth design, split_mode pooled. Train and val are pooled, then split once into a feedback stratum F and a hidden confirm stratum C, by default 48 percent. The split is stratified by the seed's pass rate so both parts have the same difficulty mix. The C ids are written to a sealed directory next to the project, outside every tree a proposer can read. test_sealed_confirm_data.py walks those trees and checks that no C id appears in any file name or content.

[4:50–5:40] כדאי לזכור את הטבלה הזו. train הוא הנתונים של ה-optimizer. הוא רואה את ה-trajectories של train ויכול ללמוד מהם הכול. val הוא הנתונים של ה-gate. הוא מחליט accept או reject, אבל הוא אף פעם לא המספר שמפרסמים, כי בחרו לפיו. test הוא הנתונים של finalize. הוא מייצר את המספר הראשי ותו לא: הוא לא בוחר candidate, לא מכוונן סף ולא מחליט מתי לעצור.

יש עיצוב רביעי, אופציונלי: split_mode pooled. מאחדים את train ו-val, ואז מחלקים פעם אחת ל-feedback stratum בשם F ול-confirm stratum נסתר בשם C, כברירת מחדל 48 אחוז. החלוקה מרובדת לפי pass rate של ה-seed, כדי ששני החלקים יהיו באותו קושי. ה-ids של C נכתבים לתיקייה חתומה ליד הפרויקט, מחוץ לכל עץ שה-proposer יכול לקרוא. test_sealed_confirm_data.py סורק את העצים האלה ובודק ששום id של C לא מופיע בשם קובץ או בתוכן.

Trials: one task, several independent draws

seed(trial k) = base_seed + k
  • base_seed defaults to the frozen split seed
  • The adapter must forward seed to every random part
  • num_trials: 1 is the scaffold default
  • At 1 trial, per-task SE is 0, so the gate's SE can collapse
SE = 0 → gate_warning event, then a declared STRICT fallback. Never a silent one.

Source: core/cap_evolve/trials.py · harness._run_and_score · gate._warn_se_zero · test_trials.py

[5:40–6:40] A trial is one rollout of one task. With num_trials above one, each task runs several times. The seed contract is simple: trial k runs with seed equal to base_seed plus k. base_seed defaults to the split seed. So two trials are independent draws, and a rerun of the same run gets the same seeds.

The adapter is responsible for passing the seed to the agent, the user simulator, any sampler. If it ignores the seed, all trials look the same and the variance is fake.

The helper trials.run_trials_pool runs the whole task-by-trial grid in a thread pool. Each cell becomes a rollout file named task, tag, and trial index.

Look at the right column. With one trial, every per-task stderr is zero. If all SEs are zero, the gate cannot tell noise from signal. The code does not hide this. It logs a gate_warning event and falls back to strict mode, accept if delta is above zero, in the open.

[5:40–6:40] trial הוא rollout אחד של משימה אחת. כש-num_trials גדול מאחד, כל משימה רצה כמה פעמים. חוזה ה-seed פשוט: trial מספר k רץ עם seed ששווה base_seed ועוד k. base_seed הוא כברירת מחדל ה-seed של ה-split. כך שני trials הם דגימות בלתי תלויות, וריצה חוזרת מקבלת אותם seeds.

ה-adapter אחראי להעביר את ה-seed לסוכן, ל-user simulator ולכל רכיב אקראי. אם הוא מתעלם מה-seed, כל ה-trials נראים אותו דבר והשונות מזויפת.

הפונקציה trials.run_trials_pool מריצה את כל הרשת של משימות כפול trials ב-thread pool. כל תא הופך לקובץ rollout עם שם המשימה, ה-tag ומספר ה-trial.

שימו לב לעמודה הימנית. עם trial אחד, ה-stderr של כל משימה הוא אפס. אם כל ה-SE הם אפס, ה-gate לא יכול להבדיל בין רעש לאות. הקוד לא מסתיר את זה: הוא רושם אירוע gate_warning ועובר ל-strict mode, כלומר accept אם הדלתא מעל אפס, בגלוי.

pass^k and pass@k: reliability vs capability

pass^kreliability
Chance that all k trials pass. C(c,k) / C(n,k)
pass@kcapability
Chance that at least one of k passes. 1 − C(n−c,k) / C(n,k)

n = trials, c = passing trials (reward ≥ 1.0)

t2 = [1, 0, 1, 1] → n=4, c=3
pass^2 = C(3,2)/C(4,2) = 3/6 = 0.50
pass@2 = 1 − C(1,2)/C(4,2) = 1.00

k > n is undefined, not zero

  • stats.pass_k(rewards, 5) → None
  • aggregate_scores omits any k above the minimum trial count
  • num_trials: 1 emits only {"1": ...}
  • Reports and dashboard list only the measured ks
Why: pass^2 = 0.0 on a 1-trial run reads as "0% reliable". The truth is "not enough trials" (issue #112).

test_pass_k_undefined.py · test_report_pass_k_render.py

Source: core/cap_evolve/stats.py pass_k, pass_at_k · loop.aggregate_scores

[6:40–7:50] Two statistics come from trials. pass^k, from tau-bench, is reliability: the chance that all k independent tries pass. pass@k is capability: the chance that at least one of k tries passes. A customer-service agent needs pass^k. A code generator with a test runner may only need pass@k.

Both use counting. With c passes out of n trials, pass^k is "choose k from c" over "choose k from n". That is the unbiased estimate without replacement. For task t2 with three passes out of four, pass^2 is 3 over 6, so 0.5. pass@2 is 1.0, because any two trials include at least one pass.

The important rule is on the right. If k is larger than the number of trials, the statistic is undefined. stats.pass_k returns None, and aggregate_scores leaves the key out. Before issue 112, a one-trial run reported pass^2 as zero. That is a false claim. test_pass_k_undefined.py now pins it, including the edge k equal to n plus one.

[6:40–7:50] שני מדדים נגזרים מה-trials. pass^k, מ-tau-bench, הוא אמינות: הסיכוי שכל k הניסיונות הבלתי תלויים יצליחו. pass@k הוא יכולת: הסיכוי שלפחות אחד מ-k יצליח. סוכן שירות לקוחות צריך pass^k. מחולל קוד עם test runner אולי צריך רק pass@k.

שניהם ספירה. עם c הצלחות מתוך n trials, pass^k הוא "בחירת k מתוך c" חלקי "בחירת k מתוך n". זה האומד הלא מוטה בלי החזרה. במשימה t2, עם שלוש הצלחות מתוך ארבע, pass^2 הוא 3 חלקי 6, כלומר 0.5. pass@2 הוא 1.0, כי כל שני trials כוללים לפחות הצלחה אחת.

הכלל החשוב מימין. אם k גדול ממספר ה-trials, המדד לא מוגדר. stats.pass_k מחזיר None, ו-aggregate_scores משמיט את המפתח. לפני issue 112, ריצה עם trial אחד דיווחה pass^2 שווה אפס. זו טענה שקרית. test_pass_k_undefined.py נועל את זה עכשיו, כולל המקרה ש-k שווה n ועוד אחד.

Standard error: how sure is the mean?

stats.stderr(xs)per task, over trials
sample SD ÷ √n. t2 = [1,0,1,1] → SD 0.5, n 4 → 0.25
stats.combined_stderrwhole split
Mixes two error sources of the split mean.
between² = var(task means) / n
within² = Σ SE_t² / n²
SE = √(between² + within²)
Example (3 tasks)value
task means1.00, 0.75, 0.25
task SEs0.00, 0.25, 0.25
split mean0.667
between² = 0.1458 / 30.0486
within² = 0.125 / 90.0139
SE = √0.06250.25
Rule of thumb from GateDecision.resolvable_effect_size: a round can resolve effects of about 2·SE, no smaller.

Source: core/cap_evolve/stats.py · gate.GateDecision · test_core.py

[7:50–8:50] Standard error answers one question: if I measured this again, how much would the mean move? stats.stderr is the textbook version: the sample standard deviation divided by the square root of n. For t2 that is 0.5 over 2, so 0.25.

For a whole split, the mean has two sources of error. Between-task error: tasks differ, and a different set of tasks would give a different mean. Within-task error: each task mean is itself noisy because it comes from a few trials. combined_stderr adds the two squares and takes the root. In the example the total SE is 0.25 on a mean of 0.667. That is a wide error bar, and that is honest for three tasks.

Every gate decision also carries resolvable_effect_size, which is 2 times SE. It tells the reader, before the delta, what size of effect this round could even detect. This came from tau2 airline: four runs of null results were read as "bad edits" when the gate simply could not see effects that small.

[7:50–8:50] standard error עונה על שאלה אחת: אם אמדוד שוב, כמה הממוצע יזוז? stats.stderr היא הגרסה של ספר הלימוד: סטיית התקן של המדגם חלקי שורש n. ל-t2 זה 0.5 חלקי 2, כלומר 0.25.

לממוצע של split שלם יש שני מקורות שגיאה. שגיאה בין משימות: משימות שונות זו מזו, וקבוצת משימות אחרת הייתה נותנת ממוצע אחר. שגיאה בתוך משימה: כל ממוצע של משימה רועש בעצמו, כי הוא בא מכמה trials בלבד. combined_stderr מחבר את שני הריבועים ומוציא שורש. בדוגמה ה-SE הכולל הוא 0.25 על ממוצע של 0.667. זה טווח שגיאה רחב, וזה כן עבור שלוש משימות.

The paired gate: compare each task with itself

paired (default of every real run)

Δ[t] = cand[t] − curr[t]
accept ⇔ mean(Δ) > k · SE(Δ)

significant (unpaired fallback)

accept ⇔ Δ > k · √(SE_c² + SE_p²)
Pairing cancels task difficulty. Tasks range from 0.25 to 1.0, but the Δs are steady. Only the spread of the Δs counts.

Source: core/cap_evolve/gate.py _verdict (modes paired, significant) · harness._paired_deltas

[8:50–9:50] Now the gate itself. Both the current champion and the candidate are scored on the same val tasks. So we can compare each task with itself. For each task t, delta t is candidate reward minus current reward. The paired rule accepts when the mean of the deltas is bigger than k times the standard error of the deltas.

Look at the chart. Gray is the parent, blue is the candidate. The tasks themselves are very different: some are at 0.25, some at 1.0. That spread is task difficulty. It is large, and it has nothing to do with the edit. The unpaired test, mode significant, counts that spread as noise. The paired test removes it, because difficulty appears on both sides of each pair and cancels. Only the spread of the green and red lines remains.

That is why paired is the default. The loop selects it whenever per-task data exists, and the scaffold spec says gate_mode paired. significant is only correct when the two sides were not scored on the same tasks.

[8:50–9:50] עכשיו ה-gate עצמו. גם ה-champion הנוכחי וגם ה-candidate נמדדים על אותן משימות val. לכן אפשר להשוות כל משימה לעצמה. לכל משימה t, הדלתא היא ה-reward של ה-candidate פחות ה-reward הנוכחי. הכלל המזווג מקבל כשממוצע הדלתאות גדול מ-k כפול ה-standard error של הדלתאות.

הסתכלו על הגרף. אפור זה ה-parent, כחול זה ה-candidate. המשימות עצמן שונות מאוד: חלקן ב-0.25, חלקן ב-1.0. הפיזור הזה הוא קושי המשימה. הוא גדול, ואין לו קשר לעריכה. המבחן הלא מזווג, mode significant, סופר את הפיזור הזה כרעש. המבחן המזווג מסיר אותו, כי הקושי מופיע בשני הצדדים של כל זוג ומתבטל. נשאר רק הפיזור של הקווים הירוקים והאדומים.

לכן paired היא ברירת המחדל. הלולאה בוחרת בה בכל פעם שיש נתונים לפי משימה, וה-spec של ה-scaffold אומר gate_mode paired. significant נכון רק כששני הצדדים לא נמדדו על אותן משימות.

Inside gate.decide(): the decision path

[11:10–12:20] This diagram is the code path of gate._verdict, left to right. First check: the split must be val, or the function raises TrainGateError. Not a reject, an exception. Second: coverage. If fewer than 60 percent of val tasks produced a valid score, the gate refuses to judge. It returns indecisive and logs a gate_warning. We come back to this.

Third: are there paired deltas? If not, the mode drops to significant and uses the combined SE. Fourth: is the SE above zero? paired_se_floor can raise the SE when per-task trial noise is larger than the cross-task spread suggests. If SE is still zero, gate_warning and the declared strict fallback.

Finally the real test: mean delta above k times SE. Accept or reject. After that, decide adds the composition: which tasks broke and which were fixed. It is descriptive. Only the opt-in gate_max_broke can use it, and only to subtract an accept.

[11:10–12:20] התרשים הזה הוא נתיב הקוד של gate._verdict, משמאל לימין. בדיקה ראשונה: ה-split חייב להיות val, אחרת הפונקציה זורקת TrainGateError. לא reject, אלא exception. שנייה: coverage. אם פחות מ-60 אחוז ממשימות ה-val הניבו ציון תקף, ה-gate מסרב לשפוט. הוא מחזיר indecisive ורושם gate_warning. נחזור לזה.

שלישית: האם יש paired deltas? אם לא, ה-mode יורד ל-significant ומשתמש ב-SE המשולב. רביעית: האם ה-SE גדול מאפס? paired_se_floor יכול להעלות את ה-SE כשרעש ה-trials בכל משימה גדול ממה שהפיזור בין המשימות מראה. אם ה-SE עדיין אפס, gate_warning ו-fallback מוצהר ל-strict.

[12:20–13:30] The gate can end in three ways, and the loop treats them differently. Accept: the candidate becomes the champion and is committed. Reject: the champion stays, the stall counter goes up, and the edit is filed in rejected memory, so the optimizer does not try it again. With stall equal to 2, two rejects in a row stop the run.

The third outcome is the subtle one. Indecisive means the gate did not judge: low coverage, a tampered candidate, an evaluation that crashed. In agent mode, round.py also marks a candidate inconclusive when its verdict flips between byte-identical control replicates. In all these cases the iteration is charged, but the stall counter is not. Stall means "the optimizer ran out of ideas", and an ambiguous measurement is no evidence of that.

The three tests in the table are each a real incident. In one smoke run, a re-gate overwrote its first control readings, so 200 rollouts bought no new evidence. Now a re-gate uses new tags and pools all replicates.

[12:20–13:30] ה-gate יכול להסתיים בשלוש דרכים, והלולאה מתייחסת לכל אחת אחרת. Accept: ה-candidate הופך ל-champion ונשמר ב-commit. Reject: ה-champion נשאר, מונה ה-stall עולה, והעריכה נרשמת בזיכרון ה-rejected, כדי שה-optimizer לא ינסה אותה שוב. עם stall שווה 2, שני rejects ברצף עוצרים את הריצה.

התוצאה השלישית היא העדינה. Indecisive אומר שה-gate לא שפט: coverage נמוך, candidate שעבר tampering, או הערכה שקרסה. ב-agent mode, round.py מסמן candidate גם כ-inconclusive כשההחלטה שלו מתהפכת בין control replicates זהים בבתים. בכל המקרים האלה ה-iteration נספר, אבל מונה ה-stall לא. stall אומר "ל-optimizer נגמרו הרעיונות", ומדידה עמומה היא לא ראיה לזה.

שלוש הבדיקות בטבלה הן כל אחת תקרית אמיתית. בריצת smoke אחת, re-gate דרס את קריאות ה-control הראשונות שלו, כך ש-200 rollouts לא קנו שום ראיה חדשה. עכשיו re-gate משתמש ב-tags חדשים ומאחד את כל ה-replicates.

[13:30–14:20] Rule: an unscored trial is missing data, not a reward of zero. When run_one raises, the trial pool turns the exception into an error rollout. The harness counts valid trials per task. A task with zero valid trials stays in the per-task report, but it is excluded from the split mean and from the paired deltas. SplitResult.coverage is the fraction that scored, and the gate goes indecisive below 0.6.

Why so strict? Read the box. In a SWE-bench run, Docker Hub rate-limited the image pulls. Every crashed trial arrived as "task not solved". Pairing made it worse: an unscored task that the parent passed counted as minus one. A candidate was rejected at minus 0.64 without one task evaluated.

There is one exception, and it is opt-in. If the candidate's own code raised the error, for example an edited tool that crashes, that is a real failure. With fault_attribution and errored_trial_policy fail, those trials score zero. Network errors, timeouts and HTTP 429 or 5xx are never blamed on the candidate.

[13:30–14:20] הכלל: trial שלא נמדד הוא נתון חסר, לא reward של אפס. כש-run_one זורק exception, ה-pool הופך אותו ל-rollout עם שגיאה. ה-harness סופר trials תקפים לכל משימה. משימה עם אפס trials תקפים נשארת בדוח לפי משימה, אבל לא נכנסת לממוצע של ה-split ולא ל-paired deltas. SplitResult.coverage הוא החלק שנמדד, וה-gate הופך ל-indecisive מתחת ל-0.6.

יש חריג אחד, והוא אופציונלי. אם הקוד של ה-candidate עצמו זרק את השגיאה, למשל tool ערוך שקורס, זה כשלון אמיתי. עם fault_attribution ו-errored_trial_policy fail, ה-trials האלה מקבלים אפס. שגיאות רשת, timeouts ו-HTTP 429 או 5xx אף פעם לא נזקפים ל-candidate.

[14:20–15:10] An audit of run_finalrun6 found the gate had no power. Each edit touched a few tasks, but the delta was averaged over all 30 val tasks. The 27 untouched tasks added only re-measurement noise. SE ran 0.022 to 0.035, while real effects were 0.011 to 0.05.

The fix is the footprint. footprint.py reads the named symbols in the diff and finds the val tasks whose rollouts exercise them. Outside the footprint, delta is zero by construction, so the code writes a zero instead of the noisy measurement. The vector keeps its full length, so the mean stays on the val scale. This is dangerous if the footprint is too small, because a hidden regression would be zeroed. So when the code is not sure, footprint returns None and the full split is used.

The same audit gave move_is_resolved: one flipped rollout out of ten is not a behavioural break. And a note: task_ownership.py tracks per-task best scorers, but it decides nothing.

[14:20–15:10] ביקורת על run_finalrun6 מצאה שלא היה ל-gate כוח סטטיסטי. כל עריכה נגעה בכמה משימות, אבל הדלתא חושבה על כל 30 משימות ה-val. 27 המשימות שלא נגעו בהן הוסיפו רק רעש של מדידה חוזרת. ה-SE היה 0.022 עד 0.035, כשהאפקטים האמיתיים היו 0.011 עד 0.05.

[15:10–16:00] A full-val evaluation is the main cost of a run. Most edits are not close calls; they are clearly neutral or clearly harmful. So there is a screen ladder: rung one screens a quarter of val, never fewer than six tasks; then half; then three quarters.

The hard rule: a screen may kill, never accept. Errors here are not symmetric. A false kill throws away a good edit and leaves no trace. A false promote costs one full-val evaluation, and then the honest gate decides. So the screen leans toward promote. The kill rule changed in issue 684: the old significance test could never fire on 5 to 11 tasks, so now a screen kills only on a gross drop of 0.15 or more.

In agent-optimize, round.py refuses a candidate with no screen record unless the driver passes skip-screen-ladder. screen_accounting is an opt-in design with known inclusion probabilities, so the screen gives an unbiased estimate. It is still labelled a scheduling signal, not a result.

[15:10–16:00] הערכה מלאה על val היא העלות העיקרית של ריצה. רוב העריכות הן לא מקרים גבוליים; הן ניטרליות בבירור או מזיקות בבירור. לכן יש screen ladder: השלב הראשון בודק רבע מ-val, ולא פחות משש משימות; אחר כך חצי; אחר כך שלושה רבעים.

הכלל הקשיח: screen יכול להרוג, אף פעם לא לקבל. הטעויות כאן לא סימטריות. kill שגוי זורק עריכה טובה ולא משאיר עקבות. promote שגוי עולה הערכת val מלאה אחת, ואז ה-gate הכן מחליט. לכן ה-screen נוטה ל-promote. כלל ה-kill השתנה ב-issue 684: מבחן המובהקות הישן לא יכול היה לפעול על 5 עד 11 משימות, אז עכשיו screen הורג רק בירידה גסה של 0.15 או יותר.

ב-agent-optimize, round.py מסרב ל-candidate בלי רשומת screen, אלא אם ה-driver מעביר skip-screen-ladder. screen_accounting הוא עיצוב אופציונלי עם הסתברויות הכללה ידועות, כך שה-screen נותן אומד לא מוטה. הוא עדיין מסומן כ-scheduling signal ולא כתוצאה.

[16:00–16:50] The paired gate is the default. These are stronger rules for when you need them. They share one idea: the measurement that picked the winner is biased upward, so confirm it on new data.

Rule P screens with the paired gate, then re-measures candidate and incumbent with ten fresh trials and new seeds. It promotes only if the confirmed mean is at least 0.02 and z is at least 2. Rule P2 is a racing design. Eight candidates race on the feedback stratum with kill-only successive halving. At most two survivors get one confirmation on the hidden stratum C, against a control measured at the same time. With one candidate, gs_decide uses group-sequential looks.

posterior.py is a Bayesian rule; test_posterior_rule_never_accepts_replicate_nulls checks it on byte-identical replicates. objectives.py handles cost honestly: cost is compared only on tasks both arms solve. Pareto and epsilon-constraint require each objective to clear its own k times SE bar.

[16:00–16:50] ה-gate המזווג הוא ברירת המחדל. אלה כללים חזקים יותר למקרה שצריך אותם. יש להם רעיון משותף: המדידה שבחרה את המנצח מוטה כלפי מעלה, ולכן מאמתים על נתונים חדשים.

כלל P עושה screen עם ה-gate המזווג, ואז מודד מחדש את ה-candidate ואת ה-incumbent עם עשרה trials חדשים ו-seeds חדשים. הוא מקדם רק אם הממוצע המאומת לפחות 0.02 ו-z לפחות 2. כלל P2 הוא עיצוב של racing. שמונה candidates מתחרים על ה-feedback stratum עם successive halving שרק הורג. לכל היותר שני שורדים מקבלים אימות אחד על ה-stratum הנסתר C, מול control שנמדד באותו זמן. עם candidate אחד, gs_decide משתמש ב-group-sequential looks.

posterior.py הוא כלל בייסיאני; test_posterior_rule_never_accepts_replicate_nulls בודק אותו על replicates זהים בבתים. objectives.py מטפל בעלות בכנות: משווים עלות רק על משימות ששני הצדדים פותרים. Pareto ו-epsilon-constraint דורשים שכל objective יעבור את סף ה-k כפול SE שלו.

[16:50–17:40] Now the seal. splits.json carries a flag, test_used. It starts false. finalize does four steps. reserve_test checks the flag without flipping it. begin_test_attempt is called once per finalize attempt: if test rollout files already exist, it refuses. Then finalize scores test twice: the best candidate as FINAL and the seed as FINAL_seed. Only after both results are written does commit_test flip the flag.

Why this order? The first version, consume_test, burned the seal before scoring. A transient crash then destroyed the run's headline number forever. So now the seal burns only on success. But that opened a hole: a finalize killed by a timeout after scoring could be retried, and the headline became a second look at test. This happened in a real run. begin_test_attempt closes it.

If you really must re-score, set CAPEVOLVE_ALLOW_TEST_RESCORE. It is an env var on purpose, so the bypass is visible.

[16:50–17:40] עכשיו החותם. splits.json נושא דגל בשם test_used. הוא מתחיל כ-false. finalize עושה ארבעה צעדים. reserve_test בודק את הדגל בלי להפוך אותו. begin_test_attempt נקרא פעם אחת בכל ניסיון finalize: אם כבר קיימים קבצי rollout של test, הוא מסרב. אחר כך finalize מודד את test פעמיים: את ה-candidate הטוב ביותר כ-FINAL ואת ה-seed כ-FINAL_seed. רק אחרי ששתי התוצאות נכתבו, commit_test הופך את הדגל.

למה הסדר הזה? הגרסה הראשונה, consume_test, שרפה את החותם לפני המדידה. קריסה רגעית הרסה אז את המספר הראשי של הריצה לתמיד. לכן עכשיו החותם נשרף רק בהצלחה. אבל זה פתח חור: finalize שנהרג ב-timeout אחרי המדידה יכול היה לרוץ שוב, והמספר הראשי הפך למבט שני על test. זה קרה בריצה אמיתית. begin_test_attempt סוגר את החור.

אם באמת חייבים למדוד שוב, מגדירים CAPEVOLVE_ALLOW_TEST_RESCORE. זה משתנה סביבה בכוונה, כדי שהעקיפה תהיה גלויה.

Three layers keep the optimizer away from test and gold

A tampered candidate is discarded, never scored 0.0: the number describes a broken harness, not the edit. Added files count as tampering.

Source: plugins/cap-evolve/hooks/hooks.json, deny_sealed_edits.py · core/cap_evolve/integrity.py · test_integrity.py, test_integrity_wiring.py::test_tampered_candidate_is_indecisive_and_costs_nothing

[17:40–18:20] How do we stop the optimizer from editing gold? Three layers. Layer one is a Claude Code plugin hook. hooks.json registers deny_sealed_edits.py as a PreToolUse hook on Edit, Write, MultiEdit and NotebookEdit. It blocks splits.json, test rollouts, gold answer files, and files named after a test id. Exit code 2 blocks the call and tells the model why. The limit: it only works when Claude Code runs the edit.

Layer two is host-independent. With protected_paths in the spec, integrity.snapshot hashes the protected files before the optimizer runs, and verify checks them before any rollout is paid. Codex, Gemini or a shell script cannot get past a hash. A tampered candidate is indecisive: discarded, not scored zero. This layer is off by default.

Layer three is the core seal from the previous slide. Even if both other layers fail, the core will not score test twice or gate on train.

[17:40–18:20] איך מונעים מה-optimizer לערוך את ה-gold? שלוש שכבות. שכבה ראשונה היא hook של ה-plugin ל-Claude Code. hooks.json רושם את deny_sealed_edits.py כ-PreToolUse hook על Edit, Write, MultiEdit ו-NotebookEdit. הוא חוסם את splits.json, rollouts של test, קבצי תשובות gold, וקבצים ששמם הוא id של משימת test. exit code 2 חוסם את הקריאה ומסביר למודל למה. המגבלה: זה עובד רק כש-Claude Code מבצע את העריכה.

שכבה שנייה לא תלויה ב-host. עם protected_paths ב-spec, integrity.snapshot מחשב hash לקבצים המוגנים לפני שה-optimizer רץ, ו-verify בודק אותם לפני שמשלמים על rollout כלשהו. Codex, Gemini או סקריפט shell לא יכולים לעבור hash. candidate שעבר tampering הוא indecisive: נזרק, לא מקבל אפס. השכבה הזו כבויה כברירת מחדל.

שכבה שלישית היא החותם של ה-core מהשקף הקודם. גם אם שתי השכבות האחרות נכשלות, ה-core לא ימדוד את test פעמיים ולא יעשה gate על train.

Lessons from real runs

HOLDOUT_PROTOCOL.md (tau2 airline)

  • 50 tasks: 0-29 are train = val, so val is "selection-biased"
  • Tasks 30-49 were scored once: "development-exposed"
  • No test traces in edits, prompts or fixtures
  • Every report states ids, seeds, candidates tried
  • Do not invent a fresh holdout that does not exist

MEASUREMENT_FINDINGS.md

  • Byte-identical code, same seeds, temp 0: arms still differ by ~binomial SE
  • Calibrate first: two identical arms give the real bar
  • Verified per-task gains do not compose: a 6-mechanism merge measured −0.0146
  • Per-task attribution needs n≈40; n=10 tables only suggest hypotheses
Explore fast, gate slow. Integrate one change at a time, with canaries from the whole suite.

Source: docs/HOLDOUT_PROTOCOL.md · docs/MEASUREMENT_FINDINGS.md (sections 1, 2, 5)

[18:20–19:00] Two docs hold the lessons from tau2 airline. HOLDOUT_PROTOCOL is about labels. Airline has only 50 tasks. Tasks 0 to 29 served as both train and val, so any val number there is a fit metric. Tasks 30 to 49 were already scored once, so they are "development-exposed". The protocol says this plainly and does not pretend a fresh holdout exists. Every report must state the ids, the seeds, and how many candidates were tried.

MEASUREMENT_FINDINGS is about the instrument. Byte-identical code on identical seeds at temperature zero still did not reproduce. Once a load-dependent excess was removed, the rest matched plain binomial noise. The lesson: measure two identical arms first, and that is your bar. Second lesson: gains verified one at a time did not compose. A merge of six verified mechanisms measured slightly negative. So integrate one step at a time.

[18:20–19:00] שני מסמכים מחזיקים את הלקחים מ-tau2 airline. HOLDOUT_PROTOCOL עוסק בתיוג. ל-airline יש רק 50 משימות. משימות 0 עד 29 שימשו גם כ-train וגם כ-val, ולכן כל מספר val שם הוא מדד fit. משימות 30 עד 49 כבר נמדדו פעם אחת, ולכן הן "development-exposed". הפרוטוקול אומר את זה בפשטות ולא מעמיד פנים שיש holdout טרי. כל דוח חייב לציין את ה-ids, ה-seeds, וכמה candidates נוסו.

MEASUREMENT_FINDINGS עוסק במכשיר המדידה. קוד זהה בבתים על seeds זהים ב-temperature אפס עדיין לא שוחזר. אחרי שהוסר עודף שתלוי בעומס, מה שנשאר התאים לרעש בינומי רגיל. הלקח: למדוד קודם שתי זרועות זהות, וזה הסף שלכם. לקח שני: שיפורים שאומתו אחד אחד לא הצטברו. מיזוג של שישה מנגנונים מאומתים נמדד קצת שלילי. לכן משלבים צעד אחד בכל פעם.

Key takeaways

  • Splits are seeded and frozen in splits.json; nothing re-splits
  • Gate on val only; accept iff Δ̄ > k·SE, paired by task
  • Missing data is not 0.0; low coverage is indecisive
  • Indecisive charges the iteration, never the stall
  • Screens may kill, never accept
  • Test is scored once, at finalize, with FINAL_seed beside it

[19:30–20:00] Six things to remember. The split is made once and frozen. The gate reads val only and needs the mean paired delta to beat k standard errors. A trial that did not run is missing, not zero, and when too much is missing the gate does not judge. Indecisive costs an iteration but does not count toward stopping. Screens are triage: they kill, they never accept. And test is scored once, next to the seed, so the reported number has a baseline.
