How the parts depend on each other

Arrows point at what is used. Sources: core/cap_evolve/_bootstrap.py, observer.py, dashboard/backend/pyproject.toml, capevolve_harbor/__init__.py

[3:50–5:00] This picture shows the direction of every dependency. Core is in the middle, and it depends on nothing outside the Python standard library. Everything else points at core.

  • Skill scripts are loose files. A host copies them anywhere. So each skill has a _bootstrap.py that finds core, for example through the CAPEVOLVE_CORE environment variable.
  • The other way, the CLI in core runs each skill's scripts/run.py as a subprocess and parses the one JSON object it prints.
  • Adapters subclass CapabilityAdapter from adapter.py.
  • The dashboard package lists cap-evolve-core as a dependency and calls reduce_run(). Core never imports the dashboard. It only starts it as a subprocess.
  • Telemetry satisfies the Observer protocol without importing it. Harbor turns Harbor results into Rollout and Score.

The plugin's skills entry is a symlink to the real skills/ folder.

[3:50–5:00] התמונה הזו מראה את הכיוון של כל תלות. ה-core נמצא באמצע, והוא לא תלוי בשום דבר מחוץ ל-standard library של Python. כל השאר מצביע עליו.

  • הסקריפטים של ה-skills הם קבצים בודדים, ו-host יכול להעתיק אותם לכל מקום. לכן לכל skill יש _bootstrap.py שמוצא את ה-core, למשל דרך משתנה הסביבה CAPEVOLVE_CORE.
  • בכיוון ההפוך, ה-CLI שב-core מריץ את scripts/run.py של כל skill כ-subprocess, ומפרסר את אובייקט ה-JSON היחיד שהוא מדפיס.
  • ה-adapters יורשים מ-CapabilityAdapter שב-adapter.py.
  • ה-package של ה-dashboard מגדיר את cap-evolve-core כתלות וקורא ל-reduce_run(). ה-core אף פעם לא מייבא את ה-dashboard, הוא רק מפעיל אותו כ-subprocess.
  • ה-telemetry מממש את פרוטוקול Observer בלי לייבא אותו. Harbor מתרגם תוצאות של Harbor ל-Rollout ו-Score.

ה-skills שבתוך ה-plugin הוא symlink לתיקיית skills/ האמיתית.

[5:00–6:10] The core package is called cap-evolve-core. It needs Python 3.10 or newer. Its dependency list is empty on purpose. CONTRIBUTING calls this a house rule: zero runtime dependencies in core, and optional features go behind extras. That is why core has its own tolerant YAML reader in specfile.py. It uses PyYAML only if it is already present.

The only console script is cap-evolve, which calls cap_evolve.cli:main. The dev extra brings pytest, plus openpyxl and pandas for the SpreadsheetBench tests. Without them, those tests skip in silence. The judge and dashboard extras are empty placeholders. The package also ships a small synthetic demo session, so cap-evolve replay --demo works with no API key.

For development, use an editable install with the dev extra, then run the unit tests and compileall, as CONTRIBUTING asks.

[5:00–6:10] ה-package של ה-core נקרא cap-evolve-core. הוא דורש Python 3.10 ומעלה. רשימת התלויות שלו ריקה בכוונה. ב-CONTRIBUTING זה כלל של הבית: אפס תלויות runtime ב-core, ופיצ'רים אופציונליים נכנסים מאחורי extras. בגלל זה ל-core יש קורא YAML סלחני משלו ב-specfile.py, שמשתמש ב-PyYAML רק אם הוא כבר מותקן.

ה-console script היחיד הוא cap-evolve, שקורא ל-cap_evolve.cli:main. ה-extra בשם dev מביא pytest, וגם openpyxl ו-pandas בשביל הבדיקות של SpreadsheetBench; בלעדיהם הבדיקות האלה מדלגות בשקט. ה-extras בשם judge ו-dashboard הם placeholders ריקים. ה-package גם כולל demo session סינתטי קטן, כך ש-cap-evolve replay --demo עובד בלי מפתח API.

לפיתוח, מתקינים editable עם ה-extra של dev, ואז מריצים את בדיקות היחידה ו-compileall, כמו ש-CONTRIBUTING מבקש.

[6:10–7:20] Core is flat. All 67 modules sit in one folder with no sub-packages. To make it easier to read, I grouped them into eight layers. This grouping is mine. It is not in the code. The numbers are real line counts.

Two files are very large. harness.py has about 5,400 lines. It holds the shared mechanics that the phase and algorithm skills call. dashboard.py has about 4,300 lines. It folds the event log into one state object and renders reports. cli.py is third, with about 1,900 lines. When you search for a behaviour, start in these three files. Then follow the imports into the smaller modules. For example, a gate decision starts in harness.py and ends in gate.py. The next three slides walk through each layer.

[6:10–7:20] ה-core שטוח. כל 67 המודולים יושבים בתיקייה אחת, בלי sub-packages. כדי שיהיה קל לקרוא, חילקתי אותם לשמונה שכבות. החלוקה הזו שלי, היא לא כתובה בקוד. המספרים הם ספירות שורות אמיתיות.

[7:20–8:30] The first layer is what the user touches. cli.py is a thin sequencer. It holds no pipeline logic. It finds each skill through the registry manifest and runs that skill's run.py in the order the spec asks. The COMMANDS table in cli.py has 14 entries, from init and doctor to run, watch and replay. __main__.py is a second, smaller entry for hosts that cannot import the package. check.py is the hard gate: no budget is spent until it passes.

The second layer is orchestration. harness.py is the big one. Its function names tell the story: ensure_splits, baseline, evaluate_candidate, run_step, hill_climb_loop, finalize. Around it sit small modules that read one part of the spec each. For example, constraints.py turns a free-text stop condition like "stop after 40 dollars" into a predicate the loop can check again and again.

[7:20–8:30] השכבה הראשונה היא מה שהמשתמש נוגע בו. cli.py הוא sequencer דק, בלי לוגיקה של pipeline. הוא מוצא כל skill דרך ה-manifest של ה-registry ומריץ את ה-run.py שלו בסדר שה-spec מבקש. בטבלת COMMANDS שב-cli.py יש 14 פקודות, מ-init ו-doctor ועד run, watch ו-replay. __main__.py הוא כניסה שנייה וקטנה יותר ל-hosts שלא יכולים לייבא את ה-package. check.py הוא ה-gate הקשיח: לא מוציאים תקציב עד שהוא עובר.

השכבה השנייה היא orchestration. harness.py הוא הגדול. שמות הפונקציות שלו מספרים את הסיפור: ensure_splits, baseline, evaluate_candidate, run_step, hill_climb_loop, finalize. סביבו יש מודולים קטנים שכל אחד קורא חלק אחד של ה-spec. למשל, constraints.py הופך stop condition בטקסט חופשי, כמו "תעצור אחרי 40 דולר", ל-predicate שהלולאה יכולה לבדוק שוב ושוב.

[8:30–9:30] Layer three measures a candidate. A candidate is one version of the files the optimizer may edit. adapter.py defines the contract a benchmark implements. types.py defines the shared dataclasses. trials.py runs several trials per task in parallel. evaluator.py is one scheduler shared by two algorithms. The cache and the eval index skip a rollout when the same files were already scored on the same task.

Layer four decides. stats.py is the only place where rewards are averaged. That keeps the math in one spot. gate.py holds the accept rule. splits.py makes the train, val and test splits from a seed and keeps test sealed. integrity.py detects if an optimizer edited protected files, like the scorer. The flow at the bottom is the short version of one evaluation. Chapter 6 explains each rule and why it exists.

[8:30–9:30] השכבה השלישית מודדת candidate. Candidate הוא גרסה אחת של הקבצים שה-optimizer מורשה לערוך. adapter.py מגדיר את החוזה ש-benchmark מממש. types.py מגדיר את ה-dataclasses המשותפים. trials.py מריץ כמה trials לכל משימה במקביל. evaluator.py הוא scheduler אחד ששני algorithms חולקים. ה-cache וה-eval index מדלגים על rollout כשאותם קבצים כבר קיבלו ציון על אותה משימה.

השכבה הרביעית מחליטה. stats.py הוא המקום היחיד שבו ממצעים rewards, וכך המתמטיקה נשארת במקום אחד. gate.py מחזיק את כלל הקבלה. splits.py בונה את ה-splits של train, val ו-test מ-seed ושומר את test חתום. integrity.py מזהה אם optimizer ערך קבצים מוגנים, כמו ה-scorer. ה-flow למטה הוא הגרסה הקצרה של הערכה אחת. בפרק 6 נסביר כל כלל ולמה הוא קיים.

[9:30–10:40] The last four layers. First, the algorithms. An algorithm is the search strategy across iterations. The plain hill-climb loop is a function inside harness.py. GEPA and SkillOpt each have their own module. hc2.py is a hill-climb that makes K proposals per round. selection.py is one registry of parent pickers, so algorithms do not each write their own. Note the pattern: the skill folder for an algorithm is thin, and the real loop is in core.

Storage and events: rundir.py owns the on-disk run directory. store.py saves every iteration, with git as the default backend. eventstream.py is the one reader for events.jsonl. Then views: dashboard.py and tui.py. Both are pure renderers of the state that reduce_run builds. Helpers are small. __init__.py even turns on faulthandler, so a crash in a C extension leaves a traceback.

[15:20–16:30] There are two ways to put the skills into an agent host. A host is the coding agent that reads the skills, like Claude Code or Codex. For Claude Code, use the plugin. Its skills entry is a symlink, so the plugin always matches the repo. It adds two subagents and four hooks. The hooks enforce honesty in code, not in prose. Key takeaways

Core is small in deps, big in code

Pure stdlib, 67 flat modules. Start in harness.py, dashboard.py, cli.py.

Skills are folders with a contract

meta.yaml + SKILL.md + run.py that prints one JSON. Rebuild the manifest after changes.

Everything else points at core

Dashboard, telemetry, Harbor, adapters and the plugin depend on core. Never the reverse.

Work through the dev skills

open-pr → track skill → review-cycles. Sign off every commit.
