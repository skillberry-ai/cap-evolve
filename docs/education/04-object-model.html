Four dataclasses everyone speaks

Task
id, input, target (gold), metadata. One unit of eval work.
Candidate
id, component, text_parts (gepa view), dir (file-tree view).
Rollout
task_id, output, trace, tool_calls, cost_usd, tokens, error, metadata.
Score
reward 0..1, feedback, n, stderr, trial_rewards, raw, metrics.

Source: core/cap_evolve/types.py — pure stdlib, each class has to_dict / from_dict

[1:20–2:30] types.py holds exactly four dataclasses. The module docstring calls it the shared vocabulary for the whole pipeline. A Task is one unit of evaluation work. Its target field holds the gold answer, and it never leaves the scorer. A Candidate is one version of the capability. It has two views: text_parts is a dictionary of named text components, which gepa uses, and dir is a path to a file tree, which the other algorithms use. Both may be set.

A Rollout is the result of running the target agent on one task with a candidate live. It carries output, trace, tool calls, cost, tokens, and an error string for infrastructure failures. A Score is the judged result: a reward between zero and one, plus natural-language feedback. The feedback is the learning signal for the optimizer. The docstring calls it gepa's Actionable Side Information. Note that Score also stores n, stderr and trial_rewards, so one Score can describe several trials of the same task.

[1:20–2:30] בקובץ types.py יש בדיוק ארבעה dataclasses. ה-docstring קורא לו אוצר המילים המשותף של כל ה-pipeline. Task הוא יחידת עבודה אחת של הערכה. השדה target מחזיק את התשובה הנכונה, והוא אף פעם לא יוצא מה-scorer. Candidate הוא גרסה אחת של ה-capability. יש לו שתי תצוגות: text_parts הוא מילון של רכיבי טקסט עם שמות, ש-gepa משתמש בו, ו-dir הוא נתיב לעץ קבצים, שבו משתמשים האלגוריתמים האחרים. אפשר למלא את שניהם.

Rollout הוא התוצאה של הרצת ה-target agent על task אחד כשה-candidate פעיל. הוא מחזיק output, trace, קריאות לכלים, עלות, tokens, ושדה error לכשלי תשתית. Score הוא התוצאה השפוטה: reward בין אפס לאחת, ועוד feedback בשפה טבעית. ה-feedback הוא אות הלמידה של ה-optimizer, מה שה-docstring מכנה Actionable Side Information של gepa. שימו לב ש-Score שומר גם n, stderr ו-trial_rewards, כך ש-Score אחד יכול לתאר כמה trials של אותו task.

    """a buggy scorer can't poison stats"""

The metrics catalog

[{"name": "reward",  "value": 1.0,
  "primary": true,  "direction": "higher"},
 {"name": "cost_usd", "value": 0.013,
  "primary": false, "direction": "lower"}]

  • primary value must equal reward
  • others are shown only — never move the gate
  • bad catalog → ValueError at construction

[3:30–4:20] Score does real work in its constructor. __post_init__ clamps the reward and every trial reward into the range zero to one. A NaN becomes zero. The comment says why: a buggy scorer must not poison the statistics. A reward of 1.7 or minus 3 would break the standard error and the gate in chapter six.

On the right is the optional metrics catalog. A scorer can report secondary numbers, for example db_match and cost_usd in the tau2 adapter. The rules are checked at construction time: names are unique, exactly one entry is primary, and the primary value must equal reward. The gate reads only the primary. The others are for the dashboard. The validation is strict on purpose. A broken catalog used to crash much later, inside harness._aggregate_metrics, far from the real bug.

[3:30–4:20] ה-Score עושה עבודה אמיתית כבר ב-constructor. הפונקציה __post_init__ מצמצמת את ה-reward ואת כל ה-trial rewards לטווח אפס עד אחת. NaN הופך לאפס. ההערה בקוד מסבירה למה: scorer עם באג לא יכול להרעיל את הסטטיסטיקה. reward של 1.7 או של מינוס 3 היה שובר את ה-standard error ואת ה-gate שנראה בפרק שש.

מימין רואים את ה-metrics catalog האופציונלי. scorer יכול לדווח מספרים משניים, למשל db_match ו-cost_usd ב-adapter של tau2. הכללים נבדקים כבר ביצירה: שמות ייחודיים, בדיוק רשומה אחת היא primary, וערך ה-primary חייב להיות שווה ל-reward. ה-gate קורא רק את ה-primary. השאר נועדו ל-dashboard. הבדיקה קפדנית בכוונה: catalog שבור היה קורס פעם הרבה יותר מאוחר, בתוך harness._aggregate_metrics, רחוק מהבאג האמיתי.

[4:20–5:10] A candidate directory holds more than the capability. The optimizer writes scratch notes there, the harness injects read-only context like trajectories and guidance, and agent hosts add their own instruction files like CLAUDE.md. None of that is the capability.

types.py defines two frozen sets: NON_CAPABILITY_FILES and NON_CAPABILITY_DIRS. Three readers use them. The content hash in cache.py skips them, so a byte-identical copy of the seed gets the same hash. gepa does not treat them as components to optimize. And diffview does not show them as edits. The comment in the code tells the history. There were three copies of this list, and they drifted. A real gepa diff showed two real changed lines under thirty-three lines of gepa's own bookkeeping. If you add a new scratch file, add it here, in one place.

[4:20–5:10] תיקיית candidate מכילה יותר מה-capability עצמו. ה-optimizer כותב שם הערות עבודה, ה-harness מזריק הקשר לקריאה בלבד כמו trajectories ו-guidance, ו-hosts של סוכנים מוסיפים קבצי הוראות משלהם כמו CLAUDE.md. שום דבר מזה אינו ה-capability.

ב-types.py מוגדרים שני frozen sets: ‏NON_CAPABILITY_FILES ו-NON_CAPABILITY_DIRS. שלושה קוראים משתמשים בהם. ה-content hash ב-cache.py מדלג עליהם, ולכן עותק זהה בבתים של ה-seed מקבל אותו hash. ‏gepa לא מתייחס אליהם כרכיבים לאופטימיזציה. ו-diffview לא מציג אותם כשינויים. ההערה בקוד מספרת את ההיסטוריה: היו שלושה עותקים של הרשימה, והם התפצלו. diff אמיתי של gepa הראה שתי שורות שינוי אמיתיות מתחת לשלושים ושלוש שורות של רישומים פנימיים. אם מוסיפים קובץ עבודה חדש, מוסיפים אותו כאן, במקום אחד.

[5:10–6:10] The project implements one class, a subclass of CapabilityAdapter, in .capevolve/project/adapters/adapter.py. Three methods are abstract: tasks, run_target and score. Get data, run, score. Stubs raise NotImplementedError with the marker IMPLEMENT ME, and the function stub_methods probes for that marker so cap-evolve check can say exactly what is missing.

Five hooks have working defaults. materialize, live and apply make a candidate live. trajectories can return a folder of native traces. runner_model returns the consuming model id so check can warn about a mismatch with the spec. Three more are fast paths. They are not on the base class at all. The harness feature-detects them with hasattr. run_batch lets tau2 drive its own batch runner. run_trials runs all trials in one call. score_batch lets swebench grade a whole trial in one Docker harness call. Any task the batch omits falls back to a plain score call, so nothing is silently dropped.

One note: the brief for this course mentions capability_sources as a hook. In the code it is a spec key in capevolve.yaml, read by the harness, not an adapter method.

[5:10–6:10] הפרויקט מממש מחלקה אחת, תת-מחלקה של CapabilityAdapter, בקובץ ‎.capevolve/project/adapters/adapter.py. שלוש מתודות הן abstract: ‏tasks, ‏run_target ו-score. להביא נתונים, להריץ, לתת ציון. stub זורק NotImplementedError עם הסימון IMPLEMENT ME, והפונקציה stub_methods מחפשת את הסימון הזה כדי ש-cap-evolve check יגיד בדיוק מה חסר.

לחמישה hooks יש ברירת מחדל שעובדת. materialize, ‏live ו-apply הופכים candidate לפעיל. trajectories יכול להחזיר תיקייה של traces מקוריים. runner_model מחזיר את מזהה המודל בפועל, כדי ש-check יזהיר על אי-התאמה מול ה-spec. עוד שלושה הם fast paths. הם בכלל לא מוגדרים במחלקת הבסיס. ה-harness מזהה אותם עם hasattr. ‏run_batch מאפשר ל-tau2 להפעיל את ה-batch runner שלו. run_trials מריץ את כל ה-trials בקריאה אחת. score_batch מאפשר ל-swebench לדרג trial שלם בקריאה אחת ל-Docker. task שה-batch השמיט נופל חזרה לקריאת score רגילה, כך ששום דבר לא נעלם בשקט.

הערה אחת: התדריך של הקורס מזכיר את capability_sources כ-hook. בקוד זה מפתח ב-capevolve.yaml שה-harness קורא, לא מתודה של ה-adapter.

How a candidate becomes live: ctx

materialize
pure: writes edits into the dir only
live
context manager; may yield a sandbox or worktree
seed
must reach a stochastic runner, or SE = 0

[6:10–7:20] What is ctx? It is whatever the adapter's live context manager yields. By default, live calls the old apply hook and yields the candidate directory path. An adapter can yield something richer: a sandbox handle or a worktree path. That is the reason for the split between materialize and live. The old apply was a global side effect, like monkeypatching a benchmark's policy. With one global slot you cannot evaluate two candidates at once, and the safety check would mutate the host. materialize is pure. live is scoped to one evaluation and tears down on exit.

Inside live, the harness loops over trials. The seed for trial k is base_seed plus k. If the runner is an LLM agent, the adapter must forward that seed. If it does not, all trials are identical, the standard error is zero, and any positive delta passes the gate. Then scoring runs serially, and the result goes to one rollout file per task and trial. The whole body runs with stdout redirected to stderr. We will see why on the stdout slide.

[6:10–7:20] מה זה ctx? זה מה שה-context manager בשם live של ה-adapter מחזיר ב-yield. כברירת מחדל, live קורא ל-hook הישן apply ומחזיר את נתיב תיקיית ה-candidate. adapter יכול להחזיר משהו עשיר יותר: handle של sandbox או נתיב של worktree. זו הסיבה להפרדה בין materialize ל-live. ה-apply הישן היה side effect גלובלי, למשל monkeypatch למדיניות של benchmark. עם מקום גלובלי אחד אי אפשר להעריך שני candidates במקביל, ובדיקת הבטיחות הייתה משנה את ה-host. ‏materialize הוא טהור. live תחום להערכה אחת ומנקה אחריו ביציאה.

בתוך live, ה-harness עובר בלולאה על ה-trials. ה-seed של trial מספר k הוא base_seed ועוד k. אם ה-runner הוא סוכן LLM, ה-adapter חייב להעביר את ה-seed הלאה. אם לא, כל ה-trials זהים, ה-standard error הוא אפס, וכל delta חיובי עובר את ה-gate. אחר כך ה-scoring רץ באופן סדרתי, והתוצאה נכתבת לקובץ rollout אחד לכל task ו-trial. כל הגוף הזה רץ כש-stdout מופנה ל-stderr. נראה למה בשקף על stdout.

Four honesty rules for an adapter

🔁

Deterministic tasks and score

check.py calls tasks('val') twice and score() twice on a probe Rollout(output="__probe_output__"). Any difference fails check.

🙈

Never leak gold

feedback goes to the optimizer. It describes why in general terms. The gold target stays in the scorer.

⚡

Infra failure is not a zero

Set Rollout.error, or Score.raw["errored"] when grading crashed. The harness drops that trial from the mean.

🧩

Do not re-implement core

Splits, trials, pass^k, gate, memory and the run dir belong to cap_evolve. The adapter only gets data, runs, and scores.

Source: core/cap_evolve/check.py, harness.py _persist_trial, docs/ADAPTER_CONTRACT.md

[7:20–8:10] Four rules keep the numbers honest. One: determinism. cap-evolve check loads the adapter, calls tasks of val twice and compares, then scores the same probe rollout twice and compares the rewards. A non-deterministic scorer fails before any budget is spent. The contract doc says this is enforced by the gate; in the code it is the check command, which the docs also call the gate.

Two: never leak the gold answer in feedback, because the optimizer reads feedback and would learn the answers. Three: an infrastructure failure is missing data, not a zero. A real example from the code comments: a Docker Hub rate-limit storm once became a val score of zero and taught the optimizer to fix content that was not broken. So set Rollout.error, or set errored in Score.raw when grading itself crashed. Four: do not rebuild splits or gating inside the adapter. Chapter six explains why those rules exist.

[7:20–8:10] ארבעה כללים שומרים על המספרים כנים. אחד: דטרמיניזם. cap-evolve check טוען את ה-adapter, קורא ל-tasks של val פעמיים ומשווה, ואז מדרג את אותו probe rollout פעמיים ומשווה את ה-rewards. scorer לא דטרמיניסטי נכשל עוד לפני שמוציאים תקציב. מסמך ה-contract אומר שה-gate אוכף את זה; בקוד זו פקודת check, שהמסמכים קוראים לה גם gate.

שתיים: לא לחשוף את התשובה הנכונה ב-feedback, כי ה-optimizer קורא את ה-feedback ויכול ללמוד את התשובות. שלוש: כשל תשתית הוא מידע חסר, לא אפס. דוגמה אמיתית מההערות בקוד: סערה של rate limit ב-Docker Hub הפכה פעם לציון val של אפס, ולימדה את ה-optimizer לתקן תוכן שלא היה שבור. לכן מגדירים Rollout.error, או errored בתוך Score.raw כשה-grading עצמו קרס. ארבע: לא לבנות מחדש splits או gating בתוך ה-adapter. פרק שש מסביר למה הכללים האלה קיימים.

How the objects relate

[8:10–9:30] This is the whole object model on one page, with real names. Note first what is not a class. The spec is a plain dict that specfile.read_yaml returns from capevolve.yaml. The harness is a module of functions, not a Harness class. The event stream is the eventstream module, a reader of events.jsonl.

Read it top down. cli.py reads the spec and runs phase skills as subprocesses. They call the harness. The harness gets a Candidate as a directory under candidates, and drives the project's CapabilityAdapter: live, run_target, score. The adapter returns Rollouts and Scores. The harness aggregates Scores into a SplitResult, which lives in loop.py, and writes everything through RunDir: events, spend, snapshots. VersionStore commits the run directory to git. On the right, two readers: reduce_run projects the run for the TUI and the dashboard, and CandidateGraph answers lineage questions. OptimizerContext and optimizer_config feed the optimizer side; chapter five shows them in action.

[8:10–9:30] זה כל מודל האובייקטים בעמוד אחד, עם שמות אמיתיים. קודם כל, שימו לב מה איננו מחלקה. ה-spec הוא dict רגיל ש-specfile.read_yaml מחזיר מ-capevolve.yaml. ה-harness הוא מודול של פונקציות, אין מחלקה בשם Harness. ה-event stream הוא המודול eventstream, שקורא את events.jsonl.

נקרא מלמעלה למטה. cli.py קורא את ה-spec ומריץ את ה-phase skills כ-subprocesses. הם קוראים ל-harness. ה-harness מקבל Candidate כתיקייה תחת candidates, ומפעיל את ה-CapabilityAdapter של הפרויקט: live, run_target, score. ה-adapter מחזיר Rollouts ו-Scores. ה-harness מצרף את ה-Scores ל-SplitResult, שמוגדר ב-loop.py, וכותב הכול דרך RunDir: אירועים, הוצאות, snapshots. ‏VersionStore עושה commit של ה-run directory ל-git. בצד ימין שני קוראים: reduce_run מקרין את הריצה ל-TUI ול-dashboard, ו-CandidateGraph עונה על שאלות של lineage. ‏OptimizerContext ו-optimizer_config מזינים את צד ה-optimizer; בפרק חמש נראה אותם בפעולה.

[9:30–10:30] Every run lives in one folder, .capevolve slash run underscore timestamp. The three files in amber are owned by RunDir. state.json holds the champion id, the budget, the spend, and live reservations. splits.json holds the frozen task partition and the seal flag for the test split. events.jsonl is the append-only audit log.

Then the artifacts. baseline.json has the seed's scores. final.json has the sealed test result and the train and val bookends. candidates holds one snapshot per candidate. rollouts holds one file per task, tag and trial. work holds the optimizer's per-iteration working copies and the round gate tables, and screens holds screening tiers. rejected, history and eval_index are jsonl logs. eval_cache.json exists only for gepa. [10:30–11:30] Each file has a write rule, and the rule is in code, not only in docs. The split is written once. The test seal is two steps: reserve_test checks the seal is unused but does not flip it, and commit_test flips it only after the test result is written. So a finalize that crashes before scoring can be retried. begin_test_attempt adds one more guard: if test rollouts already exist, a second attempt is refused, because the test set was already observed. A real run hit this: a finalize killed by a timeout had scored test, and the retry scored it again. The override is the env var CAPEVOLVE_ALLOW_TEST_RESCORE, and it is disclosed.

freeze_state writes facts like the baseline trial count once; an existing value always wins. Spend updates take an advisory file lock and write atomically with a temp file and os.replace, so a reader never sees a half-written file. Event logs are append-only.

[10:30–11:30] לכל קובץ יש כלל כתיבה, והכלל נמצא בקוד, לא רק במסמכים. ה-split נכתב פעם אחת. חתימת ה-test היא בשני שלבים: reserve_test בודק שהחתימה לא נוצלה אבל לא הופך אותה, ו-commit_test הופך אותה רק אחרי שתוצאת ה-test נכתבה. כך finalize שקרס לפני ה-scoring אפשר להריץ שוב. begin_test_attempt מוסיף עוד הגנה: אם כבר קיימים test rollouts, ניסיון שני נדחה, כי ה-test כבר נצפה. זה קרה בריצה אמיתית: finalize שנהרג ב-timeout כבר דירג את ה-test, וה-retry דירג שוב. העקיפה היא משתנה הסביבה CAPEVOLVE_ALLOW_TEST_RESCORE, והיא נרשמת בגלוי.

‏freeze_state כותב עובדות, כמו מספר ה-trials של ה-baseline, פעם אחת; ערך קיים תמיד מנצח. עדכוני הוצאות לוקחים file lock מייעץ וכותבים בצורה אטומית עם קובץ זמני ו-os.replace, כך שקורא אף פעם לא רואה קובץ חצי כתוב. יומני האירועים רק מתווספים.

[11:30–12:20] state.json has three dataclasses behind it, all in rundir.py. Budget holds the caps from the spec: max iterations, max metric calls, max dollars, the stall limit, a separate optimizer dollar cap, and stop_at_reward. Zero means off. Spent holds counters for three roles: the runner, the optimizer and the intake interview. total_usd adds the three, and that is what max_usd is checked against.

Reservations exist because evaluations can run in parallel. Before a rollout starts, the caller reserves n metric calls. If spent plus reserved plus n would pass the cap, BudgetExhausted is raised before anything is paid. After the evaluation, update_spent converts the claim to spend in the same lock hold, so there is no window where it counts twice. If the process that reserved crashes, its pid is dead and the claim is ignored. budget_exhausted returns a reason string that ends the loop.

[11:30–12:20] מאחורי state.json עומדים שלושה dataclasses, כולם ב-rundir.py. ‏Budget מחזיק את התקרות מה-spec: מקסימום איטרציות, מקסימום metric calls, מקסימום דולרים, גבול ה-stall, תקרת דולרים נפרדת ל-optimizer, ו-stop_at_reward. אפס פירושו כבוי. Spent מחזיק מונים לשלושה תפקידים: ה-runner, ה-optimizer וראיון ה-intake. total_usd מחבר את שלושתם, ומולו בודקים את max_usd.

ההזמנות קיימות כי הערכות יכולות לרוץ במקביל. לפני שמתחיל rollout, הקורא מזמין n metric calls. אם spent ועוד reserved ועוד n יעברו את התקרה, נזרק BudgetExhausted לפני ששילמנו על משהו. אחרי ההערכה, update_spent ממיר את ההזמנה להוצאה באותה החזקה של ה-lock, כך שאין חלון שבו היא נספרת פעמיים. אם התהליך שהזמין קרס, ה-pid שלו מת וההזמנה נזנחת. budget_exhausted מחזיר מחרוזת סיבה שעוצרת את הלולאה.

[13:20–14:20] reduce_run lives in core/cap_evolve/dashboard.py. It takes a RunDir and returns a dict with two keys: graph and summary. [14:20–15:00] Run schema v2 is the contract for new fields. docs/RUN_SCHEMA_V2.md lists them, and schema_v2.py is the only code that knows the enum values and the required keys. Two rules. First, everything is additive and optional, so a version one run renders unchanged. Second, emitters never raise. emit checks required keys and enum values. If one is wrong, it logs a schema_warning event and returns False. Telemetry must never fail an evaluation.

On the reader side, normalize_node fills missing v2 fields from legacy ones. An example from a real run: candidate nine had a val_mean, but it was screen-killed on eight of thirty tasks. So val_mean alone is not proof of a full eval; the node reads as screened. eval_state moves only forward: unevaluated, screened, partial, full.

[14:20–15:00] Run schema v2 הוא החוזה לשדות חדשים. docs/RUN_SCHEMA_V2.md מפרט אותם, ו-schema_v2.py הוא הקוד היחיד שמכיר את ערכי ה-enum ואת המפתחות החובה. שני כללים. ראשית, הכול תוספתי ואופציונלי, כך שריצה בגרסה אחת מוצגת בלי שינוי. שנית, emitters לעולם לא זורקים חריגה. emit בודק מפתחות חובה וערכי enum. אם משהו שגוי, הוא רושם אירוע schema_warning ומחזיר False. טלמטריה לעולם לא אמורה להכשיל הערכה.

[15:00–16:10] graph.jsonl is the candidate DAG. Each line is a node record with id, parents, status, val_mean, and courtesy copies of the screen and gate rows. A node gets a new line at each state transition, and the last record per id wins. The docstring is clear: this is a view. Every field except id, parents and status can be rebuilt from events and the gate tables. record_iteration writes one node for every judged candidate.

CandidateGraph is a read-only query layer. frontier returns active tips: not rejected or superseded, and with no active child. branches returns one root-to-tip path per tip. lineage.py adds ancestors, merge_base, which is the common ancestor with the smallest total distance, and validate, which refuses a self-parent or a cycle. In this picture, cand_3 and cand_4 are tips, and their merge base is cand_1. ParetoArchive is the persistent frontier for multi-objective gating. It holds at most fifteen points by default and evicts the most crowded one.

[15:00–16:10] ‏graph.jsonl הוא ה-DAG של ה-candidates. כל שורה היא רשומת node עם id, ‏parents, ‏status, ‏val_mean, ועותקי נוחות של שורות ה-screen וה-gate. node מקבל שורה חדשה בכל מעבר מצב, והרשומה האחרונה לכל id מנצחת. ה-docstring ברור: זו תצוגה. כל שדה חוץ מ-id, ‏parents ו-status אפשר לבנות מחדש מהאירועים ומטבלאות ה-gate. record_iteration כותב node אחד לכל candidate שנשפט.

‏CandidateGraph הוא שכבת שאילתות לקריאה בלבד. frontier מחזיר את הקצוות הפעילים: לא rejected ולא superseded, ובלי ילד פעיל. branches מחזיר מסלול אחד מהשורש לקצה עבור כל קצה. lineage.py מוסיף את ancestors, את merge_base, שהוא האב המשותף עם המרחק הכולל הקטן ביותר, ואת validate, שמסרב ל-parent עצמי או למעגל. בתמונה, cand_3 ו-cand_4 הם קצוות, וה-merge base שלהם הוא cand_1. ‏ParetoArchive הוא ה-frontier הקבוע ל-gating רב-יעדי. הוא מחזיק לכל היותר חמש עשרה נקודות כברירת מחדל ומוציא את הנקודה הצפופה ביותר.

[16:10–17:00] hash_candidate_dir is a SHA-256 over sorted relative paths and file bytes, skipping the NON_CAPABILITY lists from slide six. Two byte-identical candidates hash the same, even under different ids. Three things use this one value. EvalCache, in cache.py, is a small JSON file keyed by hash and task id. It stores reward, feedback, and a truncated slice of output and trace, never gold. It is used by gepa only; a plain hill-climb never touches it.

The evidence ledger, eval_index.jsonl, is an append-only, rebuildable index of rollouts keyed by the same cap_hash. When you re-measure identical bytes, for example a control copy of the parent, you just get more trials on the same hash. And in schema v2 the graph node field capability_hash is that exact value. Finally, VersionStore. With git, the default, it commits the run directory after every iteration, accepted or not, so git log is the run history. The command store runs a user command, like publishing to a skills store, and fires only for accepted candidates.

[16:10–17:00] ‏hash_candidate_dir הוא SHA-256 על נתיבים יחסיים ממוינים ועל תוכן הקבצים, תוך דילוג על רשימות NON_CAPABILITY משקף שש. שני candidates זהים בבתים מקבלים אותו hash, גם עם מזהים שונים. שלושה דברים משתמשים בערך הזה. EvalCache, ב-cache.py, הוא קובץ JSON קטן עם מפתח של hash ו-task id. הוא שומר reward, ‏feedback, וחתיכה מקוצרת של output ו-trace, אף פעם לא gold. רק gepa משתמש בו; hill-climb רגיל לא נוגע בו.

ה-evidence ledger, ‏eval_index.jsonl, הוא אינדקס של rollouts שרק מוסיפים אליו ואפשר לבנות מחדש, עם מפתח של אותו cap_hash. כשמודדים שוב בתים זהים, למשל עותק control של ה-parent, פשוט מקבלים עוד trials על אותו hash. וב-schema v2 השדה capability_hash של node בגרף הוא בדיוק הערך הזה. לבסוף, VersionStore. עם git, ברירת המחדל, הוא עושה commit ל-run directory אחרי כל איטרציה, מתקבלת או לא, כך ש-git log הוא היסטוריית הריצה. ה-command store מריץ פקודה של המשתמש, למשל פרסום ל-skills store, ומופעל רק ל-candidates שהתקבלו.

[17:00–17:50] There are two kinds of memory. memory.py has two small append-only writers. RejectedMemory writes rejected.jsonl with the reason for every gate reject. History writes history.jsonl for every accepted candidate. The docstring says they are write-only by design: nothing in the core reads them back. The dashboard reads them for its Memory panel.

What the optimizer is told each iteration comes from a MemorySkill. It has three hooks: seed writes the memory files, augment_instructions adds a pointer to the prompt, and write_handover runs after the gate. The default, md-files, writes LEDGER.md, which the framework rebuilds from step events, plus JOURNAL.md, the optimizer's own append-only handover, PROCESS.md, and RUNMAP.md with prior_iterations. The wiki scheme lets the optimizer write weakness and solution cards straight into the run root. All of these file names are in NON_CAPABILITY_FILES, so they never count as capability edits. Chapter seven covers the memory wiki skill in more depth.

[17:00–17:50] יש שני סוגים של זיכרון. ב-memory.py יש שני כותבים קטנים שרק מוסיפים. RejectedMemory כותב את rejected.jsonl עם הסיבה לכל דחייה של ה-gate. ‏History כותב את history.jsonl לכל candidate שהתקבל. ה-docstring אומר שהם לכתיבה בלבד בכוונה: שום דבר ב-core לא קורא אותם בחזרה. ה-dashboard קורא אותם בשביל פאנל ה-Memory.

מה שה-optimizer מקבל בכל איטרציה מגיע מ-MemorySkill. יש לו שלושה hooks: ‏seed כותב את קבצי הזיכרון, augment_instructions מוסיף הפניה ל-prompt, ו-write_handover רץ אחרי ה-gate. ברירת המחדל, md-files, כותבת LEDGER.md, שה-framework בונה מחדש מאירועי step, ועוד JOURNAL.md, יומן ההעברה של ה-optimizer עצמו, PROCESS.md, ו-RUNMAP.md עם prior_iterations. סכמת ה-wiki מאפשרת ל-optimizer לכתוב כרטיסי חולשה ופתרון ישירות לשורש הריצה. כל שמות הקבצים האלה נמצאים ב-NON_CAPABILITY_FILES, ולכן הם אף פעם לא נחשבים שינוי ב-capability. בפרק שבע נרחיב על ה-memory wiki skill.

The wire: JSON over stdout

Payload

SplitResult.to_dict(): reward, stderr, pass_k, per_task, n_scored…

Defense 1

harness sends all adapter output to stderr during run + score

Defense 2

_json_payload tries JSON object starts, newest first

[17:50–18:40] The core and the skills talk through processes. cap-evolve run in cli.py starts each phase skill's scripts/run.py as a subprocess. The script does its work through the harness and prints exactly one JSON object to stdout, for example SplitResult.to_dict for evaluate. That is why every type has to_dict and from_dict: any host, in any language, can parse the result.

The contract breaks if anything else prints to stdout. A real example from the comments: SpreadsheetBench's comparator printed a line on every passing check, and that killed a run right after an eleven-minute baseline. So there are two defenses. The harness wraps run and score in redirect_stdout to stderr. And cli._json_payload, if the whole stdout is not JSON, scans for lines that start an object and decodes the newest one first. One more fact: in the current code, the core reads these payloads as plain dicts. Score.from_dict and Rollout.from_dict are used by tests and one adapter, not by the core path.

[17:50–18:40] ה-core וה-skills מדברים דרך תהליכים. cap-evolve run ב-cli.py מפעיל את scripts/run.py של כל phase skill כ-subprocess. הסקריפט עושה את העבודה דרך ה-harness ומדפיס בדיוק אובייקט JSON אחד ל-stdout, למשל SplitResult.to_dict בשלב evaluate. זו הסיבה שלכל טיפוס יש to_dict ו-from_dict: כל host, בכל שפה, יכול לפרסר את התוצאה.

החוזה נשבר אם משהו אחר מדפיס ל-stdout. דוגמה אמיתית מההערות: ה-comparator של SpreadsheetBench הדפיס שורה בכל בדיקה שעברה, וזה הרג ריצה מיד אחרי baseline של אחת עשרה דקות. לכן יש שתי הגנות. ה-harness עוטף את ה-run וה-score ב-redirect_stdout ל-stderr. ו-cli._json_payload, אם כל ה-stdout אינו JSON, סורק שורות שמתחילות אובייקט ומפענח קודם את החדשה ביותר. עוד עובדה: בקוד הנוכחי ה-core קורא את ה-payloads האלה כ-dicts רגילים. Score.from_dict ו-Rollout.from_dict משמשים בבדיקות וב-adapter אחד, לא במסלול של ה-core.

[18:40–19:25] Three small config modules sit on the optimizer side. optimizer_config.py has one resolver for eight ablation switches. Each switch turns off a newer behavior and falls back to the legacy one. All are on by default except active_eval. The precedence is fixed: an environment variable wins, then optimizer.ablation in the spec, then a legacy top-level ablation table, then the default. A typo raises ValueError, because a typo must not run the wrong experiment. Small note: the docstring of resolve still says seven switches; the table has eight.

optimizer_cost.py meters agent-mode runs. It reads Claude Code's own session logs, prices unseen messages at list price, and remembers which message ids it already counted. pricing.py is a table of list prices, used only as a last resort by the estimate command. And the spec is a plain dict. specfile.read_yaml uses PyYAML if present, else a minimal reader, so the core stays pure stdlib.

[18:40–19:25] בצד ה-optimizer יש שלושה מודולי config קטנים. optimizer_config.py מכיל resolver אחד לשמונה מתגי ablation. כל מתג מכבה התנהגות חדשה וחוזר להתנהגות הישנה. כולם דולקים כברירת מחדל חוץ מ-active_eval. סדר העדיפויות קבוע: משתנה סביבה מנצח, אחריו optimizer.ablation ב-spec, אחריו טבלת ablation ישנה ברמה העליונה, ואז ברירת המחדל. שגיאת כתיב זורקת ValueError, כי שגיאת כתיב לא אמורה להריץ ניסוי לא נכון. הערה קטנה: ה-docstring של resolve עדיין אומר שבעה מתגים; בטבלה יש שמונה.

‏optimizer_cost.py מודד עלות בריצות agent mode. הוא קורא את יומני הסשן של Claude Code עצמו, מתמחר הודעות שעוד לא נספרו לפי מחיר מחירון, וזוכר אילו מזהי הודעות כבר ספר. pricing.py הוא טבלת מחירים, שמשמשת רק כמוצא אחרון בפקודת estimate. וה-spec הוא dict רגיל. specfile.read_yaml משתמש ב-PyYAML אם הוא מותקן, ואחרת בקורא מינימלי, כך שה-core נשאר stdlib טהור.

Key takeaways

  • Four types: Task, Rollout, Score, Candidate
  • Score clamps to 0..1; one primary metric
  • Adapter: 3 required, 5 defaulted, 3 hasattr fast paths
  • Infra error = missing data, never a zero
  • One ignore list feeds hash, gepa and diff
  • events.jsonl is the truth; state.json is a cache
  • reduce_run feeds both TUI and dashboard
  • graph.jsonl is a view; last record wins
  • Content hash keys every cache and ledger
  • Phases speak one JSON object on stdout

[19:25–20:00] Let me sum up. There are four shared types, and Score protects the statistics. The adapter has three required methods, five hooks with defaults, and three fast paths found by hasattr. An infrastructure failure is missing data. One ignore list decides what counts as the capability.

On disk, events.jsonl is the source of truth, and state.json is a derived cache with locked, atomic writes. reduce_run is the single projection for the terminal and the web. The graph is a view. The content hash keys the caches and the evidence ledger. And phases talk to the CLI with one JSON object on stdout.
