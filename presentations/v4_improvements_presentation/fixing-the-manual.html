A bare ID isn’t a failed message

cloud-024-guid-to-account

Before20% → After100%
The test request — the entire message, verbatim

“jbfsq”

Nothing else attached. No verb, no question mark. (“w4t8r” is the token used in the fix’s own worked example, not the graded message — see the next slide.)

The problem

Someone pastes a raw account ID with nothing else attached — no question, no verb. The coordinator had no rule for that shape of message, so it fell back on its generic manners and asked for clarification instead of just looking the ID up.

The fix

A new rule was added stating that a message made of one identifier-shaped token, on its own, is a routine lookup request — and gave it the exact steps to resolve it, no question asked.

orchestrator.md — new section
+## Bare Identifiers and Minimal Prompts
+A message whose entire content is one identifier-shaped
+token, with no verb and no question, is a routine request
+— not a failed or truncated message.
+
+Never answer such a message with “I didn’t catch
+that.”
Followed by a lookup table mapping ID shapes (5-char code, 12-digit number, email) to the right tool to call.

The fetch tool doesn’t read folders

platform-007-directory-path-fetch

Before47% → After100%
The request, per the skill’s own worked example

“The workload roles live under ansible/roles_ocp_workloads — find the task file for the ocp4_workload_etherpad role and report what it configures.”

You’re told where the role lives, not which file inside it — that gap is exactly what the agent guessed its way through.

The problem

The tool’s own description claimed it could fetch “files and directories.” It can’t — it reads exactly one file. The instructions then modeled calling it on a folder path, so the agent kept trying to open a folder like a document, and failing.

The fix

The tool description was corrected, and the wrong example was replaced with the right two-step move: search the repo for the real path first, then fetch that exact file.

aap2_agent.md — tool description
−Fetch file or directory contents from a GitHub repo
+Fetch one file’s contents by its complete file path.
+It is a read tool, not a discovery tool: give it a path
+you already have, never a directory and never a path
+you inferred from convention.
aap2_agent.md — worked example
−fetch_github_file(owner, repo, "setup-automation/")
+search_github_repo(owner, repo, "setup-automation")
+fetch_github_file(owner, repo, "<path from matches>")
A new example was also added showing four wrong calls from real past runs, each labeled with why it fails.

Four rules, one contradiction

platform-004-events-then-config

Before79% → After100%
The request, per the skill’s own worked example

“Why did job 11111 on the west controller fail?”

A direct job ID, GUID lookup skipped — exactly the shortcut that made the missing step invisible. (The graded trial itself asks about job 90405 on the east controller; job 11111 / west is the fix’s own worked example.)

The problem

Three rules said “don’t call the same job twice.” One buried rule needed a second call — the failed-events check — right after reading the log. The agent followed the majority and quietly skipped the step that mattered.

The fix

The “no repeat calls” rule was narrowed to only ban an identical repeat, and a new rule spells out exactly when the second call is required.

aap2_agent.md — narrowing the old rule
−Don’t re-fetch job data. Do NOT make a redundant
−second call to the same job.
+Reuse values you already hold — but a different
+action is not a re-fetch. A call is redundant only
+when it repeats the same action with the same
+arguments.
aap2_agent.md — new Critical Rule 5
+A failed job needs the log AND the failed events.
+Call get_job_events(failed_only=true) after
+get_job_log, before any GitHub fetch. Do the events
+call even when the log looks self-explanatory.
shared_context.md’s matching rule was reworded the same way, so the files stopped disagreeing.

Long doesn’t mean timeout

platform-008-log-does-not-say

Before80% → After100%
The request — this task’s question shape

“Why did this job fail?”

The real job’s log simply stops: no error line, no PLAY RECAP, zero failed events. There is nothing in the evidence to name as a cause. (Job 90408 on the west controller, in the graded trial.)

The problem

A rule of thumb told the agent: if something ran a long time before failing, call it a timeout. So it guessed a cause from the clock instead of checking whether the log actually said so.

The fix

The shortcut was removed, and a whole new check was added asking whether the evidence actually establishes a cause — before the agent is allowed to name one.

aap2_agent.md — removing the shortcut
−Timing — how long did the failing operation take?
−Short = auth/config error. Long = timeout.
+Timing narrows the candidates — on its own it is
+never the cause.
aap2_agent.md — new Step 7a
+Does the evidence actually establish a cause?
+A log that simply stops is not evidence of a cause.
+A long elapsed time, a round duration, or a wait/poll
+task as the last line does not establish a timeout.
+Naming one anyway is the single most common way this
+report goes wrong.
The same “don’t guess, say so” instruction, plus a template for reporting an unestablished cause, was echoed in shared_context.md and orchestrator.md.

Closingx

None of these four is a case of the agent getting smarter.
