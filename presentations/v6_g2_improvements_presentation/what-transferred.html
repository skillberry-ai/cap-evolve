Skill audit · v6 G2 held‑out armi

Diagnostic report · cand_0005 vs. seed · sealed test split

What transferred

The first parsec run where the gate read only tasks the optimizer never saw, and the result was then scored once on 66 sealed test tasks. The final bundle, cand_0005, raised test reward from 0.813 to 0.850 (paired 95% CI +0.011 to +0.065). This deck asks which edits produced that, using the test trials themselves rather than the optimizer’s own claims. The two edits that transferred were not about any task. They repair how the agent handles its environment: a call that never answered, and tools that are listed but never served. It also reports what did not work: one task the bundle broke, and one acceptance the gate got wrong.

What the simulator returns when a call times out — verbatim

“query_aap2 did not respond within 240s. The simulated service accepted the request and never answered; treat this as the tool being unavailable rather than as a result.”

Fixed text, any tool. Nothing was measured — a second attempt usually succeeds.

The problem

The seed told every specialist never to repeat a call with the same parameters. That rule forbade the one action that recovers from a timeout. So a timed‑out call ended the investigation, and the agent reported the gap or asked the user to retry.

What changed on the test tasks

Over the valid test trials, the seed made 6 repeat calls after 160 timeouts. cand_0005 made 108 after 152. On trials that hit at least one timeout, reward rose from 0.651 to 0.733; on trials that hit none, from 0.845 to 0.875.

−**NEVER call the same tool with the same
−parameters twice in a conversation.**
shared_context.md — cand_0005
+**A call that NEVER ANSWERED has not been tried
+yet — re-issue it once.** Two failures look
+similar and need opposite responses:
+- No answer at all → re-issue that one call once,
+ as your next call. Use this ONLY when the result
+ literally says the service *did not respond within*
+ some number of seconds.
+- The service ANSWERED → do not re-issue it.
+ An empty result, not found, a validation error,
+ a 429, or "not modelled" all mean it DID respond.
+- At most one re-issue per call, and none once two
+ calls have already failed to answer.
+- Make the re-issue yourself. Do not close by
+ telling the user to retry the query.
Condensed from the full rule; the wording is the bundle’s own. The “answered” branch matters as much as the retry: an early draft retried real errors too, and the optimizer narrowed it after a review caught that.

The manual made dead tools mandatory

harness property · affects any task that names a sandbox

What the simulator returns for these tools — verbatim

“query_provisions_db is not modelled by the simulation. The benchmark excludes it deliberately; the question should be answerable from the identifiers you were given.”

Every call to these tools gets this reply. They never succeed.

The problem

The seed made two of these tools a required first step: describe a table before any query, and check the provisions database whenever a sandbox is named. Six more places told the agent to fall back on the same route. Every such call wasted a round.

What changed on the test tasks

Calls to unmodeled tools fell from 137 to 48 over the valid test trials. In the seed, nine trials opened with one. The optimizer also had to remove all six standing contradictions: one leftover instruction elsewhere cancels the edit.

The test request — verbatim, abridged

“…on the Babylon cluster merlin. The portal shows the lab as green, but their workbenches can’t get any accelerators. …tell me which part, what state it’s in, and which AAP2 job I should open.”

What happened

cand_0005 added a true statement about the simulator: listing subjects by identifier “resolves without a cluster.” So on this task the agent dropped the cluster argument. The task’s reward contract requires that exact call with cluster: merlin, so its tool‑call score fell to 0. The agent also stopped before opening the job the user asked about.

Bundle or contract?

The rule is right for the simulator, and the contract is strict about an argument the simulator doesn’t need. Which one should change needs domain review. Either way, this task loses 0.395, past the paper’s 0.20 per‑task deployability limit.

What happened

Before judging a candidate, the gate re‑measures the champion: four trials on each of the 67 hidden tasks, run as four batches. In cand_0002’s round, the seed’s first batch scored about half its normal level. On 47 of its 65 tasks it fell more than 0.3 below the same task’s other three batches. The trials completed and returned verifier output, so the infrastructure check did not reject them.

What it changed

Averaging that batch in lowered the seed’s baseline, so cand_0002 looked far better than it was. A full re‑measurement after the run agrees there was no gain: cand_0002 scored 0.804, the seed 0.821.

Why it still matters

cand_0005 was built on cand_0002 — 93% of the lines cand_0002 added are still in it. The test result compares cand_0005 with the seed directly, so it stands. What cannot be known is whether cand_0005 would have been found if cand_0002 had been rejected.

What this means06

Recap

The edits that transferred repaired the environment, not the tasks

What transferred

Two harness repairs: retry a call that never answered, and stop calling tools that are never served. Neither mentions a task. The optimizer chose them for that reason: it ranked edits by whether the mechanism lived in the simulator, since such a mechanism must also be present in tasks it could not see.

What their value depends on

Both fixes repair the agent’s handling of the simulator. How much they help in production depends on how often real services time out and how many listed tools are actually unavailable there.

What did not work

One rule that is true of the simulator broke a task whose reward contract asks for more (platform‑131, −0.395). And one acceptance came from a bad baseline batch, which the infrastructure check could not catch, because the trials completed.

For the gate

A statistical gate is only as sound as the baseline it averages. A baseline batch that disagrees this sharply with other batches of the same bundle should be re‑measured before it enters a decision.

Test split: 66 tasks, 10 trials per task, scored once. Seed 0.813 → cand_0005 0.850, paired 95% CI +0.011 to +0.065. On the 52 tasks never used in v4 the gain is +0.032, CI +0.001 to +0.065. One optimizer seed; no further runs of this arm are planned. Full record: results/v6/v6_g2_e1/ on the parsec-history branch.
