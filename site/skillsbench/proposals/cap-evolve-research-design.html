What should the paper claim?

Working title: Optimizing Agent Capabilities: An Empirical Study of Granularity, Edit Surfaces, and Feedback.

Claim to earn: under a fixed model and measured compute budget, the useful optimization unit and editing surface depend on the type of failure and the evidence available. The contribution is a reproducible explanation of these dependencies.

Do not claim âfirst agents optimizing agents,â âfirst multi-file skills,â âfirst regression-aware search,â or a universally superior optimizer. Even component interaction and feedback-rich repair have close prior art. This review supports a candidate gap, not a proof of novelty.

Most promising focal result: test whether executable repairs need more implementation-specific feedback, while task-local specialization increasingly loses value when merged into a shared artifact. This is a hypothesis; an equally informative outcome is that the apparent effect disappears once budgets and task families are controlled.

Before committing to a large run, require one informative pilot: a stable treatment difference, a replicated null that overturns a common assumption, or a measured failure mechanism. A collection of three unrelated sweeps will be weaker than one explanation supported by all three axes.

Exact experiment protocol
  1. Freeze the initial artifact, target model, optimizer model, runtime, objective, selection rule and total spend cap. Choose one editable-surface anchor before comparing granularity.
  2. Partition training families into groups; derive group descriptors from baseline training traces only. Freeze groups for the primary experiment. G3 matches G4âs number and size of groups.
  3. Allocate a fixed total budget across local branches, reserve a predeclared fraction for merging, and report unused budget. Suggested starting reserve: 20%, selected during a disjoint pilot.
  4. Allow local search against branch tasks. A branch artifact remains a specialist until it passes the shared integration/selection protocol. Do not reject every local gain using a global gate before testing composition.
  5. Merge with the same algorithm and proposer across G2âG4. Run frozen interface checks, then evaluate a task-balanced selection set covering every group. Reject or repair within the same reserve.
  6. Evaluate each final shared artifact on unseen instances and unseen families. If merging fails, the deployed outcome is the last valid shared artifact; report the failure and its cost.

Two exposure checks: first compare equal total dollars, which answers the practical question. Then compare a smaller matched-exposure subset with equal optimizer token allowance, candidate count and rollout count. These are separate estimands, not three constraints that can generally be satisfied simultaneously.

Long traces: give G0 a searchable filesystem rather than silently truncating it. In a secondary contrast, compare direct packing, summary-plus-drill-down and filesystem access with the same evidence-read token budget.

What is a merge, and how should it be measured?

A merge combines behavior, not just non-conflicting file lines. Test three integration mechanisms on the same frozen branch outputs:

A routed specialist library is a separate deployment arm. Charge routing errors, router cost and library size; the router may see only normal task inputs. An oracle that chooses the best specialist after seeing its outcome is a diagnostic ceiling, never a deployable result.

Track compile/interface conflicts, behavioral conflicts without textual overlap, eliminated branch improvements, net new regressions, and integration spend. Predeclare the merge order and repeat alternate orders for a small subset.

Metrics and falsifiable hypotheses

Primary: final held-out mean reward under the common cost cap. Secondary: reliability, success-versus-spend curves on development data, merge success rate, regression mass and deployment cost.

H1: grouping helps most when shared failure mechanisms recur across tasks. Test G4 â G3; if this contrast vanishes, the advantage may be batching rather than useful clustering.

H2: independent task optimization achieves higher local fit but loses more of that gain during integration. Test both local and merged artifacts on a task-balanced audit set.

H3: task-specific gains transfer less to unseen families than to unseen instances of known families. Test the interaction between granularity and split type, with uncertainty.

Useful extension: compare grouping by task-text similarity, shared tool dependencies and diagnostic failure patterns. If only one grouping helps, identify the operational signal rather than announcing âclustering works.â

Why hill climbing is a reasonable backbone

Use it. Greedy parent selection with rollback is transparent, inexpensive to implement and easy to keep constant while varying experimental factors. It gives a clean operational question: what helps a fixed optimizer produce useful edits?

Its limits are real: it discards stepping stones, can lose specialists, is path-dependent and selects on noisy estimates. Keep the proposal model and mutation instructions fixed, rerun parent and candidate in matched evaluation blocks, and preserve rejected candidates for analysis. Do not infer that a rejected edit has negative true value.

Add an unchanged-artifact repeated-evaluation control and a one-shot-edit control. Repeat the main contrasts with upstream GEPA or a simple archived-candidate search, using compatible edit permissions. If the ranking changes, report an optimizer interaction rather than claiming algorithm-independent rules.

GEPA explicitly motivates preserving complementary candidates; AgentOptimizer predates cap-evolveâs rollback design. [10][28]

Two complementary experiments: search-space utility and mechanism equivalence

E2a Â· Randomized allowed-surface study

Assign identical starting agents to one allowed-edit surface. Keep proposal evidence, search budget, initialization, inference limits and selector fixed. Optimize independently over repeated chains. This estimates the effect of allowing optimization on that surface, including the optimizerâs ability to use it.

Use the same frozen registration/loader scaffolding in every arm. Description-only cannot quietly change schemas; script-only cannot rewrite SKILL.md beyond a frozen invocation scaffold. In a full package arm, record every embedded text and code change rather than counting the package as text.

E2b Â· Matched repair mechanisms

Select approximately 10â20 training-derived failure mechanisms during a disjoint pilot. Examples: reading current state before a write, preserving spreadsheet formulas, validating a date, or checking that an output artifact exists. Implement each mechanism as (a) prompt guidance, (b) a tool description where applicable, and (c) executable enforcement where applicable.

Have reviewers verify equivalent intended behavior and information access, without seeing test outcomes. Do not force equivalence where it is impossible: a mandatory wrapper cannot always be reproduced by optional prose. That difference in enforceability is itself a treatment dimension.

Apply the matched repairs without another optimization loop and run them on unseen cases. This estimates the effect of the implementation location for a specified repair, separate from which repairs an optimizer happened to discover.

Record invocation, guard activation, blocked correct actions, tool-call count and final task success. A mechanism that never executes cannot explain a gain without additional evidence.

Tool-code boundary: keep the task itself unchanged

Benchmark tools often implement the simulated world. Editing those functions can change what counts as a valid operation and make the task easier. For the primary study, keep the simulator and its canonical API immutable. Optimize an agent-side adapter around that API.

For a genuine white-box experiment, define an owned helper implementation whose external contract is fixed, and test it against a trusted reference on valid and invalid inputs. If changing the core service implementation is the scientific question, label that a separate environment-design study.

Tool removal means changing the agentâs exposed action set; it must not remove a task requirement. Composite tools must not bypass confirmation, skip required user interaction, or gain direct state access unavailable to primitive calls. Count their internal calls when measuring efficiency.

Preserve the distinction between useful new helper logic and benchmark-specific answer lookup. A script that fixes a general format problem is a candidate capability; a table of task IDs and correct outputs is memorization.

Continuous reward: use a frozen fraction of satisfied requirements or verified subgoals on tasks where partial credit is meaningful. Do not turn one Bernoulli outcome into a fake continuous score. Text critique: use a frozen evaluator model/template that receives the same visible task evidence and allowed rubric. Structure it as step, observation, violated rule, likely cause, suggested repair. Core measurement and statistical protocol
  1. Freeze study definitions: task families/splits, primary contrasts, evaluator, endpoint, exclusion rules, budgets, model snapshots and inference caps. Pilot tasks must not become final test tasks.
  2. Treat search data as training: any score, trace, accept/reject response or cluster statistic used to update artifacts belongs to adaptive development. A selector can use a separate selection set, but repeated selection still adapts to it.
  3. Replicate optimization: use three independent chains for screening and aim for at least five for confirmatory contrasts when feasible. Vary optimizer seed/session, not just execution seed. These are starting allocations, not a power guarantee.
  4. Replicate execution: pilot with three trials per task, then increase trials where variance obscures the predeclared effect size. Reset files, databases, caches and agent memory. Interleave parent/candidate or treatment/control runs to reduce temporal/provider drift.
  5. Pair comparisons: use identical tasks, environment initialization and compatible seeds. Seed equality does not guarantee identical model randomness after a prompt/code edit.
  6. Keep the denominator: task-caused timeouts and malformed outputs count under the native failure rule. Infrastructure failures get the same predeclared retry policy for every arm, a missingness count and sensitivity analysis.
  7. Final evaluation: precommit all artifacts and variants, then score them on sealed test tasks as one analysis batch. Neither the optimizer nor study decisions receive these outcomes during search. Report every predeclared arm, not a test-selected winner.

Uncertainty: report paired effect estimates with 95% intervals. For unseen-family claims, resample families as the highest task unit, then tasks/trials within family; account for independent optimization chains. Report chain variability separately and use a model appropriate to crossed chains and tasks where sample size permits. With few families, show family-level effects and explicitly broad uncertainty.

Multiplicity: name a small set of primary contrasts and correct that family of tests, e.g. Holm. Treat the rest as exploratory. A per-candidate kÂ·SE acceptance threshold is not a study-wide significance guarantee.

How the ML analogy worksâand where it stops

The train/selection/test distinction applies because candidate artifacts are fitted using task evidence. Overfitting means an improvement on adaptive search data fails to transfer to the target task distribution. The learned object is a discrete program-and-text artifact, rather than a weight vector.

A local edit can change future observations, tool choices and paths, so identical seeds do not guarantee identical trajectories.

The objective is still expected reward. What changes is the appropriate replication, causal attribution and intervention boundary. Do not claim smoothness, unbiased gradients or convergence merely because a textual update resembles gradient descent.

LLM agents can be improved by changing the external artifacts that govern their behavior, including prompts, tool interfaces, executable helpers and skill packages. Existing methods demonstrate substantial gains, but differ in their editing permissions, feedback and evaluation protocols, making it difficult to determine which design choices account for those gains. We propose a controlled empirical study of three factors: the unit of optimization, the editable capability surface and the evidence available to the optimizer. Using cap-evolve as a common experimental substrate, we compare shared and local optimization, matched repair mechanisms across artifact types, and feedback ranging from observed traces to verified reference executions. The evaluation separates local fit, merge retention, unseen-task generalization, execution reliability and total optimization cost. The intended contribution is a reproducible characterization of when agent-driven capability optimization produces reusable improvements and when it introduces specialization or collateral regressions.
