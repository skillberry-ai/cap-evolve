Harbor integration

Optimize agent capabilities with cap-evolve using Harbor for sandboxed benchmark execution — any agent, any benchmark, any environment (Docker, OpenShift, or cloud).

Why Harbor + cap-evolve

cap-evolve is eval-agnostic — it only needs a list of tasks and a deterministic score for each. Harbor provides robust sandboxed execution for benchmark trials in isolated containers. Together:

  • Safety: Benchmarks like Terminal-Bench and SWE-bench give agents full machine access. Harbor keeps these safely isolated in containers so the agent cannot wreck your host during optimization.
  • Scale: Harbor natively supports horizontal scaling (hundreds of concurrent trials). This cuts down the time cap-evolve needs per optimization epoch.
  • Honest evaluation: cap-evolve enforces strict val/test splits and a sealed test scored once — preventing the agent from memorizing the benchmark Harbor is running.

Architecture

cap-evolve optimization loop
  │
  │  1. Intake & Modify (cap-evolve)
  │     └─ diagnose failures → optimizer edits prompt/tools/skills
  │
  │  2. Execute (Harbor)
  │     └─ harbor run -d <dataset> -a <agent> -m <model> -e openshift
  │           ├─ pod 1: task-001 → agent runs with edited skill → verifier → reward
  │           ├─ pod 2: task-002 → agent runs with edited skill → verifier → reward
  │           └─ pod N: task-N   → ...
  │
  │  3. Verify (Harbor)
  │     └─ verifier scripts score each task → reward.json per trial
  │
  │  4. Learn & Commit (cap-evolve)
  │     └─ adapter reads Harbor's job results → gate (accept/reject)
  │           if accepted: commit the edit, new best
  │
  └── repeat until stall or budget exhausted
      then: finalize on sealed test split → one honest number

How it works

  1. cap-evolve proposes an edit — modifies the agent's prompts, tools, or skills in the working directory based on failed execution traces.
  2. The adapter invokes Harbor — runs the full benchmark (harbor run -d <dataset> -a <agent> -e openshift) with the newly modified capabilities. Harbor spins up isolated containers/pods, one per task.
  3. Harbor executes and verifies — each task pod runs the agent, then the verifier script scores the result and writes reward.json.
  4. The adapter reads Harbor's results — parses the job directory, extracts per-task rewards and trajectories, returns scores to cap-evolve.
  5. cap-evolve gates the edit — if the new capability beats the baseline by a statistically significant margin on the val split, it commits the edit.

Reference implementations: agent-eval-harness (Harbor workflow on OpenShift) and coding_agent_bench (SWE-bench with Harbor on OpenShift).

Prerequisites

  • Harbor CLI (≥ 0.20): uv tool install harbor
  • Local: Docker or Podman running
  • OpenShift: oc login + RBAC (see below)
  • A Harbor dataset (e.g. swe-bench/swe-bench-verified, terminal-bench@2.0)
  • Agent credentials (API key, Vertex AI ADC, or on-cluster vLLM)

Quick start

The generic pattern — substitute your agent, model, dataset, and environment:

# 1. Install
uv tool install harbor
pip install ./core ./capevolve_harbor

# 2. Set up the project
cap-evolve init
cp -r templates/adapters/harbor/* .capevolve/project/adapters/

# 3. Configure — pick your agent, dataset, and model
export HARBOR_DATASET=<org/dataset>          # e.g. swe-bench/swe-bench-verified
export HARBOR_AGENT=<agent>                   # e.g. claude-code, codex, opencode
export HARBOR_MODEL=<model>                   # e.g. claude-sonnet-4-6, gpt-4.1
export HARBOR_TASK_IDS=<task1,task2,...>       # tasks to optimize on
export HARBOR_TASK_PREFIX=<dataset-org>       # e.g. swe-bench

# 4. Run — locally with Docker, or on OpenShift
cap-evolve check .capevolve/project
cap-evolve run --spec .capevolve/project/capevolve.yaml

Running on OpenShift

Harbor's -e openshift runs each task as a pod on your cluster. Images are built remotely via OpenShift Binary Builds — no local Docker needed. You can serve models on-cluster with vLLM for a fully self-contained setup.

harbor run -d <dataset> -a <agent> -m <model> -e openshift -n 5 \
  --ae <KEY>=<VALUE> ...

Full OpenShift guide — vLLM model serving, RBAC setup, SCC configuration, agent credentials (vLLM / Vertex AI / API keys), and the cap-evolve optimization loop on-cluster.

Agent credential reference

Any agent in Harbor's agent zoo works. Pass credentials into the task pod via --ae KEY=VALUE flags. Below are the common agents with the exact flags needed.

Claude Code (Anthropic API)

harbor run -d <dataset> -a claude-code -m claude-sonnet-4-6 -e openshift \
  --ae ANTHROPIC_API_KEY=sk-ant-...

Claude Code (Vertex AI)

Bind-mount GCP credentials into the task pod via --mounts-json.

harbor run -d <dataset> -a claude-code -m claude-sonnet-4-6 -e openshift \
  --ae CLAUDE_CODE_USE_VERTEX=1 \
  --ae CLOUD_ML_REGION=<region> \
  --ae ANTHROPIC_VERTEX_PROJECT_ID=<gcp-project> \
  --ae ANTHROPIC_MODEL=claude-sonnet-4-6 \
  --ae GOOGLE_APPLICATION_CREDENTIALS=/app/.config/gcloud/adc.json \
  --mounts-json '[{"type":"bind","source":"~/.config/gcloud/application_default_credentials.json","target":"/app/.config/gcloud/adc.json"}]'

Claude Code (on-cluster vLLM)

Point claude-code at a vLLM-served model — no external API keys needed.

harbor run -d <dataset> -a claude-code -m <model-name> -e openshift \
  --ae ANTHROPIC_BASE_URL=http://<vllm-svc>.<namespace>.svc:8000 \
  --ae ANTHROPIC_API_KEY=dummy \
  --ae ANTHROPIC_MODEL=<model-name> \
  --ae ANTHROPIC_DEFAULT_SONNET_MODEL=<model-name> \
  --ae ANTHROPIC_DEFAULT_HAIKU_MODEL=<model-name> \
  --ae ANTHROPIC_DEFAULT_OPUS_MODEL=<model-name>

Codex (OpenAI)

harbor run -d <dataset> -a codex -m <model> -e openshift \
  --ae OPENAI_API_KEY=sk-...

Gemini CLI

harbor run -d <dataset> -a gemini-cli -m <model> -e openshift \
  --ae GEMINI_API_KEY=...

OpenCode (any OpenAI-compatible provider)

harbor run -d <dataset> -a opencode -m <model> -e openshift \

Oracle (no LLM — for testing the pipeline)

harbor run -d <dataset> -a oracle -e openshift -l 1

Any Harbor registry dataset or local dataset in Harbor task format works. Browse available datasets with harbor dataset list.

To select specific tasks from a dataset, use -i <task-name> (repeatable) or -l <count> to limit the total. In cap-evolve, set HARBOR_TASK_IDS.

The adapter

The bridge between cap-evolve and Harbor is a small Python adapter that fulfills the cap-evolve adapter contract — just tasks() and score():

  • tasks(split) — returns task IDs from the Harbor dataset
  • run_batch(tasks, ctx) — invokes harbor run -d <dataset> -a <agent> -e <env> as a single benchmark run, returns results
  • score(task, rollout) — reads Harbor's reward.json from the job directory and returns the score to cap-evolve

The capevolve_harbor package provides the reusable utilities:

ModulePurpose
capevolve_harbor.runInvoke harbor run via subprocess with signal forwarding
capevolve_harbor.resultsParse Harbor job directories → per-task rewards, trajectories, cost
capevolve_harbor.tasksGenerate Harbor task packages from cap-evolve tasks (optional)

Debugging

Keep the container or pod alive after a trial to inspect logs and state:

# Keep task pods alive after the trial
harbor run ... --no-delete

# Inspect the task pod (OpenShift)
oc get pods -l harbor-role=task
oc logs <pod>
oc exec -it <pod> -- /bin/sh

Harbor captures transcripts in the job directory:

jobs/<job-name>/<trial>/
  agent/trajectory.json      # agent execution trace
  agent/claude-code.txt      # raw agent stream
  verifier/reward.json       # verifier score
  verifier/test-stdout.txt   # verifier output

Only 1 task in rolloutsSet HARBOR_TASK_PREFIX to match the dataset org
