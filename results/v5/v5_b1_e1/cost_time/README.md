# results/v5/v5_b1_e1/cost_time/ — the baseline arm's per-task cost and time

Cost/token/wall-clock accounting for **`v5_b1_e1`** (the original unmodified parsec skill,
zero-shot, 5 trials/task, no optimization) across all 136 v5 tasks.

Unlike [`../../../v4/v4_t_e1/cost_time/`](../../../v4/v4_t_e1/cost_time/) — which vendors a table
produced upstream in the intake worktree and *parses it back* into `results.json` — v5 has no such
upstream script in this branch. Here `../results.json` is the single source of truth and
[`v5_b1_e1_results_table.md`](v5_b1_e1_results_table.md) is a human-readable rendering of it,
generated by
[`scripts/build_v5_b1_cost_time_table.py`](../../../../scripts/build_v5_b1_cost_time_table.py).
The dependency runs one way only, so the table cannot drift from the ledger.

## What's in the `.md`

One row per task: the 5 individual trial rewards, mean and stderr, **`spread`** (max − min) and
**`sd`**, errored-trial count, a `saturated`/`ok` headroom tag, and that task's total
cost/tokens/seconds.

`spread` and `sd` are not in v4's equivalent table. They are here because characterising how
stochastic this benchmark is was part of this arm's job: 92 of 136 tasks return a different reward
across identical repeated trials, and a table of means alone would hide that.

## Where the numbers end up

- `../results.json` — `task_ledger[].cost_usd` / `tokens` / `seconds`, same values, same source.
- `../summary.md` — the headline and cost sections.
- `../../../../ui/heatmap_v5_b1_e1.html` and `../../../../ui/trials_v5_b1_e1.html`.
- `../../../../reports/v5/v5_b1_e1/*.md` — each task's auto block.

## Caveat this table carries forward

Each row's cost/tokens/seconds is a **sum across that task's 5 trials**, and the sweep ran at
10-way concurrency on CCC/LSF. The summed "task time" at the top (48.8h) is therefore a
cost/budget figure, not a schedule figure — actual elapsed wall-clock was roughly 9h.
