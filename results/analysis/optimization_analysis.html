SkillsBench on CCC — task-by-task-43 delivers +36.3 pp average lift (updated 2026-08-23)

Update 2026-08-23 — task-by-task-43 complete across ALL 43 runnable SkillsBench tasks. Each task got its OWN cap-evolve process with its OWN shipped skills as seed. 10 trials per candidate, up to 4 iterations, dedicated LSF host per task, Sonnet-5 agent + Opus-4.8 optimizer.

Result: avg baseline 0.508 → avg best 0.871 (+0.363, +36.3 pp) across 43 tasks. 27 of 43 tasks reach val=1.0 (63%). Compared to whole-suite runnable-43 with the office quartet seed (baseline 0.140 → best 0.170, +3.1 pp), task-native seed delivers ~12× the aggregate lift.

Prior analysis: whole-suite runnable-43 — from broken plumbing to a real +3.11 pp

Analysis of three SkillsBench runs conducted on IBM CCC's rootless-podman environment: the 10-task shared-office pilot (baseline-10task), the ill-fated 87-task attempt (all87-broken-wiring, used to derive a runnable subset), and one cap-evolve optimization on the 43-task RUNNABLE subset (runnable-43task-opt, aka run_runnable_iter7_v1). Headline finding — the environment side of the pilot is solved. Thirteen layered podman workarounds (rootless single-UID user namespace, patched ubuntu base image, ignore_chown_errors, private dbus, host network, exec-tar upload/download replacements, root sandbox user) got a 43-task subset running end-to-end. Cap-evolve then produced a real +3.11 pp gain over 2 accepted iterations — meaningful signal, correct paired-SE gate behavior (rejected iter 3, accepted iters 1–2), and a clear open question about which specific edits regressed 3 control-simulation tasks. The optimization loop works; the remaining ceiling is overwhelmingly a task-domain-coverage problem, not plumbing.
The elephant in the room — 32 of 43 tasks scored exactly 0.000 across seed, cand_0001, cand_0002, and cand_0003. That's the ceiling of whole-suite optimization on this task set: only 21 of the 87 SkillsBench tasks actually ship any of our 4 seed office skills (docx/pptx/xlsx/pdf), and BenchFlow strips the task's own skills at rollout time. No amount of SKILL.md optimization will lift the 32 tasks whose domain (kernel fuzzing, hydrology, PDE solvers, financial modeling) is structurally absent from the seed. The +3.11 pp came almost entirely from ~9 tasks moving; see Section 3.

1 · Phase evolution — three environments on partly overlapping task sets

Each row is a phase: how much task coverage BenchFlow's infrastructure could sustain, what agent/optimizer model pair ran, and what the resulting val reward was. Note the task sets are DIFFERENT sizes — comparisons across phases below are limited to the intersection of tasks that actually ran.

What the columns mean

  • baseline-10task — first run that reached completion. 10 tasks hand-picked to be shared-office-only (docx/pptx/xlsx/pdf domain). Sonnet 4.6 as agent, no optimizer. 3-trial val, 3 dummy test. Purpose was to prove the podman workarounds were sufficient; result was 1/7 val tasks passing (invoice-fraud-detection at 3/3). Not a headline number — just proof of plumbing.
  • all87-broken-wiring — expanded the adapter's TASK_IDS from 10 to all 87 tasks. Seed rollout revealed two new infrastructure-error classes: network_mode: host in the compose base conflicted with 14 tasks' networks: block, and 26 tasks use a python:3.12-slim base image where our chown/dpkg wrappers don't apply. Plus 4 exotic base images. Total 44 tasks unfixable in the current setup. Killed once the 11% infra-error rate was clear, but not before recording which 43 tasks DID run cleanly — that recording became the split_ids.runnable.json used by the next phase.
  • runnable-43task-opt — the main event. 43 known-runnable tasks, cheaper Sonnet 5 as agent, Opus 4.8 as optimizer. algorithm=hill-climb, gate=paired, gate_k_se=0.2, num_trials=3, max_iterations=7. Ran seed + iters 1–3 cleanly; iter 4 optimizer process wedged (no file writes, no token growth for 1h 49min); killed under pre-agreed 90-min-stall rule.
Why no cross-phase per-task table like parsec-results had? — Because the task intersections are near-empty. baseline-10task's 7 val tasks are all in runnable-43's 43, but the agent model changed (Sonnet 4.6 → Sonnet 5) so they aren't a clean plumbing-vs-plumbing comparison. And all87-broken-wiring was killed at baseline — its seed rollouts on the 43 runnable tasks are dominated by Sonnet-4.6 vs Sonnet-5 model drift, not environment drift. Per-task story lives in Section 2 (all inside runnable-43task-opt).

3 · Why 34 tasks are stuck at 0.000 — a domain-coverage problem, not a plumbing problem

32 of 43 tasks scored exactly zero across the seed and all 3 candidates. This is NOT because the seed skill package is bad. It's because BenchFlow's default behavior on SkillsBench is to strip the task's own environment/skills/ and mount only the seed's skills/ instead. The task verifier then evaluates against outcomes the task designer expected the task-specific skills to enable.

The seed ships 4 office skills: docx, pptx, xlsx, pdf. Only 21 of 87 SkillsBench tasks ship at least one of those. The other 66 tasks have domains our seed can't help with:

The whole-suite story in one number — cap-evolve moved the in-domain (office quartet, 9 tasks) subset from 0.11 → 0.44, a real +33 pp gain where the seed had traction. It moved the whole 43-task set from 0.14 → 0.17, a +3 pp gain dragged down by 32 OOD zeros. That +33 pp on the in-domain slice is the more honest headline — and it's the direct argument for switching to task-by-task optimization (Section 5).

4 · What the optimizer got right — and what needs the next attempt

Wins the candidates demonstrated — edit-pdf lifted from 0/3 to 3/3 across cand_0001 → cand_0002. court-form-filling from 0/3 to 2/3 (cand_0001) and briefly 3/3 (cand_0003). 3d-scan-calc and syzkaller-ppdev-syzlang from 2/3 to 3/3. Two moderate wins on cross-domain tasks (multilingual-video-dubbing, flood-risk-analysis) suggesting the optimizer's general-purpose SKILL.md guidance (not just office-skill specifics) did some work. Six tasks moved in the right direction across the accepted 2 iters, with rationale traceable in the candidates' SKILL.md diffs.
The 3 control-simulation regressions — adaptive-cruise-control, hvac-control, r2r-mpc-control were all 3/3 at the seed and all dropped to 1/3 or 2/3 by cand_0002. All three ship domain-specific control skills (PID, MPC, state-space linearization, safety interlocks) — the seed's office-skill focus doesn't help them, but on the seed the base Sonnet-5 agent handled them well without extra guidance. When cap-evolve added office-doc emphasis to SKILL.md, the added guidance apparently competed for the agent's attention on control tasks. This is the exact "one edit that hurt" pattern parsec-results saw on task 004: an optimization helped in-domain tasks but had collateral damage on adjacent-but-different tasks.

The optimization loop is healthy

  • Real signal on in-domain tasks: cap-evolve identified edit-pdf's 0/3-baseline as fixable and did fix it to 3/3. That's the strongest single-task lift observed.
  • Correct gate behavior: iters 1 and 2 accepted with clean paired-Δ > k·SE margins. Iter 3 rejected with a slightly-negative Δ where individual regressions outweighed a cand_0003 win on court-form-filling. Not too permissive.
  • Cost profile: ~$15 optimizer per iter on Opus 4.8 for a 43-task hill-climb. Well within the max_optimizer_usd=400 spec cap.
  • Failure mode observed: iter 4 optimizer process appears to have wedged on an Anthropic API HTTP request that never terminated (via ETE LiteLLM). Bench containers were quiet the whole hang window; not a task-side failure. Investigation before --resume is recommended.

5 · Recommended next moves

Ordered from smallest change to biggest. Each is config-only unless noted:

  1. Narrow the whole-suite run to the office-quartet-only tasks (~21 of 87, ~9 of runnable-43). Filter split_ids.runnable.json to the tasks that ship docx/pptx/xlsx/pdf. Expected baseline: much higher than 0.1395 (probably 0.4–0.5) because everything's in-domain. Expected best-cand: 0.6+ on the same +33-pp-per-in-domain-task trajectory. This matches parsec-intake's 10-task setup and is the fastest way to a clean, defensible headline number. Same optimizer + agent + spec. Wall clock ~5–6h.
  2. Investigate the iter-4 optimizer hang before --resume. Suspect the Anthropic API path via ETE LiteLLM. Without fixing, the same hang may repeat at iter 5. A minimal check: run the optimizer's claude CLI invocation in isolation with tracing on to see if the HTTP request completes.
  3. --resume from cand_0002 for iters 5–7. Rename the KILLED dir back to run_runnable_iter7_v1/, resubmit with --resume. This tests whether the remaining 3 iterations can push above 0.17 given the current trajectory. Cost ~$45 optimizer + ~10h Sonnet-5 rollouts. Risk: if the iter-4 hang recurs, wasted spend.
  4. Switch to task-by-task optimization (EvoSkills-style). One skill per task, seeded from the task's own environment/skills/. Requires either 43 separate cap-evolve launches (LSF fan-out) or a new per-task-hill-climb algorithm inside cap-evolve. Directly comparable to EvoSkills' 71.1% headline (though only on our 43-task runnable subset). This is the biggest-lift option and the one SKILLSBENCH_INVENTORY.md was written to support.
  5. Or accept +3.11 pp as the terminal deliverable for the whole-suite pilot and freeze runnable-43task-opt/ as a reference. The environment is healthy, the loop is functional, and the ceiling is a documented domain-coverage issue — not something more iterations will fix.
