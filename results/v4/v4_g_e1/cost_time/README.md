# results/v4/v4_g_e1/cost_time/ -- G2's per-iteration cost and time

The cost/token/wall-clock accounting for **G2** (global-scope, shared-bundle hill-climb,
`v4_g2_e1`), covering all 6 completed iterations of its single evolving bundle (evaluated across all
34 tasks every iteration) plus its baseline.

- [`v4_g2_e1_results_table.md`](v4_g2_e1_results_table.md) -- hand-built from the run's own
  `events.jsonl`/`state.json` (see the table's header for exact paths). Unlike T2's cost_time table,
  this one is **not** generated by a script -- there are only 8 rows (baseline, seed, cand_0001-6,
  plus the incomplete cand_0007), so it wasn't worth building a parser for. If G2 is re-run with more
  iterations, or a second G-arm variant is added, consider promoting this to a
  `scripts/v4_g2_e1/collect_cost_time.py` analogous to T4's.

## What's different from T2's per-task table

T2 (`results/v4/v4_t_e1/cost_time/`) has one row per *task* because it runs an independent optimizer
loop per task. G2 evolves **one shared bundle across all 34 tasks at once** -- so there is no
per-task or per-tranche cost split at this grain: every row is a full 170-rollout (34 tasks x 5
trials) sweep over the same candidate, plus the optimizer's cost to propose it from its parent. The
table has a single Summary section (one row per iteration), not a Summary + Per-iteration-detail
pair -- for G2 those are the same thing.

## Where the numbers end up

- `results/v4/v4_g_e1/summary.md` -- the "Cost + wall clock" narrative section.
- Not yet wired into `results/v4/v4_g_e1/results.json` (no generator script exists; that file was
  hand-assembled). If one is written later, it should read this table the way
  `scripts/build_v4_t_results_json.py`'s `parse_cost_time_source()` reads T2's.

## Caveats this table carries (see the table's own footnotes for detail)

1. Runner `cost_usd`/`tokens` are `0.0`/`0` for `baseline/seed`, `cand_0001`, and `cand_0002` --
   a metering/instrumentation gap, not a true zero cost (later candidates show substantial nonzero
   cost/tokens for the same eval size). The eval-cost total in the table is a **floor**.
2. `cand_0007`'s optimizer cost/tokens/time are inferred by subtraction (state.json cumulative minus
   the six logged `step` events), not read directly -- the run stopped mid-proposal before a `step`
   event was written for it, and its eval never started scoring.
3. A `FINAL` test-split eval was started once (after `cand_0003`) and never completed
   (`splits.json`'s `test_used: false` confirms this) -- the run's process was restarted twice while
   resuming from state (three `run_config` pairs in `events.jsonl`), and this FINAL attempt fell in
   one of those gaps.
