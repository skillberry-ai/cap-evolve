What the optimizer added — a diff view

77 lines added to the seed aap2_agent.md. Three self-contained groups, each targeting a specific failure mode:

1 · Always emit a report
  the report — not more narration.
+ If tools do not return everything you
  wanted, PRODUCE THE REPORT ANYWAY
  with what you have — a partial report
  is worth far more than silence.
  Every specific job ID the user asked
  about MUST appear verbatim in the
  final report.
targets: agent ends its turn without emitting a message
2 · Budget rounds — no sweep
  ...report with some gaps.
+ Hard cap: no more than 2 rounds
  of query_aap2 calls before you MUST
  either advance to lookup_catalog_item
  / fetch_github_file, or write the
  report. Do NOT loop back to
  query_aap2 after GitHub fetches.
targets: combinatorial sweep of query_aap2
3 · Recovery Protocol (new section)
+ ### Recovery — get_job_log not-found
  Round 1: get_job_log(east) for all IDs
  Round 2: find_jobs on east AND west
    (one parallel batch)
  Round 3: lookup_catalog_item →
    fetch_github_file → analysis
  Never sweep controllers with the
  same missing IDs.
targets: dead-end retry across controllers when a job ID isn't found
Semantically coherent additions — the optimizer read the failure trace, identified the three failure modes, and proposed a structured fix for each.
why the aggregate didn't move

We fixed one failure — and stopped some successes

The seed's rewards are bimodal: agent either fully succeeds (reward = 1.0, gold trajectory matched) or fully fails (reward = 0.0, no report emitted). Cand_0001 flattens the distribution: always produces a report, always at ≈ 0.35. Same average, different shape — but the trade is currently a net loss.

where the fix HELPS
Trials where seed would have timed out (reward = 0.0). Cand_0001 forces a partial report — job IDs verbatim, some answer substrings match.
0.00  →  ~0.35
gain per rescued trial: +0.35
where the fix HURTS
Trials where seed would have succeeded fully (reward = 1.0). The new Recovery Protocol steers the agent AWAY from the gold trajectory — even when the agent could have followed it.
1.00  →  ~0.35
cost per broken success: −0.65
the aggregate arithmetic
On the N=30 mix (roughly half seed-wins, half seed-losses), the +0.35 gains don't outweigh the −0.65 costs.
seed 0.317  →  cand_0001 0.225
observed net: −0.09
what a well-tuned fix would look like
Make the PIVOT to find_jobs conditional — trigger it only when get_job_log genuinely returns nothing useful, otherwise follow the successful gold flow. Keep the wins, rescue the losses. Estimated headroom: ~+0.15 above seed (i.e., 0.32 → ~0.47) — and that's what the second optimization attempt is aiming for.

what this tells us
Parsec's aap2_agent.md (from PR #40's SDK migration) is already tuned on these 2 tasks. The optimizer's proposed additions (“always emit final report”, “budget your rounds”, “no controller sweep”) over-constrain the agent and hurt reward — two independent proposals, both regressed.
what this tells us about the setup
• Framework works end-to-end at N=30. Paired-SE gate correctly rejected both regressions.
• N=10 is too few on gate-stochastic tasks — an earlier N=10 pilot on the same 2 tasks measured seed val = 0.017 (95% gate=0). Same SKILL.md, unstable window.
• Real headroom is elsewhere: the 25 multi-tool v1 tasks (mean 0.142), the tool-side error rates, and composite tools — not further prompt tweaks on aap2-0047/0048.

v2 · the honest read

Numbers up — but the SKILL.md is now tuned to the scorer, not to the user

The optimizer worked as designed — it found edits that lift the reward. But those edits trade real diagnostic value for scoring artifacts.

Task 001 · get_job beats get_job_log
Scorer expected get_job (bare metadata). Seed used get_job_log (full diagnostic). Seed's answer more useful; candidate's higher-scoring.
SKILL.md now prefers bare metadata on questions where the log is what the user needs
Task 003 · verbatim quote demanded
Same tools, same info. Seed described the error in its own words. Candidate quotes "line 4 column 18" verbatim — the exact required substring.
rewards precise mimicry of gold wording, not clarity
Task 009 · specific “not found” phrasing
Same 2-tool trajectory. Candidate adds "job 91999 does not exist on controller prod0" verbatim — wording rigged to the assertion string.
rewards wording-match, not reasoning
the real finding — ground truth quality is the OTHER lever
Rubrica extracted these tasks from traces. Its expected.json encoded specific tool names + verbatim substrings that don't fully capture what “good” means. cap-evolve then correctly adapted the SKILL.md to match. Score ↑ · agent quality ↓. Rubrica's task extraction needs a human-review step for tool choice and answer substrings — before the optimizer runs.

One RH-owned win · two joint pilots to validate

Compressible patterns fall into two categories: tool ergonomics fixes (RH ships independently) and composite tools (jointly-piloted, need task-review support).

RH-owned · ship anytime
1. Tool ergonomics fix
query_babylon_catalog errors on 43% of 44 calls (cluster ambiguity). query_aap2 errors on 17% of 122 calls. Both force re-plans that inflate the loop before any skill change matters.
ask: default-cluster inference or an explicit "which cluster?" affordance — no IBM in the loop
joint pilot proposal
2. debug_aap2_job() — mini-skill
query_aap2 → lookup_catalog_item → fetch_github_file recurs in 21 traces. Argument keys drift, so this reads as a mini-skill not a fixed-signature tool.
ask: RH review of expected.json for pilot tasks first — then joint validation
joint pilot proposal
3. provisions_db batching
In ocpv: query_provisions_db → db_describe_table → query_provisions_db has stable arg keys — cleanest fixed-signature composite candidate.
ask: does the pattern still hold on SDK-path traces? Small sub-agent, easy pilot
caveats to state explicitly
Directional findings from 130 legacy traces (2 pod identities, 29 days) · PR #40's SDK path will shift some patterns · task-quality review (v2 lesson) is a prerequisite before optimizing against composites.

Takeaways & next steps

what the pilots taught us, and where we could go from here
what we learned

Four takeaways from the pilots

1
The framework works end-to-end. Loop closes cleanly, statistics resolve at N=9–30, gate accepts / rejects with defensible math.
2
Data quality dominates. v1's unreachable gold trajectory and v2's scorer-gaming both trace back to how tasks were compiled — not to the optimizer itself.
3
Ground truth needs a human review step. Rubrica's extraction is a strong starting point; RH domain review is the missing loop closure.
4
Tool ergonomics is a parallel lever. The 43% query_babylon_catalog error rate is a real, RH-owned win that doesn't wait on us.
