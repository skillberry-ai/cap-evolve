\section{Core Code Owns Every Decision an Optimizer Could Game}
\label{sec:v2:evaluation}

An optimizer that can read the answers, the scorer or the final set can look better than it is, and one that scores itself will bank noise. \capevolve{} therefore moves every such decision into core code that the optimizer cannot edit. Splits are seeded, written once and read back by every skill. The final split is sealed: the run directory raises an error on a second access, and finalization scores the returned candidate and the seed on the same final tasks exactly once. Plugin hooks, which live in core-owned scripts and not in editable skill text, deny edits to the sealed test and gold files and block a session from finishing until the adapter check and the gate are green.

Gold isolation has two layers. The adapter gives the target agent a gold-free copy of the task data and scores against the pristine copy. The proposer, a coding-agent subprocess with shell access, is isolated by running it under a separate user id or in a mount namespace, and a negative test must show denial before launch. The library does not sandbox the proposer itself, so this is a deployment requirement, and a hash manifest over the evaluation surface can detect tampering after the fact but cannot stop a read. Section~\ref{sec:v2:setup} states what was isolated for each arm.

The shipped acceptance rule, which we call the stock gate, is a paired test: accept a candidate when the mean per-task improvement over the current best exceeds $k$ standard errors of the paired differences, computed on the selection split only, with $k=1$. The hill-climb gate first sets to zero the tasks whose rollouts never touch the edited files (the edit's footprint), and agent-optimize judges with a $z$-test that has a standard-error floor. About half of all no-op edits measure as a small improvement by chance, so a gate at zero banks noise, and a one-standard-error gate still promotes a no-op candidate in a large share of ten-candidate searches (Figure~\ref{fig:v2:rulep}).

Rule P is the conservative alternative. It is a switch that is off by default and has two stages. A candidate first passes a screen on the full, unmasked difference vector at $k=1$. It is then confirmed by re-evaluating candidate and incumbent on the same selection tasks with $n_{\mathrm{conf}}$ new trials per task, with aligned seeds, and is promoted only if the confirmation improvement is large relative to its standard error ($z_{\mathrm{conf}}$) and enough tasks are covered ($\rho$). The confirmation, not the screen, becomes the next baseline, which removes the selection bias from the reference that later candidates must beat. We froze $n_{\mathrm{conf}}=3$, $z_{\mathrm{conf}}=1.282$, no minimum improvement and $\rho=0.95$ from a budget-exact simulation of one search per suite (Appendix~\ref{app:sim}); Algorithm~\ref{alg:P} gives the rule. In an all-null search of about ten candidates it promotes something falsely with probability \simPFalseA{} on Suite A, \simPFalseB{} on B and \simPFalseC{} on C, against \simKoneFalseA{}, \simKoneFalseB{} and \simKoneFalseC{} for the one-stage gate. It pays in power: a candidate with a true 8-point gain is promoted with probability \simPPowerEightA{}, \simPPowerEightB{} and \simPPowerEightC{}, against \simKonePowerEightA{}, \simKonePowerEightB{} and \simKonePowerEightC{}. Confirmation costs $2\,|D_{\mathrm{sel}}|\,n_{\mathrm{conf}}$ rollouts per screened candidate, charged to the budget. Rule P does not control adaptivity over the task set: the selection tasks also feed the proposer, so a candidate can overfit them and pass both stages. Only the sealed final set removes that bias, and only to the degree it was not reused.

Three further checks guard the measurement. A trial that errors because of the candidate scores zero, while an infrastructure error is retried and, if it persists, handled by one rule for every arm (Section~\ref{sec:v2:setup}). The gate refuses to judge when too few tasks are valid on both sides of the pair. Null-edit controls and injected scorer and adapter faults test all of this. \needs{E04 null-edit false-accept rates and the E05 and E06 fault-injection outcomes (15 pass, 7 partial, 6 gap, 1 info at last count), with the gaps stated.}

We also used these checks to audit our own history. An earlier \capevolve{} draft reported gains of \histGemmaDeltaSaved{} (Gemma-4-31B) and \histGptDeltaSaved{} points (GPT-5.5) on SpreadsheetBench. Recomputed, scorer compliance explains \histGemmaComplianceShare{}\% and \histGptComplianceShare{}\% of them, the test split had been scored in development, and optimizer sessions had read gold files (Appendix~\ref{app:hist}). That audit is the reason the measurement is code-owned.
