\section{Introduction}
\label{sec:v2:intro}

Agents run on frozen models, and their behavior is set by the files around the model: the system prompt, tool code, the tool list exposed over MCP, and skill packages \citep{agent_skills_docs}. Optimizers edit these files and report large gains \citep{skillopt,meta-harness}. Published methods span prompt and pipeline optimization \citep{dspy,miprov2-dspy,gepa}, skills \citep{skillopt,evoskill,trace2skill,wikiskill}, context playbooks \citep{ace} and harness search \citep{meta-harness,xu2026harnesslens}. Section~\ref{sec:related} places them by the surface each edits.

Two gaps limit these methods. First, each fixes the object it edits, usually the prompt, so a failure that lives elsewhere is out of reach: a rule the model knows but ignores needs tool code the model cannot skip, and a skipped routine needs a bundled script. Second, acceptance is self-scored. In simulation, a one-standard-error gate that ignores edit footprints promotes a no-op candidate in \simKoneFalseB{} to \simKoneFalseA{} of ten-candidate searches under trial noise (Appendix~\ref{app:sim}), and an optimizer that can read gold or the scorer can look better than it is. An audit of an earlier version of our own optimizer shows the cost: it reported a Gemma-4-31B gain of \histGemmaDeltaSaved{} points on SpreadsheetBench, and scorer compliance explains \histGemmaComplianceShare{}\% of it (\histGptComplianceShare{}\% for GPT-5.5; Appendix~\ref{app:hist}).

\capevolve{} addresses both gaps (Figure~\ref{fig:v2:loop}). The editable surface is a parameter of one loop over four capability types (Section~\ref{sec:v2:surface}). Every decision an optimizer could game moves into core code it cannot edit (Section~\ref{sec:v2:evaluation}). The optimizer receives a fixed/broke history of which tasks each earlier edit fixed and broke (Section~\ref{sec:v2:context}), and the loop runs as a deterministic hill-climb or as a coding agent that drives the same gate (Section~\ref{sec:v2:modes}). We implement four surfaces, prompt, tool code, MCP tool descriptions and skill packages, and evaluate prompt and tool code.

We evaluate on SpreadsheetBench (Suite A) and $\tau^2$-bench retail (B) and airline (C), plus a retail ablation family (D), with Claude Sonnet 5.5 as the optimizer for every matched arm. Section~\ref{sec:v2:setup} gives the protocol: a matched rollout checkpoint, adapted versions of nine published optimizers (eight run from their official code), and paired statistics with an equivalence rule. The design resolves differences of about 11 to 15 points between frozen artifacts, so results are descriptive estimates with intervals, and smaller gaps are inconclusive. \pend{[RESULT: per-suite estimates for the three CapEvolve configurations against the seed; one-sentence ablation findings.]}

Our contributions are:
\begin{enumerate}[leftmargin=*,nosep]
\item The editable surface as a parameter, with per-surface edit policies (Section~\ref{sec:v2:surface}).
\item Code-owned evaluation: gold isolation, a gate, and a final set scored once, with a two-stage rule whose operating characteristics we simulate (Section~\ref{sec:v2:evaluation}).
\item Two orchestration modes over one gate, and a fixed/broke history for the optimizer, ablated on Suite D (Sections~\ref{sec:v2:modes} and~\ref{sec:v2:context}).
\item An agentic intake with a hard adapter gate (Section~\ref{sec:v2:intake}).
\item A controlled protocol and descriptive estimates for the comparison and ablations (Section~\ref{sec:v2:results}). \pend{[RESULT: one line per ablation.]}
\end{enumerate}
