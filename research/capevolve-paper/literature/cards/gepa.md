- Editable surface: text prompts (instructions) of each LLM module in a compound AI system (Pi_Phi); LLM weights fixed for GEPA. Also (preliminary, Sec 5.1) a code-generation prompt for NPU/CUDA kernel writing. No tool code, MCP descriptions or multi-file skills.
- Search method: Alg.1 (p.6). Split D_train into D_feedback and D_pareto (|D_pareto| = n_pareto). Candidate pool P (full archive with parent pointers A, a genealogy tree) + score matrix S[k][i] of every candidate on every D_pareto task. Each iteration: (1) SelectCandidate via Pareto (Alg.2): per-task best score, keep candidates that are best on >=1 task, drop dominated, sample with prob proportional to number of tasks led; (2) pick one module round-robin; (3) sample minibatch (b=3) from D_feedback; (4) run candidate with feedback function mu_f (scalar + textual eval trace, e.g. compiler errors / failed constraints); (5) reflection LM rewrites that module's prompt from (current prompt, trajectories, score, feedback) (meta-prompt App. C p.22); (6) evaluate child on the same minibatch; only if score improved is it evaluated on all of D_pareto and added to pool. Returns candidate with best mean D_pareto score. Memory = lineage in prompts (each child inherits parent's accumulated lessons); no cross-iteration textual notebook beyond the prompt.
- Feedback signal: scalar metric plus module-level textual feedback from the evaluator (mu_f), plus execution traces (reasoning, tool calls). Paper reports feedback functions per benchmark (App. E.1 p.23-25), e.g. remaining gold docs to retrieve for HotpotQA/HoVer, satisfied/failed constraints for IFBench, quality and PII-leak breakdown for PUPA. Math tasks use a single-step CoT (little textual feedback).
- Task splits / held-out protocol: standard train/val/test (p.8). "Direct access to the content of validation instances is restricted" yet val scores drive Pareto selection (D_pareto = val set, p.27). Test never used for selection; final = best val aggregate. Sizes (App. E.1 pp.23-25): HotpotQA 150/300/300; IFBench 150/300/294 (IF-RLVR train split into train/val, IFBench as test); HoVer 150/300/300; PUPA 111/111/221; AIME-2025: train 45 + val 45 (AIME 2022-24 = 90 questions split equally), test = AIME-2025 30 questions each repeated 5x (150); LiveBench-Math (retrieved 2025-07-30) n=368 shuffled with seed 0 and split equally into train/val/test.
- Benchmarks (with versions) and models: HotpotQA, IFBench, HoVer, PUPA, AIME-2025, LiveBench-Math (6 tasks); Qwen3-8B (temp 0.6, top-p 0.95, top-k 20) and GPT-4.1 mini (openai/gpt-4.1-mini-2025-04-14, temp 1.0), 16384 context (p.25). Extra: NPUEval + KernelBench with GPT-4o (35 KernelBench tasks), adversarial prompt search with GPT-5 Mini (Sec 5.2).
- Metrics: task accuracy / F1 / pass rate / recall as per benchmark (mu in [0,1]); aggregate = mean over benchmarks; fastp, vector utilization for kernels.

- Reported limitations (authors' own): no dedicated limitations section. Table 3 (p.10) selection ablation on 4 tasks, Qwen3-8B (aggregate 48.84 baseline): SelectBestCandidate +6.05, BeamSearch(N=4) +5.11, Pareto GEPA +12.44. IFBench 678 rollouts -> 38.61 vs GRPO 35.88 @24000 (Table 1 caption). Single runs: no seeds/CIs reported in tables (not found).
- Candidate-evaluation allocation: two-stage. Cheap gate: child evaluated on the 3-task reflection minibatch (also the reflection data); only if better than parent on that minibatch does it get a FULL D_pareto evaluation. No racing/successive halving/posterior; paper itself flags full-val tracking as the main inefficiency (p.9).
- Task selection / curriculum: reflection minibatches are random draws (epoch-shuffled sampler in released code; paper says "stochastically sampled minibatch"). Pareto frontier is per-task and drives parent choice, i.e. task-wise diversity not task curriculum.
- Merge/composition: System-Aware Merge (App. D.1, Alg.3-4, p.24): pick two Pareto candidates i,j with common ancestor a, neither an ancestor of the other, S[a] <= min(S[i],S[j]), pair not tried before, and they changed disjoint module prompts; child copies module prompts from whichever descendant changed them (ties by higher score). Max 5 merge invocations per run (p.27). Merged child is evaluated like any candidate (so verified on D_pareto) but no separate verification. Merge helped GPT-4.1 mini (+1.1 aggregate) but hurt Qwen3-8B (-2.45, IFBench 28.23 vs 38.61).
- Optimizer self-modification: none; reflection meta-prompt fixed.
- Overlap with CapEvolve: very high for the GEPA reimplementation and for hill-climb vs GEPA comparison: reflective trajectory-based edits, candidate DAG with ancestry, per-task score vectors, Pareto parent selection, merge of complementary lineages, minibatch pre-screen then full val, rollout-budget accounting, sealed test.
- What it means for our claims: (a) any claim that "candidate DAG + merge + per-task evidence" is novel is unsafe; GEPA already has all three in prompt space. (b) Our allocation claim must be vs GEPA at matched TOTAL rollouts including val rollouts and reflection LM tokens, since GEPA's budget is mostly val. (c) GEPA fixes minibatch size 3 and round-robin module choice; CapEvolve's difference must be in surface breadth (tool code, MCP descriptions, skills), agent-driven allocation (Bayesian per-task posterior, subset triage) and gating (paired mean(delta) > k*SE vs GEPA's minibatch strict improvement). (d) GEPA reports single runs; we should report seeds. Reproduction feasibility: HIGH for GEPA itself (open MIT code, small benchmarks, rollouts budgets listed), MED for a faithful CapEvolve-adapter port since GEPA's selection depends on val-set per-task scores and full val sizes (111-300).
