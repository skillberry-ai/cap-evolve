- Editable surface: one skill artifact per task, a graph-structured natural-language document <h_s, g_s> = global guidance + nodes (execution steps with instructions) + workflows (applicability condition + ordered node path) (Sec 3.1 p.3-4); validated by a graph-schema script (App B.3). Single-file text skill, not multi-file packages, tools or MCP.
- Search method: population-based EA, population N=4, T=5 generations (p.7). Each generation: sample 15 train instances, run every skill, retain <=5 failed trajectories per skill; generate N new skills by round-robin among 4 operators (global-guidance mutation, graph-structure mutation, global-guidance crossover, graph-structure crossover); parent selection p proportional to 1/(rank+N); evaluate each child on the FULL val set; keep top-N of parents+children by val fitness (Sec 3.2 p.5-6). Archive = current population only (no lineage DAG beyond that). Memory: failed trajectories per generation.
- Feedback signal: binary task success per instance (r=0 defines failures), execution trajectories for mutation; crossover uses no trajectories.
- Task splits / held-out protocol (App B.2 Table 6 p.15): train/val/test SearchQA 400/200/1400; SpreadsheetBench 80/40/280; DocVQA 107/53/374; LiveMath 35/18/124; ALFWorld 39/18/134; deterministic split seed 42 shared with SkillOpt baseline; test only for final report; val used for selection. Main results are means of 3 repeated optimization runs (p.7); significance appendix uses 5 runs.
- Benchmarks and models: SearchQA, SpreadsheetBench, DocVQA, LiveMathematicianBench, ALFWorld; GPT-5.4 and GPT-5.4-nano (medium effort; same model executes tasks and optimizes), no harness and Codex harness (ALFWorld excluded for Codex). (Model names as stated.)
- Metrics: test success rate (exact match / workbook match / pass within limit), %.
- Budget / cost reporting: YES, optimization tokens (Table 2 p.8): total GPT-5.4 SkillOpt 81.08M vs GraphSkillEvo 61.94M; GPT-5.4-nano 103.54M vs 75.94M (SkillOpt 1.31x / 1.36x). Per benchmark it is mixed, e.g. ALFWorld 25.26M vs 32.53M, LiveMath 2.86M vs 3.50M, DocVQA(GPT-5.4) 3.69M vs 4.56M. Hyper-parameters are not matched (SkillOpt: 4 epochs, rollout batch 40, edit budget 4->2 cosine, slow update, meta-skill memory; D.1 p.17); budget matching is by reporting total tokens, not equal rollouts. Fig 3 p.8 plots val score vs tokens for 3 benchmarks.
- Reported limitations (authors' own): none stated explicitly in a limitations section; future work lists merging graph skills across domains and richer composition (p.10). Significance (App C.1 p.17, GPT-5.4-nano, 5 runs, one-sided Welch): Spreadsheet p=0.016, ALFWorld p=0.038, SearchQA p=0.069, DocVQA p=0.089 (LiveMath not reported).
- Key quantitative results: Table 1 p.7 (test avg): GPT-5.4 no-harness 75.86 vs SkillOpt 74.10 (+1.76); GPT-5.4-nano 60.90 vs 56.89 (+4.01); GPT-5.4 Codex harness 78.28 vs 76.95 (+1.33); best in 13 of 14 settings (LiveMath/nano SkillOpt 29.56 vs 28.76). Per-benchmark nano: Spreadsheet 60.71 vs 50.11 (+10.60), ALFWorld 61.19 vs 57.46 (+3.73). Table 3 p.8 graph vs unstructured counterpart (same skills, nano): -4.52/-2.50/-4.19/-1.35/-0.75. Table 4 p.9 ablation (nano; SearchQA, Spreadsheet, DocVQA avg 71.52): w/o graph 64.08, w/o mutation 54.50, w/o crossover 66.59. Table 5 p.9 cross-model transfer nano->GPT-5.4 SpreadsheetBench 71.78 (SkillOpt transferred 53.21).
- Candidate-evaluation allocation: every candidate (all N=4 children per generation) gets a full validation evaluation (fitness = J_Dval); training batch (15 instances) is used only to generate failures. No subset triage, racing or bandit. Selection pressure on tiny val sets (18-200 items) with up to 24 full-val evaluations per run (4 initial + 4x5 children) -> winner's-curse risk, not addressed beyond reporting means over 3-5 runs.
- Task selection / curriculum: random 15-instance train minibatch per generation; failed trajectories (<=5) per skill; no curriculum.
- Merge/composition (verified?): YES, crossover merges nodes/edges from one parent with global guidance from another (or vice versa) via an LLM; child is checked by the graph-schema validator, then evaluated on full val and kept only if in top-N fitness (so merges are verified by full-val fitness selection, not per-merge paired tests). Ablation shows crossover worth -4.93 avg when removed (Table 4). Not merged: tools/prompts/code.
- Optimizer self-modification: none (fixed operator prompts, App E).
- Overlap with CapEvolve: skill-package optimization (SkillOpt comparison), population + crossover vs our single-lineage hill-climb and merge in agent-optimize, validation-fitness selection, token reporting. Review correctly notes that the "graph" is inside the skill, not a search DAG.
- What it means for our claims: a population with merge operator beat the single-lineage SkillOpt by 1.8-4.0 pts avg in this paper, so "branching/merge is useful" has external support but only vs SkillOpt under unequal hyper-parameters; we need our own matched-token comparison (hill-climb vs agent-optimize vs population/crossover) and variance over repeated optimization runs. Its val sets are very small (18-53 items on 3 of 5 benchmarks) and still used for 20+ selections - a held-out/winner's-curse concern that our paired gate and sealed test address. Reproduction feasibility: high for a re-implementation (algorithm and hyperparameters fully specified; repo public but UNLICENSED, so reimplement, do not vendor).
