# Mixture of Self-Improving Branches
- Exact title: Mixture of Self-Improving Branches for Agent Harness Optimization (PDF running title "Mixture of Self-Improving Branches For Agent Harness Optimization"; arXiv API title identical)
- Authors: Haoyu Dong, Yuhang Zhou, Zihao Lin, Yifan Wu, Bo Peng, Mingyi Wang, Xiangjun Fan, Lizhu Zhang, Zhuokai Zhao (Meta; Duke; UC Davis) [PDF p.1; arXiv API]

- Code URL + license + endpoint note: none found in PDF or via arXiv page; license n/a; endpoint compatibility unverified

- Editable surface: harness code (Meta-Harness-style Python programs) plus per-branch proposal guidance in SKILL.md (p.4). Router instruction also optimized (GEPA).
- Search method: B=2 parallel Meta-Harness-like branches, N=20 iterations, one new harness per branch per iteration, proposer Claude Opus 4.6 (coding agent reading a per-branch filesystem of code/scores/traces). Archive = per-branch candidate population + traces. Selection = branch head = top mean reward on that branch's CURRENT dev subset. Branch frontier F = top-q (q=5). Every C_p=1 iterations dev subsets are pruned; every C_s=5 iterations each branch's guidance S is rewritten by the proposer from local history (Alg.1 p.5, setup p.6).
- Feedback signal: per-case binary/scalar task reward on the dev subset + execution traces.
- Task splits / held-out protocol (p.6): Math (Meta-Harness retrieval math) 250 dev / 200 held-out IMO-level; Terminal-Bench 2.0: random 30 dev / 58 test of 88; SWE-bench Lite: random 50 dev / 250 test of 300. Harness selection and router configuration use dev data only ("solely on development data", abstract); test never used for selection in the headline numbers. Table 4 p.9 separately reports test-BEST (selection on test) over 10 harnesses as a reference, labelled retrospective.
- Benchmarks and models: Olympiad-level math (Gemini 3 Flash; Claude Sonnet 4.5 actors), Terminal-Bench 2.0 (Sonnet 4.5), SWE-bench Lite (Sonnet 4.5). Baselines: no-memory, few-shot, BM25, Terminus 2, Terminus-KIRA, mini-swe-agent, Meta-Harness.
- Metrics: held-out accuracy / pass rate / resolve rate (%).
- Budget / cost reporting: partial. Appendix A Table 5 p.13 gives full-run tokens (millions): Math 79.92 (MH) vs 172.90 (ours) total, task-solving 11.10 vs 13.40; TB2.0 2,366.80 vs 4,001.39; SWE-Lite 1,907.17 vs 2,951.48. Task-solving tokens are 1.21x/1.71x/1.50x Meta-Harness (p.12), i.e. NOT matched; authors concede "unequal total token usage" (p.9). No $ or wall-clock.
- Reported limitations (authors' own): unequal total token usage and limited repeated evaluations constrain efficiency/reliability conclusions; router slightly below stronger head in two settings; ablations do not establish each trajectory change caused its test gain (p.9-10).
- Key quantitative results: Table 1 p.6 held-out: Math/Gemini 62.0 vs Meta-Harness 46.0 (+34.8% rel); Math/Sonnet 30.5 vs 29.0 (+5.2% rel); TB2.0 50.0 vs 44.8 (+11.6% rel); SWE-Lite 66.0 vs 63.6 (+3.8% rel). Table 2 p.8: Head1/Head2/Router: Math-Gemini 56.0/58.0/62.0; Math-Sonnet 26.0/31.0/30.5; TB2.0 44.8/48.3/50.0; SWE 65.6/66.4/66.0 -> router beats best head only in 2 of 4. Table 3 p.8 (Math-Gemini): dev-update interval 5/3/1 = 53.0/56.0/62.0; pruning x guidance-update: off/off 51.0, guidance only 50.0, pruning only 54.0, both 62.0. Table 4 p.9: Meta-Harness test-best 49.0 (vs dev-selected 46.0) and 32.5 (vs 29.0).
- Candidate-evaluation allocation: each candidate is evaluated once on its branch's current dev subset (no triage/racing/bandit). The subset shrinks over time (e.g. Math-Gemini Branch 2: 58 -> 44 -> 40 cases, p.7, App. B.2), so later candidates cost less (this is the stated reason task-solving overhead is only 1.2-1.7x for 2 branches, p.12). Rankings are recomputed as the subset changes, which can change the incumbent without any new evaluation (p.4). Only one candidate per branch per iteration (compute allocated equally across B=2 branches; no adaptive branch budget).
- Task selection / curriculum: YES, central. Coverage vote c_b(x)=#frontier harnesses of branch b solving x; if every frontier harness of every branch solves x, drop x everywhere; else branch b "owns" x when c_b(x) - max_{b'!=b} c_b'(x) >= Delta (=2) and x is removed from other branches' subsets (Eq.2-3 p.4). Pruning starts once each branch has >= q=5 candidates (iteration ~5). Dev-case removal is based on pass/fail outcomes of dev cases only (no test), so selection-on-dev overfitting risk applies; subsets get small (e.g. SWE-Lite 30 shared + 1-7 exclusive of 50, App B.1).
- Merge/composition (verified?): NO code merge. Branches are never merged; at deployment a router (action LLM prompted with expert source code + "head-exclusive" dev cases, i.e. cases solved by exactly one head, instruction optimized with GEPA) picks ONE branch head per input before execution (p.5). Router is verified only on held-out test as a deployed system (Table 2), after its config was fixed on dev; router recovers 75% of exclusive successes on Math-Gemini (12/18 + 18/22, p.8) and stays 4.4-5.5 pts below oracle union (p.8). Deployment executes only one head per input, but router call + both heads' code are in context.
- Optimizer self-modification: per-branch proposal guidance (SKILL.md) rewritten from search history (SkillOpt-style); the proposer's code/model are fixed. Authors state optimizer updates revise guidance "rather than model weights or optimizer code" (p.9).
- Overlap with CapEvolve: branch DAG with failure-driven specialization; per-task impact (who solves what) -> branch ownership; guidance memory files; dev-only selection. Differs: routing vs merging; no pooled Bayesian signals; no cost-aware stopping.
- What it means for our claims: closest published analogue to our multi-branch search with per-branch task focus; a claim that "branching helps" needs a matched-compute control (their branching uses 1.2-1.7x task tokens and ~2.2x total on Math, Table 5) and a single-lineage control with same dev subset pruning. Gains are single-run; Math/Sonnet and SWE-Lite differences are 1-2 problems of 200/250 (binomial SE ~3.2-3.5 pts on n=200, my calc). Router results show specialized heads are not mergeable into one artifact; if we claim "verified merge", we must show merge beats best branch on held-out, which this paper does not attempt. Reproduction feasibility: med (method simple, but needs Opus-class proposer and heavy TB2.0/SWE-Lite compute; no code).
- Discrepancies vs prior review/catalog: review's relative-gain numbers (34.8/11.6/3.8%) verified; review omits that Math/Sonnet gain is only +5.2% rel and that cost is not matched (1.2-1.7x task tokens). Catalog fine. Note the 34.8% headline is a single setting (Gemini 3 Flash math).
