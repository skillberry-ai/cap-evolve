# MIPROv2 / DSPy (two papers, one card)
Part 1 = DSPy (dspy.txt); Part 2 = MIPRO (mipro.txt; the "MIPROv2" optimizer name is the DSPy package name for the paper's MIPRO, see discrepancies).

## Part 1: DSPy
- Exact title: arXiv v1: "DSPy: Compiling Declarative Language Model Calls into Self-Improving Pipelines". ICLR 2024 camera-ready title differs: "DSPy: Compiling Declarative Language Model Calls into State-of-the-Art Pipelines" (proceedings.iclr.cc page title).
- Authors: Omar Khattab, Arnav Singhvi, Paridhi Maheshwari, Zhiyuan Zhang, Keshav Santhanam, Sri Vardhamanan, Saiful Haq, Ashutosh Sharma, Thomas T. Joshi, Hanna Moazam, Heather Miller, Matei Zaharia, Christopher Potts (arXiv API)
- arXiv id + version read: 2310.03714v1 (PDF stamp "5 Oct 2023", header "Preprint"; 32 pages; this is the only arXiv version per API updated=published)
- First date / latest version date: 2023-10-05 / 2023-10-05
- Venue/status: ICLR 2024 (spotlight on OpenReview). Sources: proceedings.iclr.cc/paper_files/paper/2024/hash/f1cf02ce09757f57c3b93c0db83181e0 (page title shows the changed title); OpenReview note sY5N0zY5Od venue "ICLR 2024 spotlight" (API search 2026-10-11). The arXiv text we read is the preprint, not the camera-ready.
- Code URL + license + endpoint note: https://github.com/stanfordnlp/dspy ; MIT (GitHub API). Current repo (v3.4.0 pyproject) depends on litellm (>=1.65.8) so OpenAI-compatible endpoints via api_base are supported (litellm dependency verified; endpoint config not run).
- Citation count: unavailable (Semantic Scholar API rate-limited repeatedly on 2026-10-11 for arXiv:2310.03714)
- Editable surface: per-module demonstrations (bootstrapped few-shot), instructions, LM weights (BootstrapFinetune), and ensembling of programs (control flow only via ensembles). Not tool code or skills.
- Search method: "teleprompters" (optimizers) in 3 stages (Sec 4 p.6-7): bootstrap demonstrations by running a teacher/zero-shot program and keeping traces that pass the metric; parameter optimization over discrete candidate sets (random search = BootstrapFewShotWithRandomSearch, or TPE via Optuna = BootstrapFewShotWithOptuna, App. E.2-E.3); optional ensembles. Archive = set of candidate programs (top-k kept, e.g. top 7 for ensembling). No reflective editing in this paper.
- Feedback signal: scalar metric of the whole program only, no labels needed for intermediate stages.
- Task splits / held-out protocol: GSM8K 200 train / 300 dev / 1.3k official test (p.8); HotPotQA fullwiki: 200 train, 300 dev sampled from a 70/30 split of the hard train subset, test = 1000 sampled from official validation (p.10). Authors say they "report extensive comparisons on the development set to avoid overfitting on test" (p.8). Test reported only for selected rows.
- Benchmarks and models: GSM8K and HotPotQA; GPT-3.5 (exact checkpoint not stated in the text read) and Llama2-13b-chat, T5-Large (770M) for finetuning.
- Metrics: accuracy (GSM8K), answer EM and passage pair-retrieval accuracy (HotPotQA).
- Budget / cost reporting: only qualitative: "compiling generally runs on the order of minutes (or tens of minutes)... a few thousand program runs (10-20 trials over 150-300 validation examples)" (p.9). No tokens/$ table.
- Reported limitations: no limitations section; Conclusion says experiments are two case studies, other tasks left to future work (p.11).
- Key quantitative results: Table 1 (p.8) GSM8K GPT-3.5 test: vanilla 25.2; bootstrap x2 61.7; CoT+bootstrap 72.9 (dev 80.3); CoT +ensemble 81.6; reflection+bootstrap 76.0. Llama2-13b test: vanilla 9.4; reflection+bootstrap 40.2; +ensemble 46.9. Table 2 (p.11) HotPotQA multihop GPT-3.5 dev EM: fewshot 36.9, bootstrap 48.7, ensemble 54.7 (test 39.6 bootstrap, 45.6* ensemble on 50% of test due to cost). Abstract claims 25%/65% over few-shot and 5-46%/16-40% over expert demos (p.1).
- Candidate-evaluation allocation: random search / TPE over fully evaluated candidates on train+val (no racing in this paper).
- Task selection / curriculum: bootstrapping uses training examples where the program passes the metric (rejection sampling); iterated bootstrap x2 uses an earlier compiled program as teacher.
- Merge/composition: ensembling top-k compiled programs with majority vote (p.8); no verification step beyond measuring the ensemble.
- Optimizer self-modification: none (teacher bootstrapping aside).
- Overlap with CapEvolve: DSPy is the substrate GEPA and MIPROv2 are shipped in; compiled-program-as-artifact idea, metric-driven optimization of module parameters, held-out dev vs test discipline.

## Part 2: MIPRO (the original MIPRO/"MIPROv2" optimizer paper)
- Exact title: Optimizing Instructions and Demonstrations for Multi-Stage Language Model Programs
- Authors: Krista Opsahl-Ong, Michael J Ryan, Josh Purtell, David Broman, Christopher Potts, Matei Zaharia, Omar Khattab (arXiv API; first two equal contribution)
- arXiv id + version read: 2406.11695v2 (28 pages; PDF stamp "arXiv:2406.11695v2 [cs.CL] 6 Oct 2024")
- First date / latest version date: 2024-06-17 / 2024-10-06
- Venue/status: EMNLP 2024 main conference. Sources: arXiv comment "EMNLP 2024. Krista and Michael contributed equally"; ACL Anthology 2024.emnlp-main.525 (pp.9340-9366, Miami, Nov 2024; page fetched 2026-10-11).
- Code URL + license: released inside DSPy (http://dspy.ai per abstract): https://github.com/stanfordnlp/dspy, MIT. MIPROv2 class: dspy/teleprompt/mipro_optimizer_v2.py (read 2026-10-11, repo main at v3.4.0). Endpoint: via litellm, see Part 1.
- Citation count: 346 (Semantic Scholar Graph API, arXiv:2406.11695, retrieved 2026-10-11)
- Editable surface: free-form instruction and few-shot demonstration set for every module (predictor) of an LM program.
- Search method (paper): Sec 3-4 pp.3-6. Proposal: bootstrap demos from successful traces; instructions proposed by a "grounded" proposer LM program fed with dataset summary, program summary, bootstrapped demos and a random prompting "tip" (the proposal strategy). Credit assignment by a surrogate: categorical latent variables (instruction idx, demo-set idx per module) with uniform priors, sampled by Tree-structured Parzen Estimator (Optuna, multivariate TPE). MIPRO step: score the parameterization on a random mini-batch of B examples, update TPE; every S steps the combination with the highest mean minibatch score is evaluated on the FULL train set; return the best fully evaluated parameterization (p.6). Variants: 0-shot MIPRO, Bayesian Bootstrap, MIPRO++ (meta-optimizes proposal hyper-params incl. proposer temperature, tip, dataset/program summary booleans). Baselines: Bootstrap Random Search, Module-Level OPRO.
- DSPy package MIPROv2 (code, not paper; version differences): constructor `auto` in {light, medium, heavy} with AUTO_RUN_SETTINGS light n=6/val_size 100, medium n=12/300, heavy n=18/1000; `minibatch=True`, `minibatch_size=35`, `minibatch_full_eval_steps=5`; default valset = last min(1000, 80% of trainset) of trainset if none supplied; TPESampler(multivariate=True); full eval of best-mean-minibatch combos every few trials and at the end; estimated calls = minibatch_size*num_trials + len(valset)*full_eval_steps. GEPA used auto=heavy (18 instruction + 18 demo candidates) (GEPA p.26).
- Feedback signal: scalar program-level metric only; no module-level labels or gradients.
- Task splits / held-out protocol (Table 3 p.14, B.1): HotPotQA 500/500/2000; HotPotQA Conditional 500/200/200; ScoNe 500/500/1200; HoVer 500/500/1520; Iris 75/-/75; Heart Disease 120/-/183 (train/dev/test). Optimizers are scored on the TRAIN set (full evals "on the trainset", p.8); dev "used to internally iterate on methods"; test for final reporting. 5 runs per method per task; Wilcoxon signed-rank on per-example run averages (p.8).
- Benchmarks and models: 7 LM programs (Table 1 p.7): HotPotQA, HotPotQA Conditional, Iris, Iris-Typo, Heart Disease, ScoNe, HoVer. Task LM Llama-3-8B (SGLang, temp 0.7); proposer GPT-3.5 (GPT-4 for ScoNe, HoVer, Iris); teacher GPT-4o for ScoNe/HoVer bootstrapping.
- Metrics: EM, accuracy, custom regex metric (Conditional), Retrieval@21 (HoVer).
- Budget / cost reporting: budgets in "full evaluation trials" (B.2 p.14): HotPotQA and ScoNe 50 full-eval trials (~300 minibatch trials), Iris/Heart/Conditional 30, HoVer 20. N candidates per module in Table 4. No $ / token / wall-clock for search. Limitations says fixed budget only.
- Reported limitations: fixed budget (no low/high-budget study); fixed proposer and task LM; weak at inferring task rules without a handwritten seed prompt; benchmark coverage (p.10).
- Key quantitative results: Table 2 (p.9) test, avg of 5 runs; MIPRO vs Bootstrap RS: ScoNe 79.4 vs 75.4; HotPotQA 46.4 vs 45.8; HoVer 39.0 vs 37.2; HotPotQA-Cond 23.3 vs 10.4; Iris-Typo 68.7 vs 58.7; but Iris 88.6 vs 94.1 and Heart Disease 74.2 vs 79.2 (RS better). Un-optimized: ScoNe 69.1, HotPotQA 36.1, HoVer 25.3, Cond 6, Iris 40.9, Iris-Typo 32, Heart 26.8. Abstract: outperforms baselines on 5 of 7 programs, by as much as 13% accuracy (p.1). Lesson 1: demonstrations-only often beats instruction-only (p.8).
- Candidate-evaluation allocation: stochastic mini-batch evaluation as a noisy objective for the TPE surrogate, periodic full-train confirmation of the top mean-score combination (~300 minibatch trials vs 50 full evals). Closest in the set to "subset triage + full confirmation".
- Task selection / curriculum: random minibatches; bootstrap demos from passing traces.
- Merge/composition: joint instruction x demo combination search per module (not lineage merge).
- Optimizer self-modification: MIPRO++ meta-optimizes the proposal strategy (a bounded set of proposal hyper-parameters), i.e. a limited form of learning to propose.
- Overlap with CapEvolve: minibatch triage + full confirmation (our optional subset triage and full-val confirmation); credit assignment across modules via surrogate (our per-task Bayesian posterior is a different object: posterior over tasks, not over parameter choices); proposer gets program/dataset summaries (our failure clusters).
- What it means for our claims: (a) "subset triage + full-val confirmation" is not new; cite MIPRO. (b) MIPROv2 is a mandatory prompt-surface baseline; use the DSPy package at a pinned version and report auto level, because the package differs from the paper (valset capped/derived, defaults). (c) MIPRO's TPE searches a fixed pre-generated candidate pool; CapEvolve generates candidates sequentially from failures; matched-budget comparison must count proposer tokens. (d) Paper selects on train score, GEPA/ours on separate val; avoid copying that. Reproduction feasibility: HIGH (open MIT code, small programs, local Llama-3-8B), MED for exact paper numbers (proposer GPT-3.5/GPT-4 versions have changed).
- Discrepancies vs prior literature review / catalog: (1) review says MIPRO "Preprint; acceptance not verified" but arXiv comment and ACL Anthology confirm EMNLP 2024 main (catalog venue field is null). (2) Review says DSPy title is the arXiv title; the ICLR 2024 proceedings title is "...State-of-the-Art Pipelines". (3) The term "MIPROv2" never appears in the paper PDF (it uses "MIPRO", "0-Shot MIPRO", "MIPRO++"); MIPROv2 is the later DSPy class name, so GEPA's "MIPROv2" results are not the paper's MIPRO. (4) Review's "surrogate-guided search" is correct. DSPy review venue ICLR 2024 is correct.
