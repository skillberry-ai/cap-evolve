- Editable surface: (a) skills s=(metadata m, workflow instructions w, resources r incl. templates/domain knowledge/scripts) [p.3 Sec 2.1]; (b) agent-side TOOLS tau=(description d, implementation f, signature sigma), e.g. python tools pdf_parser, table_extractor(pdf,page,row:int,col:int), web_search, slack_api [Tables 3-4 p.22]; (c) a context-share vector y over skills (allocation, not text); (d) a nogood memory. No MCP / tool-exposure editing; tool description d counts toward context but is not edited separately from the four typed ops.
- Typed migration (exact): four typed ops [Sec 3.4 p.5-6, App B p.19-20]. PATCH(tau,df): fix implementation under unchanged signature, preferred as wrapper f'=post∘f∘pre (removable), caller set R=empty. RETYPE(tau,sigma'): only op that changes an existing signature; f adapted; R=Dep(tau), every dependent skill call site rewritten. EXTRACT(Src,g): >=2 skills (or an existing tool) containing near-duplicate logic g -> new tool tau_g, g replaced by calls, unit tests derived from sources, R=Src∩S; allowed only if logic is shared, deterministic/unit-testable, context-independent. INLINE(tau): inline logic into every dependent skill, delete tool, record a nogood so an equivalent tool is not rebuilt. A proposal L=(tool ops, skill edits) is an ATOMIC BUNDLE including all required caller updates (Prop A.9: under persistent exact-match dependencies single-component legal edits cannot complete a breaking migration). Legality (every called tool exists, call sites match signature) via static dependency/call-site checks, then tool unit + integration + regression tests on D_val. Acceptance prefers larger ΔPerf - λ·Δc̄ (context-token change incl. interface/call-site overhead); extraction cost rule c'_i = c_i - ℓ + ℓ_δ + ℓ_d/k (Eq 9).
- Search method: archive G of validated states, instance-level Pareto parent selection (Alg 3: sample parent ∝ win count over per-train-task best) [App A.8 p.19]. Each round: minibatch M from D_train executed with random skill masking (rate ρ); Ochiai spectrum fault localisation picks tool/interaction/shared/skill repair site; reflector R + Tool-Smith propose bundle; nogood veto (exact match for structural, embedding sim θ_veto for descriptive; up to 2 revisions); validate on D_val; accept if no regression and passes, else delta-debug (ddmin, capped n_dd) failing bundle into version-scoped nogoods (with remedy/open marker; expire on version change). Skill "ecosystem": share y updated by Hedge/replicator dynamics over marginal utility per token, Bayesian second-order effect model (Thompson sampling), skill retirement if Pr(f_i>0)<ε. Returns argmax_{G} mean D_val score (Alg 2 p.18). Memory: nogoods, retired skills, per-parent posterior. Merging: none (no branch merge).
- Feedback signal: black-box score P(x)∈[0,1] + trajectories + unit tests; labels used for scoring. OfficeQA score = fraction of 5 tolerance checks passed (θ=0.8 flags failure); SealQA LLM-judge (frozen Qwen3.5-122B, 3x majority); WCB rubric checkpoints with critical-error zeroing [App D.4 p.22-23].
- Task splits / held-out protocol [App D.1 p.20]: OfficeQA 246 q, EvoSkill stratified protocol: 10% train (24), 7% val (17; Pareto selection + regression checks), 205 held-out test "never exposed during evolution"; Table 1 numbers on test only. SealQA seal-0 111 q: 11 train / 8 val / 92 test. WildClawBench: SkillClaw day-night protocol, 6 evolution days, 4 categories (6+11+11+10=38 tasks, 10 trials/day) -- evaluated on the SAME tasks the system evolves on (online), so NOT held-out. Test not used for selection on OfficeQA/SealQA (selection = D_val of 17/8 questions, which is also reused for regression/unit tests -> very noisy gate). Ablation Table 2 (122B): SealQA + WCB only; no OfficeQA ablation, so tool-op contribution on the headline benchmark is not isolated.
- Benchmarks and models: OfficeQA (Mosaic/Databricks blog Dec 2025), SealQA seal-0, WildClawBench; Qwen3.5 at 9B/27B/35B/122B/397B (OfficeQA 5 scales; SealQA 4 scales 9B/35B/122B/397B); same frozen model reflects and executes. EvoSkill and SkillClaw re-run by authors on Qwen3.5 (not their native Claude Code/Opus setups).
- Metrics: accuracy (0% tolerance for OfficeQA), mean ± sample SD over 5 runs; regression rate, tool error rate, library size.
- Budget / cost reporting: budget B = executions spent proposing AND validating (accepted+rejected, incl. ddmin) [Sec 2.3]; the numeric value of B and of context budget C is not stated in the text read (UNVERIFIED). One cost table only: Table 5 (App E p.23), OfficeQA Qwen3.5-122B: EvoSkill 42.6 calls/iter x 18 iters = 766.8 calls, 18.4M tokens, 63.9%; SkillSmith 51.3 x 13 = 666.9 calls, 16.0M tokens, 72.2% ("~13% fewer calls and tokens"). Different iteration counts (no stated matched B); no $ or wall-clock; no cost for other benchmarks/scales.
- Reported limitations (authors) [p.10]: depends on reflection quality, sparse interaction exposure, posterior calibration; ascent/veto guarantees do not ensure improvement on every sampled update; transfer, changing distributions, embodied, multi-user deployment are future work.

- Candidate-evaluation allocation: every accepted-candidate path is a full D_val evaluation (17 / 8 questions); parent chosen by Pareto win counts on train; minibatch executions for localisation; failed candidates additionally cost ddmin replays charged to B. No racing/successive halving.
- Task selection / curriculum: random minibatches from D_train; failure set = score<θ; no curriculum; synthetic perturbations only in resilience study.
- Merge/composition: no branch merge; EXTRACT merges duplicated logic across skills into a tool (verified by derived unit tests + regression).
- Optimizer self-modification: none (reflector/Tool-Smith prompts fixed); nogood memory is the only learned optimizer state.
- Overlap with CapEvolve: very high. Pareto archive of states + git-like lineage, failure-localised proposal, per-edit rejection memory (= our LEDGER/JOURNAL, plus delta-debug minimisation), validation gate with regression checks, agent-side tool code AND skill co-editing, budget as first-class (B executions, C context). Differences: SkillSmith has theory (replicator/Bayesian skill-share allocation, typed atomic migration); we edit MCP descriptions/exposure and prompts, use paired gate mean(delta)>k*SE, seal test to a single finalize, agent-driven DAG with posterior triage.
- What it means for our claims: UNSAFE: "first joint tool/skill optimisation", "tool code vs prose boundary is novel", "rejected-edit memory is novel". REQUIRED: a SkillSmith-style arm (skill-only vs free tool edits vs typed atomic bundles) on our adapters under matched execution budget B; report tool error/regression rates as they do. Their held-out evidence is small-val (17/8) and OfficeQA lacks ablation; our paired-gate/sealed-test protocol can be positioned as stricter, but only if we measure it. Reproduction feasibility: LOW (no verifiable code; must reimplement masking/Bayes/ddmin; B and C unspecified).
