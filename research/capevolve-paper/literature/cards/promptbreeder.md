# Promptbreeder
- Exact title: Promptbreeder: Self-Referential Self-Improvement Via Prompt Evolution (arXiv capitalisation; ICML proceedings: "...via Prompt Evolution")
- Authors: Chrisantha Fernando, Dylan Banarse, Henryk Michalewski, Simon Osindero, Tim Rocktaschel (arXiv API; Google DeepMind per PDF p.1). PMLR lists "Dylan Sunil Banarse".
- arXiv id + version read: 2309.16797v1 (PDF stamp "28 Sep 2023"; 64 pages; arXiv API shows only v1)
- First date (v1) / latest version date: 2023-09-28 / 2023-09-28
- Venue/status: ICML 2024 (PMLR vol. 235, pp.13481-13544, published 2024-07-08). Source: proceedings.mlr.press/v235/fernando24a.html citation meta tags fetched 2026-10-11. The arXiv text read is the v1 preprint.
- Code URL + license + endpoint note: no official code found. The paper PDF contains no code link (searched for github/open-source/released); the arXiv API gives no comment. Third-party reimplementations exist but were not evaluated. Reproduction needs reimplementation from the appendix prompts.
- Citation count: 675 (Semantic Scholar Graph API, arXiv:2309.16797, retrieved 2026-10-11)
- Editable surface: task-prompts (a unit holds two sequentially applied task-prompts, plus a mutation-prompt, plus in the few-shot variant a context list of correct workings out) and, self-referentially, the mutation-prompts and hyper-mutation prompts. The prompting topology (two-stage) is fixed (p.9).
- Search method: population of N=50 units; binary tournament GA (Sec 3 p.5): sample 2 individuals, mutate the fitter with one of 9 operators and overwrite the loser. Paper states nine mutation operators in five classes (p.6-8): direct mutation (zero-order and first-order prompt generation); estimation-of-distribution mutation (EDA, EDA rank-and-index, lineage-based; LLM continues a filtered list of population/elite prompts, ordered by ascending fitness, fitness values not shown); hyper-mutation (zero-order and first-order, mutate the mutation-prompt); Lamarckian (induce a task-prompt from a correct working out); crossover (10% chance after a mutation, fitness-proportionate partner) and context shuffling. Initialization: problem description + random mutation-prompt + random thinking-style. Diversity maintenance when stuck: random char strings prepended, BERT-similarity fitness sharing, evolving sampling temperature of the mutant (App. J.2 p.27). Memory: elite history list, population; archive = population only (loser overwritten).
- Feedback signal: scalar accuracy on a random batch of 100 training Q&A pairs per fitness evaluation. LLM is not shown fitness values (found it copied list entries, p.6).
- Task splits / held-out protocol: datasets without official split (MultiArith, AddSub, SingleEq, SVAMP) are split 50/50 into train and test before experiments (App. J.2 p.27, Table 1 caption p.2); others use official train/test. Runs continue "until the training fitness appeared to plateau" then the fittest individual of the whole run (by noisy 100-example training fitness) is evaluated once on the test set (p.27). Test not used for selection as described; stopping point is a human judgement from training curves. Test-set sizes not extracted.
- Benchmarks and models: GSM8K, SVAMP, MultiArith, AddSub, AQuA-RAT, SingleEq, CommonsenseQA, StrategyQA, ETHOS hate speech, Instruction Induction (24 tasks, App. K), PaLM 2-L as the LLM for everything (Redescriber/Inducer/Evaluator contexts, max 50/30/5 tokens; temperature 0 for inducer/evaluator).
- Metrics: accuracy.
- Budget / cost reporting: evaluations only: population 50, "typically 20-30 generations", 1-2k fitness evaluations per run (App. J.2 p.27; a generation = 25 pair competitions); each evaluation = 100 questions through up to two LM calls, so ~1-2e5 question runs per task (my arithmetic). Ablation runs: population 10 for 200 evaluations (App. L p.63). No tokens/$/wall-clock; no matched-budget baselines (baselines are numbers from other papers).
- Reported limitations (p.9): prompting topology is fixed so only content, not the prompting algorithm, is adapted; PB remains limited compared to open-ended human thought; suggests LLM-based diversity assessment as future work. Also notes mutation-prompt random draw at init hurts GSM8K (p.9).
- Key quantitative results: Table 1 (p.2) PaLM 2-L zero-shot: PB GSM8K 83.9, MultiArith 99.7, SingleEq 96.4, AddSub 87.8, SVAMP 90.2, StrategyQA 71.8, CSQA 85.4, AQuA-RAT 62.2; vs PS+ (PaLM 2-L) 60.5 / 92.5 / 94.7 / 74.4 / 86.3 / 50.1 / 73.3 / 39.4; APE 77.9 on GSM8K; OPRO 80.2 on GSM8K (taken from the OPRO paper, whose headline instruction was picked by test accuracy; see opro card). Few-shot PB: GSM8K 83.5, MultiArith 100.0, SVAMP 93.7, StrategyQA 80.2. ETHOS: 89% vs hand-designed 80% (p.9). Ablation (App. L Fig.4 p.63): removing self-referential operators is harmful under nearly all conditions (p.9). Table 8 (App. J.4 p.28, GSM8K): share of applications producing a fitter child: zero-order hyper-mutation 42%, lineage-based 26%, first-order hyper-mutation 23%, EDA rank-and-index 12.7%, direct 12%, EDA 10.7%, Lamarckian 6.3%.
- Candidate-evaluation allocation: every individual is evaluated on a fresh random 100-example batch (noisy, no full-train evaluation); no racing; fitness carried forward as the single noisy estimate (the loser is overwritten, the winner's fitness is not re-estimated).
- Task selection / curriculum: random batches from the full training set each evaluation; few-shot context list built from correct workings out.
- Merge/composition: crossover (task-prompt from another member via fitness-proportionate selection; not applied to mutation-prompts) and context shuffling; no verification beyond the child's own fitness evaluation.
- Optimizer self-modification: YES, the defining feature. Mutation-prompts are evolved with hyper-mutation-prompts (zero- and first-order). Ablations show removing them hurts, though only on prompt-text tasks and without a held-out control that matches compute.
- Overlap with CapEvolve: self-modifying optimizer instructions (our optimizer-prompt/PROCESS memory evolution), population/diversity maintenance, lineage and elite history.
- What it means for our claims: (a) "optimizer self-improvement" has a prior ICML 2024 baseline; any claim of optimizer self-modification must be separated into executor-surface edits vs meta-optimizer edits with its own held-out evaluation. (b) Population search with noisy 100-sample fitness and no full val is the contrast case for our paired-SE gate and sealed test. (c) No code: a Promptbreeder arm requires reimplementation, so low priority as a mandatory baseline. Reproduction feasibility: LOW (no official code; PaLM 2-L required; prompts in appendix allow a reimplementation).
- Discrepancies vs prior literature review / catalog: none found on venue (ICML 2024 verified at PMLR), title, or description. Catalog has no code URL and I found none. Minor: review says "evolves task prompts and mutation prompts"; also true: crossover and elites; review does not mention absence of official code.
