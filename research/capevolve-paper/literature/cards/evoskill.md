- Editable surface: agent "program" = system prompt + skill folders (SKILL.md trigger metadata + procedural instructions + optional Python/TS helper scripts/refs); skill-only mode or prompt-only mode (App D p.22). Code fixed.
- Search method: textual-feedback-descent loop (Alg 1 p.4). Frontier G of k best programs (default K=3; git branch per program, git tags frontier/*), round-robin parent, failures = train-batch samples with weighted multi-tolerance score <0.8, Proposer P (sees failures, traces, ground-truth answers, cumulative feedback history H) -> Skill-Builder S writes skill folder -> candidate scored on val; enters frontier if frontier not full or beats worst member (evict worst); early stop on no improvement. NOTE: despite "Pareto frontier" wording in abstract, Alg 1 ranks by scalar val score (top-k), not Pareto dominance. Memory: H (proposal, delta, verdict). Merge: "skill-merge" of unique skills from independent runs (keep highest-run version on name/description overlap) -- no stated validation of the merged library.
- Feedback signal: scalar fuzzy score + execution traces + ground-truth labels given to Proposer (not copied into skills).
- Task splits / held-out [Sec 2.3.1, 3.1.2, 3.2.2]: stratified (LLM-clustered categories) disjoint train / val / test. OfficeQA (246 q): val 17 (~7%), train 5/10/15% (12/24/36), test = remainder, "never exposed during evolution", all reported accuracies on test. SealQA seal-0 (111 q): 10% train, remaining split into val/test (sizes not given in EvoSkill; SkillSmith states 11/8/92). BrowseComp: stratified 128-example sample for zero-shot transfer. Test not used for selection; BUT the headline (67.9, merge) is the best of 5 configurations all reported on test (mild test-side choice), 1 run each.
- Benchmarks and models: OfficeQA (Dec 2025 blog), SealQA seal-0, BrowseComp; Claude Code + Opus 4.5 only; 1.5 epochs.
- Metrics: exact match (tau=0) via OfficeQA deterministic fuzzy scorer; LLM-judge for SealQA/BrowseComp.
- Budget / cost reporting: none for the search (no tokens, $, rollouts, wall-clock). Footnote 3 p.6: single run per config "due to computational cost of running Opus 4.5"; variance left to future work.
- Reported limitations: single seed; broader domains, multimodal, shared libraries, cross-model/harness transfer are future work (Sec 5).
- Key quantitative results: OfficeQA exact-match test, base 60.6; 5% train 63.4; 10% 65.8; 15% 64.5; merge-unique 68.1 in Table 1 [p.6] but 67.9 in abstract/text/Fig 2 caption (internal inconsistency). SealQA 26.6 -> 38.7 (+12.1) [Sec 3.2.3 p.7]. BrowseComp zero-shot with SealQA-evolved skill 43.5 -> 48.8 (+5.3, n=128) [p.7]. No SkillsBench/SpreadsheetBench numbers.
- Candidate-evaluation allocation: every candidate gets one full val evaluation (17 OfficeQA q); no subset/racing/posterior.
- Task selection / curriculum: category-keyed pools, batches sampled without replacement and cycled; iteration skipped when no failures.
- Merge/composition: manual cross-run skill-merge (unverified); no in-loop merge.
- Optimizer self-modification: none (Skill-Builder bootstrapped with fixed meta-skill).
- Overlap with CapEvolve: very high for the skill-package/hill-climb lane: git-branch lineage, val-gated acceptance, feedback history file (our LEDGER/JOURNAL), failure-driven proposals, sealed disjoint test.
- What it means for our claims: held-out discipline, git lineage and rejected-proposal memory are NOT novel; EvoSkill is the baseline of record for skill-package editing (SkillOpt, WikiSkill, SkillSmith all compare to it).
