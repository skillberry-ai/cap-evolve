# ADAS (Meta Agent Search)
- Exact title: Automated Design of Agentic Systems
- Authors: Shengran Hu, Cong Lu, Jeff Clune (arXiv API 2026-10-11)
- arXiv id + version read: 2408.08435, PDF stamp v2 (2 Mar 2025), 34 pages, header "Published as a conference paper at ICLR 2025"
- First date (v1) / latest: 2024-08-15 / v2 2025-03-02 (arXiv API; no journal_ref)
- Venue/status: ICLR 2025 (main conference, poster) -- sources: PDF header on every page; OpenReview t9U3LW7JVX "ICLR 2025 Poster" (api2.openreview.net search 2026-10-11). Also workshop versions at NeurIPS 2024 workshops (LanGame spotlight, AFM, OWA oral).
- Code URL + license + endpoint note: https://github.com/ShengranHu/ADAS (PDF p.1 abstract); Apache-2.0 (GitHub license API); README sets OPENAI_API_KEY (read) -> direct OpenAI SDK; custom base_url not verified. Last push 2025-01-28.
- Citation count: unavailable (Semantic Scholar 429)
- Editable surface: whole agent as Python code: a single `forward` function using a ~100-line framework (FM query, formatting) -> prompts, control flow, tools, workflow all editable (Sec 3, p.4).
- Search method: Meta Agent Search -- LLM meta agent (GPT-4/4o) iteratively writes a new agent conditioned on an ever-growing archive of all prior agents + metrics; two self-reflection novelty checks; up to 5 reflect-and-fix attempts on runtime errors; add to archive; fixed iterations (25 ARC, 30 other) (p.4-6, Alg. App H). Archive seeded with hand-designed baselines (CoT, CoT-SC, Self-Refine, Debate, QD...); empty-init variant in App I. No explicit selection rule beyond prompting the LLM with archive; no merging beyond LLM "crossover" in-context.
- Feedback signal: scalar validation performance (accuracy/F1) plus runtime errors; no per-task traces to the meta agent in main method (they note the "naive evaluation function ... overlooks valuable information", App J p.34).
- Task splits / held-out protocol: ARC: 20 val / 60 test questions (grid <=5x5, public train easy), each evaluated 5 times (p.6). DROP/MGSM/MMLU: 128 val / 800 test; GPQA diamond: 32 val / 166 test, 5 evals (App E p.29). Search uses val; reports test with 95% bootstrap CI. Caveat: Fig 3a plots held-out test accuracy per iteration; Sec 4.3 picks "top 3 agents with the best test accuracy" on ARC for transfer (p.8) -> selection of transferred agents appears to use test accuracy (for MGSM top-3 selection criterion not stated -> UNVERIFIED).
- Benchmarks and models: ARC (easy subset), DROP, MGSM, MMLU, GPQA; transfer to GSM8K, GSM-Hard. Meta agent GPT-4 (ARC) / gpt-4o-2024-05-13 (others); agents evaluated with gpt-3.5-turbo-0125; transfer to Claude-Haiku, GPT-4, Claude-Sonnet (p.6-9, App E).
- Metrics: accuracy, F1 (DROP), with 95% bootstrap CI.
- Budget / cost reporting: yes, coarse -- one ARC search+eval run ~USD 500, one reasoning-domain run ~USD 300 (OpenAI API), mostly gpt-3.5 evaluation cost (App J, p.34). No token counts; baselines are hand-designed (no search cost), no matched-search-budget comparison to other optimizers except OPRO (budget not stated).
- Reported limitations: safety of executing model-written code (containerized); single objective only; naive/expensive evaluation function; higher-order (self-referential) ADAS left as future work (Sec 6, p.10, J p.34).
- Key quantitative results: Table 1 (p.7), test, gpt-3.5: Meta Agent Search DROP F1 79.4, MGSM 53.4, MMLU 69.6, GPQA 34.6 vs best hand-designed 65.8 / 39.0 / 65.9 / 31.6; OPRO 69.1 / 30.6 / 67.6 / 32.9. Empty-init variant MGSM 67.5 but DROP 73.9 (App I table, p.34). Transfer MGSM->GSM8K 69.5 vs best baseline 43.6 (Table 2, p.8). ARC cross-model: best agent 48.3 on Claude-Sonnet vs 39.3 Self-Refine (Table 3, p.9). Per-iteration ARC curve only in Fig 3a (p.5).
- Candidate-evaluation allocation: full validation evaluation of every candidate (ARC val 20 x5 runs; others 128 val x1) -- no triage/racing.
- Task selection / curriculum: none (fixed val set); self-described "naive evaluation function".
- Merge/composition: none explicit; "crossover" of stepping stones happens implicitly inside the LLM's context (p.6). No verification of merges.
- Optimizer self-modification: not performed; proposed as "Higher-order ADAS" future work (p.10).
- Overlap with CapEvolve: code-space search over whole agent with archive + coding LLM proposer; CapEvolve hill-climb is single-lineage with failure-cluster evidence; ADAS archive is just prompt context (no DAG/posterior/triage).
- What it means for our claims: cannot claim "agent-written code as the editable surface" or "archive-conditioned proposer" as novel. Need a direct baseline (ADAS-style archive proposer) at matched proposer-token + rollout budget on our adapters; note the original val sets are tiny (20-128), so ADAS gains have wide CIs and our SE-gated acceptance is a defensible contrast. Reproduction feasibility: medium (Apache-2.0, small codebase, but built on OpenAI SDK + their own tasks; AFlow and MASS report that reproductions behave differently).
- Discrepancies vs prior review/catalog: none material (ICLR 2025 confirmed). Catalog code_url null -> ShengranHu/ADAS. Review says it studies "transfer as well as task performance" -- confirmed (Sec 4.3). Note AFlow (p.8 Table 1) reports its own ADAS reproduction far below the original paper's numbers (e.g. MATH 35.4), so cross-paper ADAS numbers are not comparable.
