# Branch2Skill (slug: branch2skill)
- Title: Branch2Skill: Efficient Skill Evolution Through Reasoning Trees; authors Yanwei Ren, Haotian Zhang, Likang Xiao et al. (8 total; Beihang et al.); arXiv 2608.08677v1; first 2026-08-09; preprint (comment: 9 pages, 6 figures, 3 tables, technical report).
- Code: abstract says "Code will be published"; no URL (unverified).
- Surface: one skill document; edits APPEND / REPLACE / DELETE.
- Method: per update step, MCTS (PUCT, 3 children, depth 6, 40 iterations) builds a reasoning tree for each of 2 training problems with the target model under the current skill; an elite path vs same-prefix sibling alternatives yields step-wise evidence; one optimizer call (GPT-5.5) returns one candidate skill (Sec 3.4 p4-5). The tree search is over reasoning trajectories, NOT over skill candidates; single-lineage skill hill-climb.
- Eval/gate: candidate evaluated on a fixed validation set by direct inference; accepted iff no designated metric decreases (componentwise non-regression, ties accepted), else rollback; final = best-validation checkpoint; single evolution epoch (Eq.3 p5). Splits (train/val/test): SearchQA 40/200/1400, SpreadsheetBench 40/40/280, OfficeQA 20/24/172, DocVQA 80/53/374, LiveMath 20/40/124, ALFWorld 20/18/134 (Table 1 p5). Seeds/CIs not stated; SkillOpt rerun with official configs, other baselines copied from the SkillOpt paper (p5).
- Headline (GPT-5.5 target, test, p6): Branch2Skill vs SkillOpt: SearchQA 83.9/80.4, Spreadsheet 77.5/76.4, OfficeQA 70.9/72.1, DocVQA 92.2/91.2, LiveMath 60.5/54.8, ALFWorld 96.3/95.5; aggregate gain 128.7 vs 117.8 points; also GPT-5.4, 5.4-mini, 5.4-nano, Qwen3.6-35B-A3B targets.
- Cost: evolution tokens 141.3M vs SkillOpt 526.7M (-73.2%), "include all evolution model calls" (Table 1, Fig 2, p5-6); gain per M tokens 0.911 vs 0.224. Ablation Table 3 on depth/children/iterations shows search capacity matters (LiveMath 60.5 at defaults vs 46.8 single-path evidence).
- RELEVANCE: low-med. Efficiency via richer per-task evidence from tree search (token accounting that includes all calls is a good model), but no candidate-level allocation, merging, or memory; validation gate is a non-decreasing rule on tiny val sets (18-53 tasks). Touches (a) only as per-task evidence efficiency.
