# BONSAI (slug: bonsai)
- Exact title: BONSAI: Evolvability-Guided Tree Search over Skills
- Authors: Yash Priya Shastri, Anand Eswaran, Adnan Qidwai, Pankaj Thorat, Sachin Joshi (5; IBM Research)
- arXiv id + version read: 2608.07056v1
- First date / latest date: 2026-08-07 / 2026-08-07

- Code URL + license: none stated in PDF text (grep for github/available/released found nothing) -> unverified. OpenAI-compatible: unverified.
- Citation count: unavailable
- Editable surface: one natural-language skill document (frozen performer granite-4.1-30b); nothing else.
- Search method: Monte-Carlo tree search over skill documents; root = fixed seed doc, every child = one LLM "reflective rewrite" of its parent from scored failed attempts (Sec 2.1, p1-2). Selection by UCT-like U(s)=v(s)+lambda(Q(s)-v(s))+c*sqrt(lnN(p)/N(s)) with lambda=1 (p2 Eq.3), where Q(n)=mean validation fitness of the node's lineage (descendants) = "evolvability", free by-product of search; brittleness sigma=v-Q. Progressive widening |children|<cw*m^alpha (alpha=1/2, first layer 4). Archive = full tree (e.g. 32 docs from 131 proposals on SpreadsheetBench, Fig 1). Final ship = argmax of validation fitness v (plain best doc; no test reads) (p4, Alg.1). Acceptance: child kept only if summed per-task score on the SAME training minibatch (5-8 tasks) strictly exceeds parent's (Eq.4), then scored on full validation split. Rejected proposals back up a visit only, not a value sample (Eq.6).
- Merge/composition (verified?): optional GRAFT operator: cross-lineage donor B's capability is restated by the optimizer as a revision of A (child of A only); fires if |B+| >= tau (tasks where B outscores A on stored per-task train scores); admitted only if summed score on payload+guardrail+anchor tasks improves and no guardrail task regresses (g_i(c)>=g_i(A) for all i in A+), and if A+ empty must beat donor too (Eq.8, Alg.2 p4-5), then scored on validation. So yes: a validated, per-task-guarded cross-branch merge (asymmetric transfer, tree stays a tree).
- Memory of failed edits: lineage-scratchpad (App A p8): did-not-work notes filed per version, concatenated along path to root, compacted by an Observer to <=6; OFF by default and not evaluated (p4, p6).
- Feedback signal: exact-match accuracy per task (partial credit logged but never steers); optimizer sees task, answer, reason judged wrong.
- Task splits / held-out protocol: fixed train/val/test per benchmark: SpreadsheetBench 80/40/280, SearchQA 400/200/1400, LiveMathematicianBench 60/60/57; test touched once at end; identical splits across arms (p5). Single run at seed 42 (p5-6).
- Benchmarks and models: SpreadsheetBench, SearchQA, LiveMathematicianBench; performer granite-4.1-30b (temp 0), optimizer DeepSeek-V3.2 (temp 0.7).
- Metrics: held-out accuracy and solved counts (Table 1 p6); budget in performer rollouts.
- Budget/cost reporting: rollout-matched budgets (~2400 SSB, ~18,000 SearchQA, ~3000 LiveMath), GEPA capped at BONSAI's measured uncached rollout count; optimizer calls 131 on SSB; no dollar/token cost, no accounting for unselected branches beyond equal rollouts (p5-6).
- Reported limitations: single run per benchmark, one performer/optimizer pair, gain reflects whole search strategy, scratchpad not evaluated, acceptance on 5-8 tasks is noisy (p6).
- Key quantitative results (Table 1 p6, test): SpreadsheetBench no-skill 7.50, seed 17.50, GEPA 21.07, SkillOpt 20.00, BONSAI 23.21, BONSAI+GRAFT 25.00 (65 vs 70 of 280 solved); SearchQA GEPA 78.29, SkillOpt 75.57, BONSAI 79.00, +GRAFT 78.93 (1400 test); LiveMath (57 test items) GEPA 56.14, SkillOpt 59.65, BONSAI 64.91, +GRAFT 63.16. lambda=1 vs lambda=0 (Table 2 p6): 23.21/20.00, 79.00/76.86, 64.91/57.89. Abstract: +3.87 vs GEPA, +3.97 vs SkillOpt (3-benchmark average).
- Candidate-evaluation allocation: tree search with UCB over nodes (visit counts) and lineage-mean value; cheap screen on training minibatch (5-8 tasks) before full-val scoring of accepted children; budget concentrated: top-5 nodes take 58% of visits. Nothing Bayesian per task.
- Task selection/curriculum: next training minibatch (sequential batches); per-task scores reused for graft.
- Optimizer self-modification: none (Observer compacts scratchpad using the same optimizer).
- Overlap with CapEvolve: HIGH on (a) (budget-aware allocation across candidates in a DAG-like archive, cheap-subset triage then full-val confirmation), (b) (per-task-guarded cross-branch graft validated on train batch then val), (e) (did-not-work memory along lineage, off by default). Not (c),(d),(f).
- What it means for our claims: (a) "adaptive allocation across candidates with cheap-subset triage then full-val confirmation" is NOT novel (BONSAI does batch triage + val confirmation + UCB). (b) "verified merging" must be narrowed: BONSAI's graft is validated by per-task guardrails, differing from ours in being asymmetric single-parent revision using stored per-task scores, evaluated only on train tasks before val. (e) failed-edit memory exists but is unevaluated here. Required comparison: BONSAI (UCT on lineage mean) and GRAFT vs our agent-optimize on equal rollouts, and cite for per-task payload/guardrail. Reproduction feasibility: medium (algorithm fully specified, no code link found).
- Notes on evidence quality: single seed 42 per arm, tiny test sets (57 items on LiveMath: one item = 1.75pt; 280 on SSB), differences of 2 points = 5-6 tasks; acceptance gate on same minibatch that produced the edit; SkillOpt and GEPA run by the authors with granite/DeepSeek-V3.2 (SkillOpt weaker with weak optimizer by their own explanation); baseline wins attributed to search strategy only partially isolated (Table 2 isolates lambda).
