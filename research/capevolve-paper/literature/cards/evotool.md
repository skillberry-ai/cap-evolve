- Editable surface: four natural-language module prompts of a tool-use policy: Planner, Selector, Caller, Synthesizer (Sec 3-4). Edits are prompt text only; "do not add new tools or environments" (Mutator prompt A.5 p.15). Tool code / tool descriptions are NOT edited.
- Search method: evolutionary population of 4-module prompt specs. Per generation (Alg. 1, p.13): sample parent proportional to win frequency on selection set S_sel; run mini-batch (B=3) from S_train; Blamer LLM assigns module blame scores from trajectory + diagnostics -> pick argmax module; Mutator LLM writes one minimal edit to that module only; child kept if mini-batch mean reward > parent; then every population member is evaluated on all of S_sel, and only candidates that are the (arg)max winner on >=1 instance survive; sampling weight = fraction of instances won. G=8 generations; return best mean on S_sel (p.15). Instance-wise-winner retention is a form of Pareto/lexicase-like selection. No merge.
- Feedback signal: binary/scalar outcome reward + full trajectory + structured diagnostic events (tool-choice, argument validity, tool execution, synthesis-grounding), and LLM-generated NL critique (Sec 4.1-4.2).
- Task splits / held-out protocol: S_train, S_sel (held-out selection set) and the benchmark's official evaluation split (p.12, 15). Sizes of S_train and S_sel are NOT given in the PDF -> UNVERIFIED. All prompt-search baselines select the final prompt on the same S_sel and report on the official split (A.3 p.12). Test not stated to be used for selection.
- Benchmarks and models: ToolBench (G1/G2/G3), RestBench (TMDB, Spotify), tau-Bench (Retail, Airline; original tau-bench, Pass@1), BFCL (single/multi-turn subsets); GPT-4.1 and Qwen3-8B (Sec 5.1, A.6). Version of BFCL/ToolBench not given -> UNVERIFIED.
- Metrics: Pass Rate, Success Rate, Pass@1, accuracy; overall average of benchmark averages.
- Budget / cost reporting: only token cost vs performance plot (Fig 3b, p.6; values in plot only) and "same per-instance interaction budget" statement; no rollouts, $, or wall-clock for the search; baselines claimed to share "evaluation budget" (p.6) but how budget is counted is unspecified.
- Reported limitations: iterative inference adds latency; evaluation limited to textual/API environments (Limitations p.9). No discussion of variance/seeds (no CIs or seed counts found in the main tables).
- Key quantitative results: Table 1 (p.5) overall avg: GPT-4.1 EvoTool 70.6 vs DRAFT 64.9, EvoPrompt 63.8, ReAct 60.6; tau-Bench avg 52.0 (retail 64.8, airline 39.1) vs ReAct 47.9. Qwen3-8B EvoTool 57.0 vs best baseline DRAFT 51.8 (+5.2), ReAct 49.0. Blame ablation (Qwen3-8B, Table 2 p.7): Static 48.6, Random 39.5, Monolithic 49.1, best single-module 50.6 (Sel-only), EvoTool 57.0. Mutation guidance (Table 3 p.7, 'success rate', benchmark/model unlabeled; 74.6 equals Qwen3-8B RestBench avg in Table 1): full 74.6; w/o trajectory 70.2; w/o NL feedback 65.2; neither 62.8. Selection (Table 4 p.8): Static 48.6, Greedy 52.0, Top-k 52.7, EvoTool 57.0 (note Static ToolBench 56.0 in T4 vs 55.9 in T2: small inconsistency). Cross-model transfer: Qwen-evolved policy +4.7 on GPT-4.1; GPT-4.1-evolved +12.7 on Qwen3-8B (text p.8; Fig 5).
- Candidate-evaluation allocation: cheap child gate on a 3-example mini-batch (child accepted if mean reward > parent's on same batch -- very noisy with B=3), then full S_sel evaluation of all population members each generation (population size not stated). Instance-wise-winner pruning is the selection pressure; no SE-based gating.
- Task selection / curriculum: random mini-batches from S_train; selection set fixed; failure-localization via blame is the "focus" mechanism but over modules, not over tasks.
- Merge/composition: none explicit; modules can be mixed implicitly since each child differs from parent in one module, but no crossover/merge step.
- Optimizer self-modification: none (fixed Blamer/Mutator prompts).
- Overlap with CapEvolve: failure-localized edits (blame -> one module), trajectory-conditioned critique, and per-instance diversity retention of specialists (cf. our protect-set / per-task fixed-broken impact). Edit surface narrower (prompts only).
- What it means for our claims: cannot claim novelty for "localize failure to a component then edit only that component" nor for per-instance-winner population retention. Required comparison: single-surface-per-iteration (blame-gated) vs multi-part edit (ours) ablation. Their tau-Bench numbers (original tau-bench) must not be compared with tau2/tau3. Reproduction feasibility: low-medium (no code released, split sizes missing, tiny mini-batch gate; must re-implement from Alg. 1).
