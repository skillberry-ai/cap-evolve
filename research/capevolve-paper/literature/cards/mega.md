- Editable surface: heterogeneous agent workflow graph: code nodes, LLM calls (prompt + decoding), tool-using agent nodes, orchestration structure, tool configuration (Sec 6 p.16-17). Plus a persistent Wisdom Graph (skills, strategies, curation patterns, optimization trajectories as PCR triplets) that guides optimization.
- Search method: three-layer system. L1 distills session traces into wisdom assets (domain pre-clustering + BIRCH behavioural clustering, LLM synthesis, structural filtering, behavioural A/B validation with teacher-generated tests). L2 stores atoms in a typed graph, derives relations by deduction/abduction/induction, retrieves via Prize-Collecting Steiner Tree, ROI-based curation. L3 multi-agent optimizer (central optimization agent + scientist, code reviewer, redesign agent; "over a dozen" agents) with iteration 0 diagnosis and "delta mode" iterations applying up to three targeted fixes per iteration; verdict tuples (dAcc, dLat, dTok) feed back to L2 (Sec 6.6 p.22). Most algorithmic detail (PCST weights, ROI formula, thresholds) is not disclosed.
- Feedback signal: task metric from user checkers/rubrics (ground-truth evaluation data), tokens, latency; execution traces. Can synthesize evaluation data when absent (Data Agent, p.18-20).
- Task splits / held-out protocol: Experiments use GEPA-artifact splits train/val/test: HotpotQA 150/100/300, IFBench 150/100/294, HoVer 150/100/300, PUPA 111/111/221 (p.25); MEGA uses SMALLER val sets than GEPA's originals (100 vs 300 for HotpotQA) "to reduce optimization cost". SkillsBench axis uses all 84 tasks (no optimization, pool retrieval only). Whether test was untouched during optimization is not stated explicitly; within L3, the evaluation sample is a "seed-epoch" subset of D_train (below), with validation run at baseline, epoch boundaries and momentum events (p.21).
- Benchmarks and models: SkillsBench (84 tasks, 11 domains; Gemini CLI + Gemini 3 Flash, 5 attempts/task, 43 concurrent Docker trials, 4,207-asset skill pool; p.23); GEPA suite HotpotQA, IFBench, HoVer, PUPA on gpt-4.1-mini-2025-04-14 (p.24-25). Baselines for the second axis are NOT re-run: MIPROv2/TextGrad/GEPA numbers cited from the GEPA paper, Feedback Descent from its paper (Table 5 caption p.25).
- Metrics: pass rate, tokens/task, curation latency, efficiency = score per Mtok (Table 4); benchmark scores (Table 5).
- Budget / cost reporting: for SkillsBench: tokens/task and curation latency reported (Table 4 p.23). For optimization (Table 5): NO rollout counts, tokens, $, or wall-clock for the MEGA optimization run, and no budget-matched comparison with the cited baselines.
- Reported limitations (authors' own): scope-of-disclosure note (p.3); data synthesis limited to text I/O (p.18); "gains reflect integrated infrastructure, not any single component" - no component ablation is reported (p.25, 27). No limitations section.
- Key quantitative results: Table 4 p.23 (SkillsBench, 84 tasks): No Skills 31.5% / 894k tok / eff 0.353; AgentSkillOS 41.1 / 1189k / 403.4 s / 0.345; SkillNet 41.7 / 983k / 37.8 s / 0.424; MEGA(WG) 46.5 / 822k / 11.8 s / 0.566. Table 5 p.25 (GPT-4.1 mini, aggregate of 4): baseline 52.67, MIPROv2 59.71, TextGrad 61.08, Feedback Descent 66.56, GEPA(best of GEPA/GEPA+Merge) 69.52, MEGA 76.55 (+7.03 over GEPA); per-benchmark HoVer 74.67 vs GEPA 56.67 (+18.00), IFBench 61.05 vs 55.95, HotpotQA 72.67 vs 69.00, PUPA 97.81 vs 96.46. Single numbers; no seeds/CIs reported.
- Candidate-evaluation allocation: "Seed-Epoch" (Def. 2, p.21): a fixed seeded sample D_e = Sample(D_train, n, seed_e) (Fig 8: 50 samples) is used for ALL iterations in an epoch so deltas are paired on identical tasks (removes data variance); when |delta| < eps for m consecutive iterations the epoch is saturated and a new seed/fresh sample is drawn (a fresh-sample generalization check). Validation is momentum-triggered (baseline, epoch boundaries, recovery from regression or new best) rather than every iteration. Code reviewer does static analysis + dry-run before each evaluation "before they consume evaluation budget". No bandit/racing/posterior; eps, m, n details beyond 50 not given.
- Task selection / curriculum: Seed-Epoch resampling as above; coverage-driven synthetic data augmentation when dimension density/diversity is low (<=50% synthetic cap, Fig 9); ROI-based error prioritization (error rate x case count / cost; p.20); overfitting detection restricts next epoch to prompt-only edits when train-val gap exceeds a threshold (p.22); anti-heuristic enforcement forbids answer-format regexes/lookup tables.
- Merge/composition (verified?): composition is of retrieved knowledge atoms into plans (PCST), not of candidate agents; effectiveness verified by A/B (L1 behavioural A/B tests: treatment vs control with wisdom in system prompt, p.10) and by L3 fixed-seed verdicts. Candidate-agent branches/merges: none described. (The "GEPA(best)" row takes the max of GEPA and GEPA+Merge variants, not MEGA's own merge.)
- Optimizer self-modification: claimed ("the optimizer optimizes itself", p.26): curation patterns and optimization trajectories are accumulated and used to guide later runs; no evidence provided that this cross-run self-evolution improves results (Table 5 is a single-pass comparison; no multi-run compounding experiment reported).
- Overlap with CapEvolve: cross-run durable memory (like LEDGER/JOURNAL), failure-ROI prioritization, controlled fixed-sample evaluation for attribution (similar to our paired per-task deltas), heterogeneous workflow editing, synthetic eval-data generation.
- What it means for our claims: treat as architecture description with thin, non-reproducible evidence: baselines are copied from other papers (different seeds, harness, possibly different model snapshots/budgets), MEGA's own search budget is unreported, val sets are smaller than baselines', and the system is proprietary. Do not cite it as evidence that wisdom-graph memory helps optimization; at most cite the Seed-Epoch idea (fixed paired sample per epoch, resample on saturation) as prior art for paired evaluation and memory-based cross-run reuse. A CapEvolve claim of "memory files reduce search cost" would need our own budget-matched ablation. Reproduction feasibility: low (proprietary core; repo = results only).
