# Self-Evolving Multitask Harness
- Exact title: Self-Evolving Harness on Multiple Tasks with the Agent as Its Own Optimizer
- Authors: Qiankai Xu (Nanjing University) [PDF p.1; arXiv API]
- arXiv id + version read: 2609.38372v1 (stamp "arXiv:2609.38372v1 [cs.AI] 29 Sep 2026", p.1)

- Venue/status: arXiv preprint; no journal_ref; acceptance not verified (preprint)
- Code URL + license + endpoint note: none stated in PDF (only third-party repos cited: Self-Harness, Codex, mini-swe-agent, deep-swe); license n/a; endpoint unverified
- Citation count: unavailable (Semantic Scholar 429 on 2026-10-11)
- Editable surface: ENTIRE harness source code (any file may be added/deleted; seed = 49-line Python file: short system prompt, bash tool, loop) plus free-text "evolution notes" N_t kept across iterations (Sec 3.1-3.2 p.5-6). Harness grows 49 -> 430 (iter 5) -> 524 lines (iter 7) (Table 4 p.10).
- Search method: single-lineage, no archive of alternatives. Each iteration: solver (same frozen model, same harness) runs a batch once per task; the SAME agent in a fresh session acts as proposer, reading full unsummarized run records (trajectories, scores, grader output) + notes + previous update session, and directly edits the harness within a new-lines budget a_t (cosine schedule 500, 441, 300, 159, 100; stage 2: 200 then 100; Eq.8 p.7). Acceptance = "engineering checks" only (edits touch only harness, >=1 non-notes change, new lines <= a_t, mock-model full run completes; Eq.5 p.6); on failure a repair session. No score comparison, no validation set, no rollback (Sec 5.7 p.12 states this explicitly).
- Feedback signal: task score r and grader log v per run; textual trajectories; model reads everything raw.
- Task splits / held-out protocol: Stage 1 (iters 1-5): 5 benchmarks, each with 60 train tasks used exactly once (12 per benchmark per iteration = 60-task batch) and a disjoint held-out set never run during evolution (Table 3 p.8): TB 2.1 60/29x3 runs, GAIA2 60/100, OfficeQA Pro 60/73x2, tau3-bench banking 60/37x2, SWE-Bench Pro 60/100. Five OOD benchmarks never used in stage 1: SWE-bench Verified 100, DeepSWE 53, BrowseComp-Plus 100, APEX-Agents 100, Claw-Eval 100 held-out (80 train used only in stage 2). Evaluated versions (Seed, Iter 5, Iter 7) fixed in advance (Alg.1 line 12 p.7); no selection on held-out. Post-hoc reward-hacking audit of all eval trajectories (p.8).
- Benchmarks and models: Terminal-Bench 2.1, GAIA2, OfficeQA Pro, tau3-Bench banking, SWE-Bench Pro; OOD above. One model: "GPT-5.6 Sol", high reasoning, 258,400 in / 65,536 out tokens (as stated p.8; not independently verifiable); baseline Codex CLI 0.146.0.
- Metrics: success rate or official score x100; averages weight benchmarks equally.
- Budget / cost reporting: NONE for the search (no rollouts-count total, tokens, $, or wall-clock for evolution). Only structure: 5 iterations x 60 tasks + 2 x (40+20) tasks. Authors discuss "costs" only qualitatively (Sec 5.7).
- Reported limitations (authors' own, p.12): one strong model only; evolution stochastic and a single chain (variation unestimated); some benchmarks few held-out tasks; second stage = one new domain; local fixes with side effects; acceptance without validation ("validating each update at an acceptable cost is a missing piece"); edits narrow to few mechanisms.
- Key quantitative results: Fig 3(a) p.9 in-dist average (held-out): Seed 55.7, Iter 5 60.17 (+4.48 vs Seed, +2.99 vs Codex 57.2; text p.8); TB2.1 66.67 -> 83.91; SWE-Pro 51.00 -> 61.00; Iter 5 BELOW Seed on OfficeQA Pro and tau3 banking (Sec 5.6 p.12). Fig 3(b) OOD average: Iter 5 70.45 vs Seed 57.81 (+12.64) vs Codex 70.57 (text p.9); BrowseComp-Plus 34.0 -> 90.0 (Codex 93.0); excl. BrowseComp-Plus: Iter5 65.56 vs Seed 63.76 vs Codex 64.97. Fig 4 p.10: Claw-Eval Iter 5 66.17 -> Iter 7 68.06; passed tasks 52 -> 57.
- Candidate-evaluation allocation: none. A candidate harness is not evaluated before adoption; its effect is only visible implicitly as the next batch's fresh tasks (different tasks each iteration, so no paired comparison).
- Task selection / curriculum: YES. Multi-benchmark mixing (12 tasks/benchmark/batch, no task reused), decaying edit-size budget as "learning rate" (cosine), stage 2 = 40 new-domain tasks + 20 "success anchors" (previously solved training tasks rerun with the current harness, spread evenly over benchmarks) as replay to expose regressions to the proposer (Sec 3.4 p.7). Anchors are shown to the proposer but not used as a gate.
- Merge/composition (verified?): none; authors suggest keeping multiple versions (DGM-style) as future work (Sec 5.7).
- Optimizer self-modification: YES, explicit. Proposer runs on the very harness it edits (same model, same harness version), so improvements to the solver harness change the proposer's own tooling (Sec 1.1, 3.2). Table 2 p.5 marks "Ours" as the only method combining same model + same harness + minimal start + all-code scope + mixed task types + runnability-only acceptance (SICA shares same model/same harness but starts hand-designed and uses score-based selection).
- Overlap with CapEvolve: agent-driven edit of whole harness code from raw trajectories; train/held-out separation; edit-size budget analogous to our budgeted edits; success-anchor replay ~ our protect-set.
- What it means for our claims: it is a strong negative/positive reference for a gate: its ungated loop produced two regressions vs seed (Sec 5.6), supporting the value of the paired val gate and protect-set; but it also shows ungated single-pass edits can give large OOD gains (+12.64) on one model, so we cannot claim gating is necessary for gains, only for regressions. Any "generalization" claim of ours should include an OOD-benchmark evaluation of the final artifact and a "no-gate" ablation. Single chain, no seeds: gains over seed on 29x3 / 37x2 / 73x2 task sets are noisy (authors say so). Reproduction feasibility: low-med (loop trivial, but ten benchmarks, GPT-5.6-class model, no code).
- Discrepancies vs prior review/catalog: review's 4.48/12.64 and Claw-Eval 66.17->68.06 verified. Review says "same frozen model/harness as solver and proposer" - correct. Review does not mention that no acceptance gate/validation exists nor that search cost is unreported. Catalog: no arxiv_comments (API has "18 pages, 5 figures").
