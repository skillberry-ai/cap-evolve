# OPRO
- Exact title: Large Language Models as Optimizers
- Authors: Chengrun Yang, Xuezhi Wang, Yifeng Lu, Hanxiao Liu, Quoc V. Le, Denny Zhou, Xinyun Chen (arXiv API; Google DeepMind per PDF p.1)
- arXiv id + version read: 2309.03409v3 (42 pages; catalog downloaded_version v3)
- First date (v1) / latest version date: 2023-09-07 / 2024-04-15
- Venue/status: ICLR 2024 (main conference). Sources: arXiv comment "ICLR 2024; 42 pages, 26 figures, 15 tables. Code at https://github.com/google-deepmind/opro"; ICLR proceedings page proceedings.iclr.cc/paper_files/paper/2024/hash/3339f19c5fcee3ad74502947a32be9e6 (title match, fetched 2026-10-11). Oral/poster status not checked.
- Code URL + license + endpoint note: https://github.com/google-deepmind/opro ; Apache-2.0 (GitHub API). README: supports text-bison (PaLM API) and OpenAI GPT models via keys; "you may serve your own model and plug it in" in opro/prompt_utils.py; no base_url option seen in README; README warns about large API costs (README grep). README lists openai 0.27.2 (old SDK), so an OpenAI-compatible server needs code changes.
- Citation count: 1194 (Semantic Scholar Graph API, arXiv:2309.03409, retrieved 2026-10-11)
- Editable surface: a single instruction string (placed at A_begin, Q_begin or Q_end); also toy problems (linear regression, TSP) where the solution is a text-encoded vector/route.
- Search method: meta-prompt optimization loop (Sec 2-4). Each step: meta-prompt = meta-instructions + the best 20 instruction-score pairs so far, sorted ascending by score, + 3 randomly drawn training exemplars (Sec 5.1 p.8; the "optimization trajectory" is the memory); optimizer LLM sampled 8 times (temp 1.0) to propose 8 new instructions; each scored on the fixed training subset; added to trajectory. Default 200 steps. No explicit selection or parent choice; the LLM is the search policy. Archive = top-20 list in context.
- Feedback signal: scalar training accuracy per instruction only. Authors tried adding error cases to the meta-prompt and report similar results, concluding errors alone are not informative enough (Conclusion p.21).
- Task splits / held-out protocol: GSM8K: 3.5% random sample of the 7,473 training examples (~262) fixed as the optimization set; evaluated on the full 1,319 test set after optimization (p.8-9). BBH (23 tasks, <=250 examples each): 20% of examples for optimization, remaining 80% for testing (p.11). Selection in headline tables: Table 4 caption (p.9) "instruction with the highest TEST accuracy for each scorer-optimizer pair", i.e. the reported top instruction is chosen on test (optimistic; the text does not say how the other rows were chosen). Overfitting study (Fig.11 p.19) uses a 1/3-1/3-1/3 train/val/test split and finds train acc 5-20% above test acc (Tables 7, 10).
- Benchmarks and models: GSM8K, BBH 23 tasks, MultiArith and AQuA (transfer); linear regression, TSP. Optimizers: PaLM 2-L, PaLM 2-L-IT, text-bison, gpt-3.5-turbo, gpt-4. Scorers: pre-trained PaLM 2-L, text-bison (temp 0).
- Metrics: accuracy.
- Budget / cost reporting: steps (200 default, 8 candidates/step => ~1600 candidate evaluations; ~262 GSM8K questions each, so ~0.42M scorer calls; this arithmetic is mine, not reported). Authors note far fewer steps suffice (step 6 found 78.2 vs 80.2 at step 107, p.10). No $/tokens/wall-clock for the search.
- Reported limitations: for math optimization: context length, bumpy landscapes (p.6, App. A). For prompt optimization: optimizer does not effectively use error cases; needs a training set of at least tens of examples to avoid overfitting; sensitive to initialization (p.21).
- Key quantitative results: Table 4 (p.9) GSM8K test, PaLM 2-L scorer: "Let's think step by step" 71.8; empty 34.0; OPRO-found with PaLM 2-L-IT optimizer "Take a deep breath and work on this problem step-by-step." 80.2; PaLM 2-L optimizer 79.9; gpt-3.5 78.5; gpt-4 74.5. text-bison scorer: baseline 64.4, OPRO best 68.5 (text-bison optimizer). Abstract: up to +8% on GSM8K and up to +50% on BBH tasks (p.1). BBH 5%+ gains over "Let's think step by step" on 19/23 (PaLM 2-L) and 15/23 (text-bison) tasks (p.11). Fig.12 (p.20): OPRO beats EvoPrompt GA/DE meta-prompts under gpt-3.5-turbo optimizer; EvoPrompt even degrades on GSM8K from generic seeds.
- Candidate-evaluation allocation: every proposed instruction is evaluated on the SAME fixed training subset (3.5% GSM8K / 20% BBH); no per-candidate adaptive allocation; sample-size reduction is done once, by the fixed subset.
- Task selection / curriculum: 3 exemplars randomly resampled per step; error-focused sampling tried, no gain.
- Merge/composition: none; the LLM may implicitly combine features of high-scoring instructions in the trajectory.
- Optimizer self-modification: none (meta-prompt fixed per optimizer; they ablate meta-prompt parts and temperature).
- Overlap with CapEvolve: "propose from scored history" is the hill-climb memory pattern (our LEDGER/JOURNAL), incumbent-plus-history prompting, ablation of exemplar/trajectory content.
- What it means for our claims: (a) OPRO is the simple control: scalar-score-history prompting without traces; our claim that trajectories/trace evidence help must beat it at matched evaluations. (b) Its protocol of picking the best instruction by test score is exactly what the sealed-test discipline forbids; cite as a pitfall. (c) Training-vs-test gap of 5-20% supports the need for val confirmation gates. Reproduction feasibility: MED (code open, Apache-2.0; PaLM/text-bison are gone, so reproduction requires a different scorer and optimizer; steps and prompt templates are specified).
- Discrepancies vs prior literature review / catalog: none found on title, venue (ICLR 2024 corroborated by arXiv comment and proceedings) or the description. Not in the review: headline instruction chosen by best test accuracy (Table 4 caption), and the 3.5% / 20% optimization-set sizes.
