- Editable surface: multi-agent system = (i) per-agent prompts (instruction + few-shot exemplars) via MIPROv2 and (ii) topology chosen from a pruned block space {Aggregate, Reflect, Debate, Summarize, Tool-use/Executor} with agent counts, rule-based ordering [summarize, reflect, debate, aggregate] (Sec 3, p.5-7).
- Search method: 3 sequential stages (Algorithm 1, p.7): (1) block-level prompt optimization per building block (warm-up predictor with APO, then each block conditioned on it), record influence I = E(a_i*)/E(a_0*); (2) topology search: sample N=10 configurations by rejection sampling from an influence-weighted (softmax, t=0.05) pruned space under agent budget (<=10), 3 val evals each, pick best; (3) workflow-level prompt optimization on best topology. MIPRO: <=3 demos, 10 instruction candidates, 10 rounds per agent (p.8). No archive beyond candidate list; no merging; stage 1/2 can run in parallel (Fig 6 caption p.9).
- Feedback signal: scalar validation metric only (no trace-based critique); notes textual-feedback conditioning as future work (App A p.18). For MBPP/HumanEval uses public test cases as executor feedback (p.18).
- Task splits / held-out protocol: sub-sampled splits (Table 2, p.18), |Val|/|Test|: MATH 60/100, DROP 60/200, HotpotQA 50/100, MuSiQue 50/100, 2WikiMQA 50/100, MBPP 60/200, HumanEval 50/100, LCB 100/200. Search/selection on val (3 evals per topology), report on held-out test mean+-std over 3 runs (p.8). Std is over reruns, not over task sampling; test sets of 100 give wide binomial CIs.
- Benchmarks and models: MATH, DROP, HotpotQA/MuSiQue/2WikiMQA (LongBench), MBPP, HumanEval, LiveCodeBench test-output-prediction; gemini-1.5-pro-002 and flash-002 main; Claude 3.5 Sonnet and Mistral-Nemo-12B in App C. Same LLM as evaluator and optimizer (p.8).
- Metrics: accuracy (MATH, LCB), F1 (DROP, multi-hop QA), pass@1 (MBPP, HumanEval).
- Budget / cost reporting: yes -- Table 7 (p.22) training (search) tokens and $ for MATH (inferred: Acc column matches Gemini-1.5-flash MATH row of Table 1): AFlow 11M in/8M out $3.89; ADAS 23M/13M $5.61; MASS 24M/11M $5.09; inference per query tokens and $ also given. Table 7 Acc column: SC 69.3, SR 71.3, Debate 71.7, AFlow 64.3, ADAS 72.7, MASS 81.0 -- SC/SR/Debate/MASS match Table 1 Flash MATH, but ADAS 72.7 does NOT match Table 1 Flash MATH 68.00 (unexplained; p.8 vs p.22). Inference cost of compared MAS controlled to be comparable (<=10 agents). Fig 9 (p.22) Pareto-front accuracy vs total tokens. Claim: comparable training cost to ADAS/AFlow, but stages 1-2 parallelizable.
- Reported limitations: topology space may be incomplete (e.g., sparse communication), could use Bayesian optimization for sample efficiency, prompt optimizer could use textual feedback (App A, p.18). AFlow meta-prompt only works with Claude 3.5 Sonnet so AFlow* is "for reference" (Table 1 caption p.8).
- Key quantitative results: Table 1 (p.8) Gemini-1.5-pro avg over 8 tasks: MASS 78.79 vs CoT 65.28, SC 68.18, Self-Refine 66.90, Debate 70.26, ADAS 69.72 (AFlow* not averaged, partial). Flash avg: MASS 74.30 vs ADAS 64.75, Debate 65.91. Stage ablation avg (Gemini-pro, Fig 5 left p.9): CoT 63.5, APO 68.0, 1PO 74.2, 2TO 77.3, 3PO 78.8. Ablations w/o PO and w/o pruning hurt on HotpotQA (Fig 5 right; values plot-only -> UNVERIFIED).
- Candidate-evaluation allocation: fixed number of candidates (N=10 topologies), each fully evaluated 3x on the same val set; prompt optimizer (MIPRO) handles its own trial budget. Influence-weighted sampling prunes the topology dimensions BEFORE evaluation, based on stage-1 results -- a cheap prior but not racing/bandit.
- Task selection / curriculum: none; random subsampled val/test.
- Merge/composition: compose influential blocks sequentially in a fixed rule order; no merge verification beyond evaluating the composed topology on val.
- Optimizer self-modification: none.
- Overlap with CapEvolve: closest to the "allocate budget across editable surfaces" thesis: explicitly orders surface optimization (local prompts -> topology -> global prompts), measures per-block influence, and shows interaction (prompt optimized under one topology need not transfer). Reports per-stage ablation and matched search-token cost.
- What it means for our claims: "budgeted allocation across editable surfaces" is NOT novel in spirit; MASS is the key prior art. Differentiate: our surfaces are tool code/MCP descriptions/skill packages (not MAS topology), trajectory-driven edits and sealed-test finalize. Required comparison: a staged-surface ablation (prompt-only, tool-only, joint, MASS-style staged order) at matched token/rollout budget. Reproduction feasibility: low-medium (no code found; Gemini-specific; small test sets).
