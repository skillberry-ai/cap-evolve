README says "More results are coming soon". Endpoint support UNVERIFIED (paper used MiniMax API, OpenRouter GLM-5, local SGLang for Qwen).
- Citation count: 83 (Semantic Scholar API, retrieved 2026-10-11)
- Editable surface: a DeepAgents-SDK harness definition file: system prompt, bootstrap/execution/verification/recovery instructions, skills, subagents, memory sources, runtime-control policy (middleware) (Fig 3 p.10; Sec 4.1 p.9).
- Search method: iterative rounds; per round: evaluate current harness on held-in + held-out, cluster held-in failures by deterministic verifier-grounded signature (cause, causal status, mechanism), SAME fixed model proposes K diverse minimal edit bundles, each candidate evaluated on both splits, accepted if d_in>=0 and d_ho>=0 and max>0, ALL accepted candidates MERGED into next harness (Algorithm 1 p.6; Sec 3.4 p.8). Lineage of harnesses with logged accept/reject (Fig 4 trees show accepted/rejected branches and merged "combined" candidates evaluated as their own node). 7-20 candidate evaluations per run (Fig 4 axes, pp.12, UNVERIFIED for non-shown runs). K and T not stated in main text (UNVERIFIED).
- Parent selection: single incumbent harness (greedy lineage with branching candidates per round).
- Feedback signal: binary verifier pass/fail per task, execution traces, clustered failure patterns (text); proposer sees evidence bundle, passing behaviours to preserve, summaries of past attempted edits.
- Task splits / held-out protocol: Fixed held-in / held-out split per benchmark BEFORE running (p.9). Held-in supplies evidence; "held-out" is hidden from the proposer BUT is used by the promotion gate in every round => it is a VALIDATION/selection split, not a sealed test. No separate test set. Sizes: TB2 64-task subset of 89 (held-in/out counts not stated; inferable ~43/21 from percentages, UNVERIFIED); SWE-bench Verified 100 cases = 67/33; AppWorld 180 = 90/90 (held-in = official train partition, held-out sampled from test_normal/test_challenge) (p.9, App. A p.20). Each candidate eval = 2 repeated attempts.
- Benchmarks and models: Terminal-Bench-2.0 (64 tasks), SWE-bench Verified (100-case subset), AppWorld (180). MiniMax M2.5, Qwen3.5-35B-A3B, GLM-5 (model also the proposer) (p.9).
- Metrics: Pass (%) over 2 attempts per task via official verifiers; relative and absolute gains.
- Budget / cost reporting: NONE found (no tokens, $, wall-clock, or call counts for the search; only candidate-evaluation counts in Fig 4). No matched-budget baselines; baselines are only the initial minimal harness (no Meta-Harness / GEPA comparison in main results).
- Reported limitations: no dedicated limitations section found (grep: none); fixed model/evaluator emphasised as control. Arguments about overfitting rest on the regression gate.
- Key quantitative results [Table 1 p.11] initial -> final held-in / held-out / overall: TB2 MiniMax 43.0->50.0 / 40.5->61.9 / 42.2->53.9; Qwen 15.1->36.0 / 23.8->38.1 / 18.0->36.7; GLM-5 47.7->57.0 / 42.9->57.1 / 46.1->57.0. SWE-bench Verified MiniMax 46.0->52.5, Qwen 19.5->41.5, GLM-5 52.0->55.5 (overall). AppWorld GLM-5 44.4->85.0 (+40.6 pp, largest absolute), Qwen 22.5->52.2 (+132% relative). "No promoted harness degrades either split" (p.11).
- Candidate-evaluation allocation: full evaluation of every candidate on BOTH splits (all tasks), with repeats (2); no subset/racing/bandit.
- Task selection / curriculum: none (fixed splits).
- Merge/composition: YES -- all accepted compatible edits merged into next harness; merged result appears to be evaluated as its own candidate in Fig 4 (e.g. "Merged retained" node), but a mandatory post-merge verification rule is not stated in Sec 3.4 (UNVERIFIED).
- Optimizer self-modification: No (loop fixed). "Self" refers to the target model proposing edits to its own harness, not to editing the optimizer.
- Overlap with CapEvolve: very high structurally (failure clustering -> bounded edits -> regression gate -> merge accepted edits, harness code/prompt edits, same models class: open-weight MiniMax/Qwen/GLM), including TB2/SWE-bench Verified benchmarks.
- What it means for our claims: Any CapEvolve claim to "cluster failures, make targeted edits, accept via non-regression gate, merge branches" is directly pre-empted by Self-Harness. Its headline "held-out" gains are selection-set gains (promotion uses held-out), so they cannot be compared to a sealed-test number; need to re-run on a sealed test or label as validation. Unlike CapEvolve it reports no cost. Comparison needed: same models/benchmarks with a sealed test and equal candidate-evaluation counts. Reproduction feasibility: MED (benchmarks/models public; code has no license; hyperparameters K,T not in main text).
- Discrepancies vs prior review/catalog: Catalog slug self_harness; review calls it "examines evolving harness implementations" -- understated: it is the closest published match to the hill-climb+gate+merge design. Review does not note the held-out-as-gate issue or lack of license. Code URL in catalog is from the arXiv comment; confirmed.
