- Editable surface: a context "playbook" (system-prompt / agent-memory text) made of itemized bullets with ids and helpful/harmful counters; no tool code, no tool descriptions, no multi-file skills (Sec 3.1, p.5).
- Search method: not a search over candidates; sequential learning loop with 3 roles (same LLM): Generator produces trajectories, Reflector (up to 5 refinement rounds) extracts lessons, Curator emits delta bullets merged by deterministic non-LLM logic with embedding de-duplication (grow-and-refine) (Sec 3, p.4-5). Batch size 1; offline = multi-epoch (max 5) over training split; online = sequential on test stream. Memory = the playbook itself. No archive of alternative contexts, no accept/reject gate on val.
- Feedback signal: execution feedback and, optionally, ground-truth labels (GT) for the Reflector; ACE also run label-free using execution success/failure (Table 1, 2 "GT Labels" column). Degrades without reliable signal (Table 2 FiNER ACE-no-GT 71.1, online no-GT 67.3 < base 70.7, p.8).
- Task splits / held-out protocol: "original train/validation/test splits" (p.6). Offline: optimize on train, evaluate on test pass@1. ONLINE: methods evaluated sequentially on the test split -- predict then update context on that same sample, same shuffled test order for all methods (p.6) => test-time (transductive) adaptation, not held-out. Split sizes for AppWorld/FiNER/Formula not in main text -> UNVERIFIED. BIRD-SQL/DDXPlus: 1000 random train examples; GEPA given an extra validation set of 500 (BIRD) / 372 (DDXPlus) examples (p.16). No sealed test; test performance is the only reported selection-free number, but no per-seed CIs reported.
- Benchmarks and models: AppWorld (test-normal, test-challenge; TGC/SGC), FiNER, Formula (XBRL finance), DDXPlus, BIRD-SQL (StreamBench; LLM-judge GPT-4o-mini). Default backbone DeepSeek-V3.1 (non-thinking) for Generator/Reflector/Curator; extra: GPT-OSS-120B, GPT-5.1, Llama-3.3-70B (App A.1). Baselines: ReAct base, ICL, MIPROv2 (auto=heavy), GEPA (auto=heavy), Dynamic Cheatsheet (p.6-7).
- Metrics: TGC, SGC, average; accuracy; latency, #rollouts, $ for adaptation.
- Budget / cost reporting: yes, for adaptation. Table 4 (p.10): AppWorld offline ACE vs GEPA latency 9,517 s vs 53,898 s (-82.3%), rollouts 357 vs 1,434 (-75.1%); FiNER online ACE vs DC latency 5,503 s vs 65,104 s, token $2.9 vs $17.7. Input/output tokens -80.8%/-83.6% vs GEPA (text p.10). Single run, no variance. Note rollouts differ partly because ACE has no validation loop (GEPA does).
- Reported limitations: depends on a reasonably strong Reflector; noisy/harmful contexts without reliable feedback signals; not all tasks need rich context (HotPotQA, Game of 24) (Sec 5 p.10; also p.8-9).
- Key quantitative results: AppWorld avg (Table 1 p.7, DeepSeek-V3.1): ReAct 42.4; +ICL 46.0; +GEPA 46.4; +ACE offline w/ GT 59.4 (TGC normal 76.2/ SGC 64.3 / challenge 57.3 / 39.6); ACE offline no GT 57.2; online DC 51.9; online ACE 59.5. Finance avg (Table 2 p.8): base 69.1; GEPA 72.5; MIPROv2 70.9; ACE offline GT 81.9 (FiNER 78.3, Formula 85.5); ACE no-GT 77.1; online ACE 76.6. Ablation (Table 3 p.9): w/o Reflector or multi-epoch 55.1; w/o multi-epoch 56.8; full 59.4. Abstract's "+10.6% agents / +8.6% finance" are average gains over selected baselines (p.7-8). Leaderboard comparison to IBM CUGA (60.3) is context only (footnote p.8).
- Candidate-evaluation allocation: none -- single trajectory of context states; each delta is committed without val gating (so no candidate evaluation allocation).
- Task selection / curriculum: processes every training sample (multi-epoch); no selection/curriculum.
- Merge/composition: yes in a narrow sense -- itemized delta bullets merged deterministically (non-LLM) with semantic de-duplication; parallel deltas can be merged in batch (p.4-5). Not verified by testing merged vs unmerged; ablation shows incremental delta update helps (App A.5).
- Optimizer self-modification: none (fixed Generator/Reflector/Curator prompts).
- Overlap with CapEvolve: context-only surface ~ our "system prompt / memory" surface; CapEvolve's LEDGER/JOURNAL/PROCESS memory and failure clusters resemble the Reflector->playbook loop; ACE's "grow without rewriting" argues against monolithic LLM rewriting (context collapse) which is relevant to how large multi-part edits are applied.
- What it means for our claims: cannot claim that prompt/context-only evolution is weak or that structured incremental memory is new; also ACE's online results are test-stream adaptation, so any CapEvolve comparison must separate offline (train->test) from online. Required comparison: ACE offline playbook (train split only, GT and no-GT) vs CapEvolve prompt-only mode at matched rollouts on the same adapter splits, with a sealed test. Reproduction feasibility: high-medium (Apache-2.0, public code, DeepSeek-V3.1 via configurable providers; AppWorld setup needed).
- Discrepancies vs prior review/catalog: none material (ICLR 2026 confirmed incl. OpenReview poster). Review says "AppWorld and domain-reasoning results" -- correct; review does not mention that the headline online numbers adapt on the test stream and that the GEPA baseline used an extra validation set.
