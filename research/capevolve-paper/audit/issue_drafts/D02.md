# gate: default k_se=1.0 paired gate accepts ~16% of no-op candidates (~50% over 10 iterations); docs overstate what an accept means

_Draft for `skillberry-ai/cap-evolve`. Base SHA `e3cb513`. Defect id D02 (campaign audit, parent #743/#744)._

## Problem
The default accept rule is `mean(Δ) > 1.0*SE(Δ)`, a one-sided z-test at alpha≈0.159, applied to a sequence of candidates with the parent replaced on accept. Gate/SKILL documentation presents the bar as what makes an accept 'mean something'. There is no multiplicity correction across iterations.

## Code locations
- `core/cap_evolve/gate.py:422-459` and docstring L10-14
- `skills/algorithms/hill-climb/SKILL.md` ('Why the bar is Δ > k·SE')
- `core/cap_evolve/cli.py:956` (`--k-se` default 1.0), `templates/project/capevolve.yaml:93`
- Related: #351 (closed), #544, #113

## Reproduction
`python3.12 -I audit/repro/r3_fpr.py` (null candidates = same per-task true rates, Beta(.7,.7) difficulties):
```
T  trials | single null test | P(>=1 false accept in 10 iters)
30  1  0.161   0.505      30  5  0.159  0.534
60  3  0.160   0.577     140  3  0.169  0.540
```

## Impact
About half of all 10-iteration hill-climb runs on a no-op optimizer would bank at least one 'improvement'. Val-gain claims need a null-edit control arm; the gate must not be described as a 5% test.

## Proposed correction
Either (a) document it explicitly as a 16% screening heuristic and require fresh-trial confirmation before the headline, or (b) alpha-spend across iterations (e.g. k_se from a Bonferroni/Šidák schedule over `max_iterations`). Add a calibration test that simulates null candidates and asserts the documented false-accept rate.

## Acceptance test
- Simulation test in `core/tests` asserting per-test accept rate for null candidates equals the documented value within MC error.
- README/SKILL text states the false-accept rate.
