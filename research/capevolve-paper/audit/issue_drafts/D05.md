# agent-optimize finalize 'confirmation' pools selection-era trials with the fresh ones

_Draft for `skillberry-ai/cap-evolve`. Base SHA `e3cb513`. Defect id D05 (campaign audit, parent #743/#744)._

## Problem
`act.py finalize` tops up the champion's same tag by `--n-confirm` (default 3) trials and calls `judge(champion, 'seed')`. `judge` shells to `gate_check --mode reward_gated`, which loads all rollouts of the champion tag (`objectives.load_trials(run_dir, tag)`), i.e. the trials that produced the promotion plus the new ones. The digest `p_beat` pools by `cap_hash` across tags (ledger), a different pool.

## Code locations
- `skills/algorithms/agent-optimize/scripts/act.py:514-548` (confirm), `388-408` (`judge`)
- `skills/algorithms/agent-optimize/scripts/gate_check.py:260-263`
- `core/cap_evolve/objectives.py:113-136` (`load_trials`)
- `core/cap_evolve/eval_index.py:49-62` (`counts`, pooled by hash)

## Reproduction
Static: `sed -n 524,531p act.py`; `sed -n 260,263p gate_check.py`. (A synthetic reproduction needs a run dir; trivially: promote with n=3 trials, confirm adds 3 more under the same tag -> the verdict is computed on 6.)

## Impact
The confirm is not an independent replication. Winner's-curse bias is diluted, not removed, so 'confirmed on full val with fresh seeds' (SKILL.md) overstates the evidence; relates to the failed merged-candidate confirmation in campaign #744.

## Proposed correction
Write the confirm trials under a fresh tag (or mark ledger rows) and gate on fresh trials only; keep the pooled verdict as secondary. Refuse to seal unless the fresh-only verdict accepts.

## Acceptance test
- Unit test: with pre-existing champion rollouts that favour the champion and fresh rollouts equal to seed, finalize refuses to seal.
- `final.json` records both `confirm_fresh` and `confirm_pooled`.
